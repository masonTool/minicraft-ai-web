## 1. 现状：三层，不是两层

```
core/   410 个 .ts   世界模拟 / 规则 / 背包 / 合成 / 命令 / 联机协议   ← 基本零 DOM
render/ 33 个 .ts    WebGL2 + three.js 的 3D 世界
ui/     49 个 .ts    DOM 界面（约 2.1 万行，InventoryScreen 独占约 7,600 行）
        index.html   内联 CSS 约 5,700 行（设计令牌 / 原版配色 / 横屏断点 / 层叠约定）
        main.ts      约 2.06 万行（主循环 + 输入 + 一部分 HUD 接线）
```

**关键事实**：游戏逻辑本来就不在 DOM 里（全仓 `document.` 在 `core/` 只出现在
`I18n.ts` / `webglSupport.ts` / `ClientId.ts` / `hostCore.ts` 四个文件，都是环境探测）。
所以"搬到 canvas"= **重写界面层**，`core/` 一行不用动。

## 2. 路线：独立 2D canvas 覆盖层（不是塞进 WebGL）

| | A. 2D 覆盖层（**选它**） | B. 进 WebGL（正交相机 + 精灵批处理） |
| --- | --- | --- |
| 文字 | `fillText` 直接用系统字体 | 必须 SDF/MSDF 字形图集（含中日韩 = 动态图集） |
| 6 语言 | 零字体资源 | 构建期扫文案 + 运行期扩图集 |
| 调试 | 浏览器里能直接看/截图 | 基本靠肉眼 |
| 移植到原生 | 一般 | 最好 |

选 A 的唯一决定性理由：**文字**。B 的收益（一张纹理、一批四边形）只在"确定要出原生/主机版"
时才成立；在此之前，字形图集的成本会让整个迁移变成另一个项目（见决策 D1、D2）。

## 3. 目录与依赖方向

```
src/ui2d/
  text.ts      字体栈 / 测量缓存 / 分词 / 截断 / 折行 / drawText     ← 纯函数，离线可断言
  input.ts     hitRegionAt（纯函数） + Ui2DInput（指针路由）
  overlay.ts   2D 覆盖层：DPR、尺寸、清屏、销毁
  widgets.ts   画法：圆角矩形 / HUD 底板 / 进度条 / 原版按钮
  Hud2D.ts     组合：收状态 → 画（当前只有阶段 0 的三样）
  index.ts     汇总入口
```

依赖只能往下走：`面板/Hud2D → widgets/overlay → text/input`。
**禁止**反向依赖 `main.ts`，也禁止依赖 `ui/` 里的 DOM 组件（唯一例外 `ui/Device.ts`）。
这条约束是"将来整层换后端"的前提：`Hud2D` 只认 `Ui2DOverlay` 暴露的
`context + width/height`，换后端时改一个类。

## 5.1 已落地（阶段 1.5：快捷栏）

阶段 0 那三样（红闪 / Boss 条 / 破坏与进食进度）**选得对但看不见**：它们都是
"事件发生时才出现"的浮层，正常玩的时候屏幕上什么都没有，用户的原话是
"改的这几个地方都不太明显，看不出来效果如何"。于是 1.5 换成每帧都在眼前的快捷栏。

- `src/ui2d/Hotbar2D.ts`：面板（`#c6c6c6` + 3px 斜面 + 2px 黑描边）、9 个格子
  （`#8b8b8b` + 2px 斜面）、图标、数量（12px 四向描边）、序号（10px）、
  耐久条（3px 三档）、选中格（白框 + 半透明白底 + 上抬 2px + 放大 1.08 + 柔光）。
- **几何不抄常量**：输入是 `getBoundingClientRect()` 量出来的面板与格子矩形
  （相对覆盖层），所以断点、`env(safe-area-inset-bottom)`、转屏后的尺寸全自动跟上。
- **快照缓存**：状态签名不变时每帧只 `drawImage` 一次；换槽/捡东西/掉耐久/转屏才重建。
- **命中仍借 DOM**：`.slot` 设 `opacity: 0`、`#hotbar` 自己的底/斜角/描边设成透明
  （边框宽度保留，免得两侧按钮位移），点击与长按提示走原来那条绑定。
  ⚠️ 不能用 `visibility: hidden` / `display: none` —— 那样格子不再参与命中，
  `bindHotbarTouch` 与长按看物品会一起失效。
- 断言：`tests/ui2d.test.ts` 34 条（新增 12 条：内容盒 / 图标居中 / 数量与序号锚点 /
  耐久轨道与比例 / 选中格的缩放与上抬 / 快照原点 / 签名稳定性）。

## 5.2 阶段 0 的回顾（为什么它没能证明什么）

## 5.5 已落地（阶段 1：控件库）

七个控件的**画法 + 纯状态机**都在 `ui2d/controls.ts`，状态一律留在调用方。
判据来自 §4：每个控件都要有"命中 → 状态 → 回调"的离线断言，并且能在一页里摆一排。

| 控件 | 画 | 状态机（纯函数，可断言） |
| --- | --- | --- |
| 开关 | `drawToggle` | `toggleNext` |
| 滑块 | `drawSlider` | `sliderTrackRange` / `sliderRatioFromX` / `sliderRatioStep` |
| 下拉 | `drawDropdownField` / `drawDropdownMenu` | `dropdownMenuRect`（放不下自动翻上）/ `dropdownIndexAt` |
| 页签 | `drawTabs` | `tabRects` / `tabIndexAt` |
| 滚动列表 | `drawListRow` / `drawScrollbar` | `listMaxScroll` / `clampListScroll` / `listScrollByWheel` / `listVisibleRange` |
| 提示框 | `drawTooltip` | `tooltipRect`（下方放不下就翻上、左右夹进视口） |
| 弹窗 | `drawModalFrame` | `modalRect`（居中、小屏夹进视口） |

三条经验：

- **状态必须留在调用方**。canvas 没有"元素自己记得自己开着没有"，把状态和绘制混在一起，
  迟早演进出 DOM 那套 `class` 的第二种真相；所以这里只给 `draw*(ctx, rect, state)` 与纯函数。
- **两处几何不是"画"出来的**：下拉往哪翻、提示框贴哪边 —— DOM 版靠"挂 `body` + 浏览器 clamp"，
  canvas 得自己算，算错的症状是"偶尔被屏幕边切掉"，离线断言（21 条）正好钉这个。
- **弹窗面板要不透明**。用 `drawHudPanel`（半透明 HUD 底板）会把底下的列表文字透上来，
  看起来像字叠字；这里按原版用 `#232323` + `--pixel-bevel-dark` 的硬斜角。

预览页 `tools/preview/controls.html`（`?state=dropdown|tooltip|modal`、`?tint=1`）**故意打开**
`pointer-events`（游戏里铺满全屏的覆盖层必须关着），所以能真的点开关、拖滑块、滚列表。

## 5.6 已落地（阶段 2 收尾：三样提示条）

`ui2d/overlays.ts`：目标名（`#target-info`）、攻击蓄力条（`#attack-cooldown`）、
物品名浮标（`#selected-item-name`）。都由 `Hud2D.setTips()` 统一收口，画在**最上层**。

三处与前面几块不同的做法：

- **不做快照缓存**。三样加起来每帧也就两次 `fillText` + 一块 44×3 的小矩形，
  为它们维护签名反而更贵（前三块是"几十个图标/一整条面板"，量级完全不同）。
- **矩形仍然量 DOM**：目标名的宽度随文本变，触摸瞄准时 JS 还会改它的 `left/top`（`.pinned`），
  自己算等于把那套 CSS 再实现一遍；只在"文本 / 锚点 / 视口尺寸"变化时量。
- **物品名的淡出按时间算**（`itemNameAlpha(age)`：350ms 淡入 → 保持到 2000ms → 350ms 淡出），
  DOM 那边是 CSS `transition`。好处是暂停时不淡（暂停时 `shownAt` 不变），
  代价是**帧率低时会"跳格"**——这是刻意的取舍，见决策 D14。

断言：`tests/ui2d.test.ts` 51 条（本批 +5：蓄力条几何 44×3 与 +16px、进度量化到 2%、
物品名的三段曲线、全空不画、过期不画）。

## 5.8 已落地（阶段 3 前置：面板输入通道）

`ui2d/menu.ts` 的 `CanvasMenu` 顶替了浏览器白送的三件事：

| 浏览器给的 | canvas 里要自己做的 | 实现 |
| --- | --- | --- |
| 焦点（Tab / `:focus`） | 一个整数 + 循环上下 + Home/End | `menuFocusAfterKey` |
| 按钮的点击 | 行矩形 → `hitRegionAt` → 行 id | `regions()` / `handlePointer()` |
| `Enter` 触发 / `Esc` 关闭 | 按键翻译成**意图** | `handleKey()` 返回 `{activate}/ {close}/ {move}` |

三条边界（写死，别在调用方随意扩展）：

- **这一层不含任何游戏逻辑**：`handleKey` 只返回行 id，真正的"回到主菜单 / 删世界"由
  `main.ts` 按 id 分派。所以它连 `main.ts` 都不 import。
- **它也不决定"菜单打开时游戏该不该暂停/还收不收其它按键"**：那是调用方的事。

## 5.9 已接线（阶段 3 第一页：暂停菜单）

### 关键做法：不重写任何动作

（`pause.advancements` 那颗按钮在批次 20261024-1152 就被删过，抄表的人不会知道）。

### 为什么这一块选了"原位重画"，而不是像前面那样自己排版

1. F3 那串文案是**拼出来的多行字符串**（帧率、区块、坐标、维度、内存…），重排一遍

关着时一次都不读（默认就是关的）。计分板几乎不变，等于零成本。

## 5.13 已落地（阶段 3：主菜单 / 世界列表的**整页镜像**）

`ui2d/menuScreen.ts` 的 `MenuScreen2D`：把一块**已经写好的静态 DOM 界面**原样画到 canvas ——
读每段文字（矩形 + 计算样式的颜色/字号/字重/对齐）与每块底色/边框（含圆角），按原位重画；
DOM 只把 `opacity` 设 0 让位像素。已接：主菜单 `home` 与世界列表 `worlds`（`?ui2d=1`）。

### 与前面几块的根本区别

| 块 | 几何从哪来 | 像素谁排 | DOM 的交互 |
| --- | --- | --- | --- |
| 快捷栏 / 血条 | 量 DOM | **自己画**（像素级复刻） | 留着（`opacity: 0` 或 `visibility`） |
| 设置页 / 暂停菜单 | 自己算 | **自己画控件** | 留着（动作靠 `button.click()` 转发） |
| **主菜单（本批）** | 量 DOM | **照原位重画，不排版** | 留着（完全不动） |

### 为什么这里选"镜像"

主菜单是**静态**的，而且以后还会长东西（迷你游戏、资源包、账号…）。把布局抄进 canvas
等于每加一个按钮写两遍，而抄错的表现只是"有点歪"，没有断言抓得到。镜像不需要知道界面上
有什么：加按钮、改文案、换语言全部自动跟上。

### 三条边界（别越线）

- **`opacity: 0` 让位，不用 `visibility` / `display`** —— 按钮必须继续可点（与快捷栏同一条，
  `TIPS.md` 有记）。**滚动、焦点、输入、下拉展开全留在 DOM**，镜像层一概不管。
- **带 `<input>` 的视图不镜像**（`create` / 多人面板）：`<input>` 的当前值不在 `textContent`
  里，镜像过去是空框，比不迁移更差。
- **两处已知近似**：渐变底退化成纯色（世界卡片的缩略图偏暗 —— D22）、
  四边不等宽的像素斜角只能画一种颜色（按钮凸起感弱一点）。

### 签名与刷新

菜单没有"打开/切视图/滚动"的事件，所以 `MenuScreen2D` 每 4 帧比一次签名
（视口尺寸 + 所有可滚动元素的 `scrollTop` + 整块 `textContent`），变了才重读计算样式；
`main.ts` 另用 200ms 轮询发现"菜单开了 / 关掉了"（`WorldScreen` 不暴露这些事件）。

## 5.14 已落地（阶段 3 的硬骨头：文本输入 / 输入法）

`ui2d/textInput.ts` 的 `CanvasTextInput`：**屏幕外放一个看不见但可聚焦的 `<input>`**
承接所有输入（含中文输入法），canvas 只画 `value` / 光标 / 选区 / 组合态下划线。

三条不能破的约束（都是"看起来能跑、真机不能用"的形状）：

| 约束 | 为什么 |
| --- | --- |
| 用 `opacity: 0`，**不能用 `display: none` / `visibility: hidden`** | 那样元素拿不到焦点，移动端也不会弹软键盘 |
| `pointer-events: none` | 它只是"收字的管子"，不能让它在屏幕上拦点击；聚焦靠调用方显式 `focus()` |
| 组合态靠 `compositionstart/update/end`，**不靠 `value`** | 拼音阶段的字母已经在 `value` 里了，但"哪一段还没上屏"只有事件知道；下划线要画在那一段下面 |

其它细节：`Enter` 提交 / `Esc` 取消时**先看 `event.isComposing`**（组合中这两个键归输入法，
抢了就变成"打拼音时按回车直接提交了半截"）；退格按**码点**切（`Array.from`），
否则删 emoji 会留下半个代理对；文字超宽时 `visibleSlice` 只在光标顶到右边界才滚动。

断言：`tests/ui2d-textinput.test.ts` **18 条**（光标位置与夹取、插入/替换/退格、码点退格、
可见窗口与滚动、选区与光标矩形、闪烁周期）。

⚠️ **还没接进游戏**：新建世界表单、聊天空格、多人面板都还是 DOM 输入框。这一层是它们的
前置件 —— 接线要按"点在某块矩形上 → `open()`，每帧 `render(ctx, rect)`，提交时写回设置/消息"来做，
属于下一批。真机输入法（尤其安卓各家 WebView 的候选栏位置）也只能在真机验。

### 顺手修掉一个"只在游戏里才炸"的 bug：覆盖层的 z-index

`Ui2DOverlay` 的默认 `zIndex` 是 `1`（跟着 `#app` 里的 WebGL 画布走，那个位置是对的）。
但镜像的宿主是 `document.body`，而被镜像的目标自己带高 z-index：

| 目标 | 它自己的 z-index | 覆盖层必须 ≥ |
| --- | --- | --- |
| `#world-screen`（主菜单） | 40 | 45 |
| `#chat`（聊天） | 8 | 12 |

现在 `MenuScreenOptions.zIndex` 显式传，两个调用点各自写明理由。

> 这类"层叠上下文"问题离线断言查不到、预览页也照不出来，只有把它放到真实 DOM 里才会暴露。
> 记住判据：**镜像哪棵树，覆盖层就要排在它的层叠顺序之上**。

`readCanvasBlits()` / `drawCanvasBlits()`，绘制顺序定为 **底 → 位图 → 文字**
（与 DOM 里"槽位底 → 图标 → 数量"一致）。

### 一个签名抓不到的坑：只换了图、没换字

## 5.22 修复（镜像必须自己裁剪：滚出去的、溢出面板的都不该画）

用户 2026-10-27：「点左侧那个分类按钮时，他会把所有的内容都平铺出来，直到所有物品栏都
伸出到弹窗以外。正常来说应该收在弹框内、物品滚动显示。」

根因：**镜像不知道 `overflow`**。`readTextRuns` / `readTextBlocks` / `readCanvasBlits`
一律按元素的 `getBoundingClientRect()` 画，而 DOM 那边是靠 `overflow: hidden / auto` 裁的 ——
`.inv-grid.inv-creative` 是 `max-height: 46vh; overflow-y: auto`，96 格里滚出去的那些
照样被读出来画到面板外面，于是"所有物品平铺、伸出弹窗"。

修法（`textPanel.ts`）：

- `makeClipQuery(root, origin)`：从元素往上走到 `root`（含），把每个**会裁剪的祖先**
  （`overflow-x/y` 不是 `visible`）的 **padding-box**（`clientLeft/Top/Width/Height`，
  自然排除边框与滚动条）求交；结果按元素缓存。
- 三个读取函数都给每条记录带上 `clip`，并把**完全落在裁剪框外的直接跳过**（顺带省掉一堆 `fillText`）。
- 三个绘制函数用 `paintClipped(ctx, clip, paint)`：有裁剪就 `save → rect → clip → paint → restore`。

于是滚动区里"滚出去的部分"和"溢出面板的部分"都不再被画 —— 与浏览器一致。
⚠️ 滚动本身仍由 DOM 处理（覆盖层是 `pointer-events: none`，滚轮/触摸照旧落到下面那层），
canvas 只负责"看得见的那一块"。

## 5.23 修复（首页按钮错位：量早了，而且再也不重量）

用户 2026-10-27：「首页的三个按钮显示位置是错的，点击的位置也是错的。」

**根因是"量太早 + 不重量"**，用真 `WorldScreen` 复现（`tools/preview/world-real.html`，
把 `index.html` 那段 `<style>` 用 `fetch` 搬过来，才是真布局）：

```
button「游戏」的 y：150ms 时 483 → 1650ms 时 309     （差 174px）
```

字体/排版稳定后按钮整体上移。而 `MenuScreen2D` 的签名只看"文字 / 输入框值 / 滚动位置"，
**几何不在签名里**，于是第一帧量到的旧位置被一直沿用：

- canvas 画在 y≈483（屏幕下半），DOM 真的在 y≈309 → 看起来"按钮错位"；
- 点击落到 DOM 的真实位置，于是"点也点不中"。

三处一起修：

1. **签名带上几何**：`source.getBoundingClientRect()` + `scrollWidth/scrollHeight`；
2. **所有镜像都开 `pollMs`**（主菜单 200ms、聊天输入行 250ms、多人 200ms、背包 120ms）：
   定期强制重读，兜住"盒子尺寸没变、内部元素却动了"的情况；
3. **等字体**：`document.fonts.ready.then(sync)`，字体到位后再量一遍。

### 顺带修掉截断："Minicra…"

大标题（`world-logo`，48px + 负 `letter-spacing`）量出来比盒子宽，被 `maxWidth` 截成
"Minicra…"。现在 `readTextRuns` 会读 `letter-spacing`，把 **`-letterSpacing × 字数`**
记进 `TextRun.widthSlack`，绘制时加到 `maxWidth` 上（F3/计分板不受影响：它们的补偿是 0）。

> 教训：**镜像的正确性 = 一次测量的正确性 × 测量时机的正确性**。
> 后者更难发现——错位看起来像"画错了"，实际是"画的是刚打开那一瞬间的旧布局"。

## 5.24 修复（触摸拖拽滚动：手贴着列表，列表要跟着走）

用户 2026-10-27：「滑动物品滚动的能力不行，世界列表也滑不动；就应该像普通列表一样，
手贴着列表上下移动，它跟手。」

根因：游戏为了拖动视角把 `html, body` 的 `touch-action` 设成 `none`（`index.html` 第 236 行）。
内层滚动容器即使写了 `touch-action: pan-y`，各家 WebView 的处理也不一致 —— 结果就是
手指贴着列表滑，列表纹丝不动。

修法：`MenuScreen2D` 自己接管（`bindDragScroll`）：

- `pointerdown`（触摸/笔）→ 从命中元素往上找**第一个真的能滚**的祖先
  （`scrollHeight > clientHeight + 2` 且 `overflow-y` 是 auto/scroll）；
- 纵向位移超过 **8px** 才算"这是滑动"（之前一律放过：点击、物品拖拽、横向拖动都不受影响）；
- 之后每次 `pointermove`：`scrollTop = startScroll - dy`（夹在 0~max），并立刻 `refresh(true)`
  —— 不等到 `pollMs`，所以是"跟手"而不是"两帧一跳"；
- `pointerup/cancel` 结束；`input/textarea/select` 上的手势不劫持（免得影响选字）。

**为什么不做成"通用滚动容器"**：镜像里的滚动条是 UA 画的，canvas 里没有（已记 M35）；
惯性（松手后衰减）也没做（M36），现在是"松手即停"，手感偏硬但它可预测。

验证（Playwright 合成 touch 指针事件）：`inventory-mirror.html?creative=1` 里向上拖 60px →
`grid.scrollTop` 从 **0 变 60**，画面同步重画。

## 5.25 修复（背包左右立栏没上 canvas：镜像根选错了一层）

用户 2026-10-27：「左右两边的按钮 —— 左边的分类按钮、仓库按钮，右边的人物、成就，那三颗（也还是 DOM）」。

原因很简单：镜像根取的是 `.inv-panel`，而 DOM 结构是

```

```

（而且漏掉的部分看起来"正常"，只是它还是 DOM）。

## 5.26 已落地（自绘滚动条 + 拖拽惯性）

## 5.29 补齐（M35 的另一半：滚动条可拖）

- 按下时先做一次**滚动条命中**（4px 宽的条给 ±3px 宽容），命中就进入"拖条"模式，
  不再走内容拖拽 —— 否则在右边缘拖会变成滚动内容，拇指反而纹丝不动。
- 抓在**拇指上**：记下 `offset = 按下点 - 拇指顶`，拖的时候拇指不会往上跳。
- 抓在**轨道空白**：先把拇指中心跳到按下点（等价于点一下翻页），再继续拖。
- 换算：`ratio = (y - offset - 轨道顶) / (轨道高 - 拇指高)`，`scrollTop = ratio × 可滚距离`；
  两端夹住，`travel <= 0` 或不可滚时直接不理。

验证（Playwright 合成 touch）：创造物品栏先把 `scrollTop` 归零，抓住右边缘的拇指往下拖 72px →
`scrollTop` **0 → 153**（可滚距离 168），松手停住（拖条不产生惯性，与手机一致）。

## 5.30 修复（背包两处：拖着的东西不见了 / 悬停没有反馈）

**① 拖着拖着东西没了**（这一批引入、这一批修掉）

之前为了让位像素，给 `#inv-held` 加了 `html.ui2d-inv #inv-held { opacity: 0 }`。
但 `#inv-held` 挂在 `#inventory-screen` 下、在镜像根 `.inv-shell` **外面** —— 藏了却没人画，
于是拖动物品的过程中那一叠直接消失，松手才又出现。现在这条规则已删除：
它继续由 DOM 画（镜像覆盖层是透明的，照样看得见）。

> 教训与 `.inv-shell` 那次同源：**让位之前先确认"由谁来画"**。让位 + 没人接手 = 内容消失，
> 而且这种"消失"只在特定操作（拖动）中出现，静态截图完全正常。

**② 悬停高亮**（`MenuScreen2D.setHighlight`）

`.inv-slot:hover` 是 CSS 画的，但在 `opacity: 0` 的子树里看不见 —— 玩家会以为"这一格点不动"。
现在由调用方喂一个矩形，canvas 画一圈白框 + 薄白底：

- `main.ts` 用 **`elementFromPoint`** 找指针下那一格（`opacity: 0` 的子树仍参与命中），
  所以它天然跟着滚动、跟着布局走，不用自己维护几何；
- `setHighlight()` **只重画、不重读 DOM**：每帧都可能喂同一个矩形，重读整棵树要几十次
  `getComputedStyle`；现在只比一次矩形，变了才用缓存重画。

## 5.35 接入（M26b 第二步：`?ui2dinv2d=1` 自绘面板叠加在同一位置）

自绘这条路还不支持 19 种工作站的布局，**直接替换会丢功能**。所以先做"叠加"：

- 数据直接读 `this.inventory`（`Inventory` 本来就有 `get/set`）；

## 5.36 补齐（自绘面板的六种操作与 DOM 对齐；触摸"先按住再决定"）

`InventoryPanelHost` 原来只接了左键取放 + 左键拖拽均分，这一批把剩下的补齐，
规则全部复用 `inventoryModel` 里已经断言过的纯函数：

| 操作 | 行为 | 用到的函数 |
| --- | --- | --- |
| 左键 | 取整叠 / 放入 / 合并 / 交换 | `leftClick` |
| 左键拖过多格 | 均分（余数给前面） | `distributeDrag` |
| 右键 | 取一半（向上取整）/ 放一个 | `rightClick` |
| 右键拖过多格 | **每格放一个**（不是均分） | `rightDragDistribute` |
| 双击（400ms 内同格） | 收集同类凑满；凑不到就退化成快速移动 | `doubleClickGather` + `quickMove` |
| 长按（500ms 不动） | 取走**一半** | `splitTake` |

### 触摸端必须先"按住再决定"

鼠标是"按下即拿起"，触摸不能照抄 —— 那样长按分堆永远拿不到（东西已经在手上了，
第一版实测就是长按后**整叠**跑到手上）。所以触摸按下时只记 `pendingTouch` 并起计时器：

- 松手时还在等 → 这是一次点击 → `leftClick`
- 500ms 没动 → 分堆（`splitTake` 一半），并清掉 `pendingTouch`（松手不该再点一次）
- 滑动超过 8px → 取消计时器 → `leftClick` 拿起，之后按拖拽处理

### 验收（Playwright 合成指针事件，读 `window.__probe()`）

| 操作 | 结果 |
| --- | --- |
| 右键点 64 那格 | 格子 32、手上 32 |
| 右键拖过 10/11 | 各放 1 个（第 9 格被别的物品占着 → 跳过） |
| 双击 12 那格 | 手上 12 + 41 = **53**，第 1 与第 27 格都空 |
| 触摸长按 64 | 格子 32、手上 32，且松手不再拿起 |
| 触摸拖 0→4..7 | 64 分成 **16×4**（第 5 格是别的物品 → 跳过） |

⚠️ 长按分堆现在只取一半：DOM 版会弹出"拖到某处选数量"的滑条，那套 UI 还没画（M31 里记着）。

## 5.37 补齐（自绘面板的"长按选数量"：按住那格 + 横move 调 + 松手确认）

上一批长按只取一半，DOM 版是"弹一条滑条选数量"。这批把它做成**不用额外命中区域**的形态：

- 长按 500ms → 进入 `split` 状态：目标格压暗、正上方出现一块小牌（数量 + 绿色占比条）；
- 横向移动按 `splitCountFromDrag(dx, max)` 换算：**每 12px 加 1 个**，夹在 `1..max`（纯函数，4 条断言）；
- 松手才真正 `splitTake(count)` 落进光标 —— 中途改主意直接把手指移回来再松手即可。

为什么不照抄"弹滑条"：滑条要额外一块命中区域，手指得**离开格子**去拖它，手机上一个滑就点歪了；
而"按住不放 + 横move"是原版基岩版的做法，手指始终在格子上，不会跑。

### 一个画序坑

第一版把"压暗"画在 `drawInventoryPanel` **之前**，结果槽位底色把它整个盖住（截图里看不出被选中）。
压暗与数量牌必须画在**面板之后**（`drawInventoryPanel` 会重画整块面板底与每格底色）。

### 验收（Playwright 合成 touch）

长按第 0 格（64）→ 右移 120px（牌上显示 11）→ 松手：格子 **53**、手上 **11**。

## 5.38 扩展（自绘面板支持工作站：`extra` 槽位组）

之前 `layoutInventoryPanel` 只会排"27 + 9"，也就是纯背包。合成台/熔炉/铁砧这些界面
需要在玩家背包**上方**再加一组槽位（3×3 合成格、原料+燃料……），右侧还可能有一个**结果格**。

现在布局函数接受 `extra: { cols, rows, result? }`：

## 5.39 补齐（自绘背包的提示框与耐久条）

**为什么必须补**：镜像方案里 tooltip 一直是 DOM（`#item-tooltip`，z-index 60）。一旦自绘面板接管指针，
DOM 的 `hover` 就再也收不到事件 —— 提示框会**彻底消失**，而且这种"丢了功能"很容易被当成"还没做"。

`ui2d/itemTooltip.ts`：

- 观感照抄 `#item-tooltip`：近黑紫底 `#100010f2`、2px 紫边、左侧稀有度色条、白字带阴影；
- 位置逻辑抽成纯函数 `itemTooltipRect()`：默认指针右下、右边放不下翻左、下面放不下翻上、最后夹进视口；
- 内容由调用方注入（`describeOf`）：名字/说明/耐久在 `core`（`itemName` / `itemDef`），`ui2d` 不依赖 `core`。

顺带把**槽位里的耐久条**接上（`durabilityOf`）：之前自绘面板传的是 `null`，工具类物品光秃秃的。

断言 4 条（位置：右下、翻左、翻上、夹进视口）。

⚠️ 提示框只画"名字 + 说明行 + 耐久"，**附魔列表与铁砧改名还没画**（DOM 版有）。

## 5.40 合流（"拿在手上那一叠"只能有一份状态）

替换前最后一块地基：**光标合流**。

DOM 面板自己有一份 `held`（画在 `#inv-held` 里），自绘面板也有一个 `cursor`。两份各画各的
结果很具体：拖动时屏幕上出现**两叠**，一叠跟着 `#inv-held`、一叠跟着 canvas。

所以 `InventoryPanelHost` 加了 `externalCursor: { get, set? }`：

- 入口（`handlePointer` / `open`）先 `pullCursor()` 从外部拉一次；
- 出口在 `render()` 里 `pushCursor()` 推回去（没给 `set` 就只读）。

游戏侧现在这样接（`?ui2dinv2d=1` 的叠加层）：

```ts
externalCursor: { get: () => this.inventoryScreen.heldStack }
```

`InventoryScreen` 因此开放了一个只读的 `heldStack` getter。**只读是刻意的**：这一阶段自绘面板
不吃输入，`set` 一旦写上就会与 DOM 的逻辑打架；等自绘真正接管输入时再加 setter，那时 DOM 面板
已经不渲染了，也就不存在两份。

断言/验证：预览页 `?ext=1` 用一个外部对象模拟 DOM 的 `held` —— 打开时面板立刻画出 `3×5`，
移动指针后仍是 `3×5`，而**外部对象没被写脏**（只拉不推）。

## 5.41 最后一步（`?ui2dinv=1`：自绘面板真正接管输入）

前一批把光标合流（只读）做了，这一批让自绘面板**吃指针**：

- 覆盖层 `pointer-events: auto`，`pointerdown/move/up` 喂给 `InventoryPanelHost`；
- DOM 面板退场：`html.ui2dinv #inventory-screen .inv-shell { visibility: hidden }`、
  `html.ui2dinv #inv-held { visibility: hidden }`（**visibility 不是 display** —— 里面的按钮
  和输入框还要能被 `elementFromPoint` 命中、被读值）；
- 光标写回 DOM：`externalCursor.set` → `InventoryScreen.setHeldStack()`，两份状态在这里合成一份。

### 面板外的控件怎么办：`forwardClickAt()`

关闭 ×、左右立栏（分类/仓库/人物/成就）在面板**外面**，画布盖上去之后就点不到了。
这一批不重画它们，改用一条转发通道：

```ts
canvas.style.pointerEvents = 'none';       // 同一帧内临时让开
const el = document.elementFromPoint(x, y);
canvas.style.pointerEvents = 'auto';       // 立刻恢复（用户看不到闪烁）
el.dispatchEvent(new MouseEvent('click', { bubbles: true }));
```

只在**没有拖动**时转发：拖动是操作槽位的手势，松手时不该顺手点一下别的东西。

⚠️ 只转发 `click`：按钮/页签够用，需要 `pointerdown/move/up` 序列的控件（拖拽抽屉）不在范围内。

### 验收（预览页，画布盖住一颗 DOM "关闭"按钮）

- 点面板**外**（画布上面、按钮真实位置）→ 按钮的 `click` 触发（`closed: false → true`）；
- 点面板**内**（第 0 格）→ 拿起 64、`closed` 仍为 `false`（没有误转发）。

## 5.42 补齐 + 遗漏盘点（数字键换槽 / Shift 快速移动 / 拖出丢弃）

### 本批补的三样

| 输入 | 行为 | 实现 |
| --- | --- | --- |
| 数字键 `1`~`9` | 把**悬停那格**与对应快捷栏格交换（不经过光标） | `swapSlots()` + `host.handleKey('DigitN')` |

## 5.48 收尾（M41 光标写回、M43 死亡界面/引导卡、M38 创造物品栏第一版）

### M41：`Q` 丢掉的东西不能被我们写回去

接管模式下 `Q` 由 DOM 的 keydown 处理（读的是同一份 `held`），本来能丢。但**下一帧重画会把它推回去** ——
`render()` 原来每帧都 `pushCursor()`，等于用我们手里的旧值覆盖了 DOM 刚清空的 `held`：
表现是"按 Q 丢不掉"，而且看起来像按键没生效。

修法：加 `cursorDirty` —— 只有**我们自己改动过**才推，否则先拉一次。
于是外部改动（Q 丢弃、快捷键换槽）在下一次重画时被正确吸收，也不会被覆盖。
验收：预览页 `?ext=live`（可写的外部光标）→ 外部把 `held` 置空后，自绘侧 `held` 也变 `null`，
**外部对象没有被写回去**。

（三种烧燃料的必须 `{ flame: true, result: true }`）。

### `ui2d/armorRules.ts`：装备列不是"5 个普通格子"

`canPlaceInSideSlot(slot, itemKind)` 三条规则：盔甲格只收对应部位、副手什么都收、空手永远能放；
`sideSlotAt(index, sideStart)` 把下标换算成部位（**不能写死 0..4**：装备列可能排在工作站槽位之后，
写死会让规则作用到错误的格子）。物品属于哪一类由调用方给（品类在 `core`，`ui2d` 不依赖它）。

### 这一批**没有**做的

把这两样接进 `?ui2dinv=1`：需要游戏侧把「当前打开的是哪个容器」与「物品的装备品类」喂给宿主，
而那条链路只能在真机里验。表与规则已经可以用，接的是十行代码。

## 5.3 调试遮罩：一块黄色告诉你"这块是谁画的"

`?ui2d=1&ui2dtint=1`（只在 `ui2d` 打开时生效）。屏幕上**每一块黄色的地方就是 canvas 画的**，
其余颜色来自 DOM / WebGL。预览页同理：`tools/preview/hotbar.html?tint=1`、
`tools/preview/hud.html?only=boss&tint=1`。

- 实现只有一句（`ui2d/debug.ts`）：所有绘制结束后把 `globalCompositeOperation` 切成
  `source-atop`，整块刷一层半透明黄 —— 合成器只染"**已经有像素的地方**"，
  于是不用维护"这一帧画了哪些矩形"，将来新增控件自动被覆盖。
- 为什么需要它：迁得对的时候**外观与 DOM 一模一样**，看的人根本分不出哪块换了
  （阶段 0 的教训，用户原话"改的这几个地方都不太明显"）。遮罩把"进度"从
  "肉眼比像素"变成"数黄块"。
- ⚠️ 三条边界：① 只是调试开关，**不进设置页**；② **不跟 `ui2d=1` 绑定** ——
  多一次全屏填充会让帧率 A/B 失真，颜色也不对，真机验收时容易被当成 bug；
  ③ 它是"整层"的，同屏多样东西时看不出哪块对应哪个控件（要点名得另加标签，本批不做）。
- 一个反直觉但正确的现象：**红闪打开时整屏都是黄的** —— 因为红闪本身就是全屏 canvas 填充，
  遮罩忠实地把整层都染了。

## 6. 判定不搬 / 搬法特殊（写清楚，免得下次重新踩）

| 东西 | 结论 | 原因 |
| --- | --- | --- |
| **准星** `#crosshair` | **不搬**（阶段 0 已排除） | 靠 `mix-blend-mode: difference` 与下层画面差值混合，属于 DOM 合成器能力；2D canvas 的 `difference` 只在本图层内合成，叠到 WebGL 上就是白十字，浅色场景反而看不见。真要搬：单独一张 canvas 并保留那条 CSS。 |
| **文本输入**（聊天/告示牌/铁砧/搜索/世界名） | **DOM 必须留** | canvas 无法唤起系统输入法（IME）。方案：**隐藏 `<input>/<textarea>` 收字 + canvas 显示**，自己处理 composing 下划线、光标、选区、粘贴。`ui/Keyboard.ts` 的 `--kb-inset`（键盘不挤压画面）要在 canvas 版重新对齐。 |
| 长按/拖拽/连发 | 搬（阶段 4） | 现在靠 DOM 元素级 pointer 事件 + 定时器；canvas 里要自己记"按下的是哪个区域、手指移出即取消"（`Ui2DInput` 已经按这个语义写）。 |
| **快捷栏的点击/长按**（阶段 1.5） | **画在 canvas、命中仍走 DOM**（过渡） | 覆盖层的 `pointer-events` 是**元素级**的：铺满全屏，打开就吃掉 `#touch-look` 的视角手势。区域级穿透要等阶段 6 重做手势层，这一批不值得冒险 —— 所以格子设 `opacity: 0`（**不是** `visibility: hidden`，那会连命中一起关掉）。 |
| 原生控件（`<select>`、滚动条、tooltip 的 title） | 搬（自己画） | 没有等价物；下拉要挂到最上层避免被裁切（DOM 版挂 `body` 也是这个原因）。 |
| 无障碍（`role` / `aria-label` / 键盘 Tab） | **会退化** | canvas 对读屏是一张图。缓解：保留一层不可见的镜像节点（`aria-hidden` 之外），或至少在开关打开时给出可访问的替代入口。这条要写进发布前的检查表。 |
| 全屏 / 剪贴板 / 文件下载 / 指针锁 | DOM API 不变 | 这些本来就不是"绘制"，`ui/Fullscreen.ts` 等模块继续用。 |

## 7. 迁移 checklist（每个面板都要过一遍）

1. **色值只抄不猜**：`widgets.ts` 的 `PALETTE` 与 `index.html` 的 `--mc-*` / `--hud-*`
   必须一一对应；改一处要同步另一处（迁移期两边并存，色漂是最难发现的一类回归）。
2. **文案必须走 `t()` / `tp()`**：canvas 没有 `textContent` 给 i18n 审计扫，
   所以 `audit:i18n` 看不到的漏翻会直接画到玩家脸上。新面板的文案一律先进 `locales/`。
3. **绘制单位是 CSS px**：不要自己乘 DPR（`overlay` 已经 `setTransform`）。
4. **`pointer-events` 默认关**：只有真有可点区域时才打开（`Ui2DInput.setRegions` 自动做），
   否则铺满全屏的层会吃掉触摸端的视角手势。
5. **手机横屏是第一场景**：所有断点先在 844×390 下看，再回去看 PC。
6. **关掉开关必须能完全回退**：每个面板迁移时保留 DOM 实现，直到该阶段真机验收通过再删。

## 8. 门禁与测试改写（这条最容易被低估）

- `tools/ui-test.ts` 约 **6,400 行**断言，其中很大一撮是**对源码文本与 CSS 做字符串匹配**
  （例如"设置行容器不再用 label"、"dropdown 必须挂 body"、`index.html` 里的某条样式）。
  面板一旦搬到 canvas，这些断言会**成片变红**，而且红的原因不是功能坏了。
- 处置顺序：**先加新的**（对 `Ui2DOverlay` 的绘制描述 / 布局纯函数做断言），
  **再删旧的**（DOM 实现删除的同一次提交里删掉对应断言）。不要先删后加 —— 中间那段空窗期
  等于没有回归保护。
- 阶段 0 已经示范了正确的粒度：把"排版决策"（折行/截断）与"几何换算"（Boss 条宽度、
  进度条位置）做成纯函数，断言打在这两处，而不是打"某一个像素长什么样"。

## 9. 现在的风险清单

1. **真机帧率未知**（最大风险）：DOM 合成层 vs 多一张全屏 canvas，谁更便宜要在真机上量。
2. **输入法**（阶段 3 的硬骨头）：隐藏 input 的光标/选区/composing 体验，安卓各家 WebView 差异大。
3. **背包交互**（阶段 4）：4 天能过、8 天也正常；它的交互全是点/拖/长按/连发的组合。
4. **门禁红灯期**：阶段 2~5 期间 `ui-test` 会持续有失败项，必须"边迁边绿"，不能攒到最后。
