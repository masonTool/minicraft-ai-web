## 1. 现状：三层，不是两层

```
core/   410 个 .ts   世界模拟 / 规则 / 背包 / 合成 / 命令 / 联机协议   ← 基本零 DOM
render/ 33 个 .ts    WebGL2 + three.js 的 3D 世界
ui/     49 个 .ts    DOM 界面（约 2.1 万行，InventoryScreen 独占约 7,600 行）
        index.html   内联 CSS 约 5,700 行（设计令牌 / 原版配色 / 横屏断点 / 层叠约定）
        main.ts      约 2.06 万行（主循环 + 输入 + 一部分 HUD 接线）
```

**关键事实**：游戏逻辑本来就不在 DOM 里（全仓 `document.` 在 `core/` 只出现在
`I18n.ts` / `webglSupport.ts` / `ClientId.ts` / `hostCore.ts` 四个文件，都是环境探测）。
所以"搬到 canvas"= **重写界面层**，`core/` 一行不用动。

## 2. 路线：独立 2D canvas 覆盖层（不是塞进 WebGL）

| | A. 2D 覆盖层（**选它**） | B. 进 WebGL（正交相机 + 精灵批处理） |
| --- | --- | --- |
| 文字 | `fillText` 直接用系统字体 | 必须 SDF/MSDF 字形图集（含中日韩 = 动态图集） |
| 6 语言 | 零字体资源 | 构建期扫文案 + 运行期扩图集 |
| 调试 | 浏览器里能直接看/截图 | 基本靠肉眼 |
| 移植到原生 | 一般 | 最好 |

选 A 的唯一决定性理由：**文字**。B 的收益（一张纹理、一批四边形）只在"确定要出原生/主机版"
时才成立；在此之前，字形图集的成本会让整个迁移变成另一个项目（见决策 D1、D2）。

## 3. 目录与依赖方向

```
src/ui2d/
  text.ts      字体栈 / 测量缓存 / 分词 / 截断 / 折行 / drawText     ← 纯函数，离线可断言
  input.ts     hitRegionAt（纯函数） + Ui2DInput（指针路由）
  overlay.ts   2D 覆盖层：DPR、尺寸、清屏、销毁
  widgets.ts   画法：圆角矩形 / HUD 底板 / 进度条 / 原版按钮
  Hud2D.ts     组合：收状态 → 画（当前只有阶段 0 的三样）
  index.ts     汇总入口
```

依赖只能往下走：`面板/Hud2D → widgets/overlay → text/input`。
**禁止**反向依赖 `main.ts`，也禁止依赖 `ui/` 里的 DOM 组件（唯一例外 `ui/Device.ts`）。
这条约束是"将来整层换后端"的前提：`Hud2D` 只认 `Ui2DOverlay` 暴露的
`context + width/height`，换后端时改一个类。

## 5.1 已落地（阶段 1.5：快捷栏）

阶段 0 那三样（红闪 / Boss 条 / 破坏与进食进度）**选得对但看不见**：它们都是
"事件发生时才出现"的浮层，正常玩的时候屏幕上什么都没有，用户的原话是
"改的这几个地方都不太明显，看不出来效果如何"。于是 1.5 换成每帧都在眼前的快捷栏。

- `src/ui2d/Hotbar2D.ts`：面板（`#c6c6c6` + 3px 斜面 + 2px 黑描边）、9 个格子
  （`#8b8b8b` + 2px 斜面）、图标、数量（12px 四向描边）、序号（10px）、
  耐久条（3px 三档）、选中格（白框 + 半透明白底 + 上抬 2px + 放大 1.08 + 柔光）。
- **几何不抄常量**：输入是 `getBoundingClientRect()` 量出来的面板与格子矩形
  （相对覆盖层），所以断点、`env(safe-area-inset-bottom)`、转屏后的尺寸全自动跟上。
- **快照缓存**：状态签名不变时每帧只 `drawImage` 一次；换槽/捡东西/掉耐久/转屏才重建。
- **命中仍借 DOM**：`.slot` 设 `opacity: 0`、`#hotbar` 自己的底/斜角/描边设成透明
  （边框宽度保留，免得两侧按钮位移），点击与长按提示走原来那条绑定。
  ⚠️ 不能用 `visibility: hidden` / `display: none` —— 那样格子不再参与命中，
  `bindHotbarTouch` 与长按看物品会一起失效。
- 断言：`tests/ui2d.test.ts` 34 条（新增 12 条：内容盒 / 图标居中 / 数量与序号锚点 /
  耐久轨道与比例 / 选中格的缩放与上抬 / 快照原点 / 签名稳定性）。

## 5.2 阶段 0 的回顾（为什么它没能证明什么）

## 5.5 已落地（阶段 1：控件库）

七个控件的**画法 + 纯状态机**都在 `ui2d/controls.ts`，状态一律留在调用方。
判据来自 §4：每个控件都要有"命中 → 状态 → 回调"的离线断言，并且能在一页里摆一排。

| 控件 | 画 | 状态机（纯函数，可断言） |
| --- | --- | --- |
| 开关 | `drawToggle` | `toggleNext` |
| 滑块 | `drawSlider` | `sliderTrackRange` / `sliderRatioFromX` / `sliderRatioStep` |
| 下拉 | `drawDropdownField` / `drawDropdownMenu` | `dropdownMenuRect`（放不下自动翻上）/ `dropdownIndexAt` |
| 页签 | `drawTabs` | `tabRects` / `tabIndexAt` |
| 滚动列表 | `drawListRow` / `drawScrollbar` | `listMaxScroll` / `clampListScroll` / `listScrollByWheel` / `listVisibleRange` |
| 提示框 | `drawTooltip` | `tooltipRect`（下方放不下就翻上、左右夹进视口） |
| 弹窗 | `drawModalFrame` | `modalRect`（居中、小屏夹进视口） |

三条经验：

- **状态必须留在调用方**。canvas 没有"元素自己记得自己开着没有"，把状态和绘制混在一起，
  迟早演进出 DOM 那套 `class` 的第二种真相；所以这里只给 `draw*(ctx, rect, state)` 与纯函数。
- **两处几何不是"画"出来的**：下拉往哪翻、提示框贴哪边 —— DOM 版靠"挂 `body` + 浏览器 clamp"，
  canvas 得自己算，算错的症状是"偶尔被屏幕边切掉"，离线断言（21 条）正好钉这个。
- **弹窗面板要不透明**。用 `drawHudPanel`（半透明 HUD 底板）会把底下的列表文字透上来，
  看起来像字叠字；这里按原版用 `#232323` + `--pixel-bevel-dark` 的硬斜角。

预览页 `tools/preview/controls.html`（`?state=dropdown|tooltip|modal`、`?tint=1`）**故意打开**
`pointer-events`（游戏里铺满全屏的覆盖层必须关着），所以能真的点开关、拖滑块、滚列表。

## 5.6 已落地（阶段 2 收尾：三样提示条）

`ui2d/overlays.ts`：目标名（`#target-info`）、攻击蓄力条（`#attack-cooldown`）、
物品名浮标（`#selected-item-name`）。都由 `Hud2D.setTips()` 统一收口，画在**最上层**。

三处与前面几块不同的做法：

- **不做快照缓存**。三样加起来每帧也就两次 `fillText` + 一块 44×3 的小矩形，
  为它们维护签名反而更贵（前三块是"几十个图标/一整条面板"，量级完全不同）。
- **矩形仍然量 DOM**：目标名的宽度随文本变，触摸瞄准时 JS 还会改它的 `left/top`（`.pinned`），
  自己算等于把那套 CSS 再实现一遍；只在"文本 / 锚点 / 视口尺寸"变化时量。
- **物品名的淡出按时间算**（`itemNameAlpha(age)`：350ms 淡入 → 保持到 2000ms → 350ms 淡出），
  DOM 那边是 CSS `transition`。好处是暂停时不淡（暂停时 `shownAt` 不变），
  代价是**帧率低时会"跳格"**——这是刻意的取舍，见决策 D14。

断言：`tests/ui2d.test.ts` 51 条（本批 +5：蓄力条几何 44×3 与 +16px、进度量化到 2%、
物品名的三段曲线、全空不画、过期不画）。

## 5.8 已落地（阶段 3 前置：面板输入通道）

`ui2d/menu.ts` 的 `CanvasMenu` 顶替了浏览器白送的三件事：

| 浏览器给的 | canvas 里要自己做的 | 实现 |
| --- | --- | --- |
| 焦点（Tab / `:focus`） | 一个整数 + 循环上下 + Home/End | `menuFocusAfterKey` |
| 按钮的点击 | 行矩形 → `hitRegionAt` → 行 id | `regions()` / `handlePointer()` |
| `Enter` 触发 / `Esc` 关闭 | 按键翻译成**意图** | `handleKey()` 返回 `{activate}/ {close}/ {move}` |

三条边界（写死，别在调用方随意扩展）：

- **这一层不含任何游戏逻辑**：`handleKey` 只返回行 id，真正的"回到主菜单 / 删世界"由
  `main.ts` 按 id 分派。所以它连 `main.ts` 都不 import。
- **它也不决定"菜单打开时游戏该不该暂停/还收不收其它按键"**：那是调用方的事。

藏起来、由 canvas 接管那一页的输入 —— 那一步接错就是"Esc 打不开/关不掉"，值得单独一批。

## 5.9 已接线（阶段 3 第一页：暂停菜单）

### 关键做法：不重写任何动作

```ts
// 激活：
this.pause2dButtons[index].click();
```

（`pause.advancements` 那颗按钮在批次 20261024-1152 就被删过，抄表的人不会知道）。

| --- | --- | --- |

### 为什么这一块选了"原位重画"，而不是像前面那样自己排版

1. F3 那串文案是**拼出来的多行字符串**（帧率、区块、坐标、维度、内存…），重排一遍

### 代价与门禁

`readTextRuns` 要调 `getComputedStyle`，**会触发样式重算**。所以 `main.ts` 里先拼一个
"文字内容 + 视口尺寸"的签名，**没变就不读**：F3 开着时每帧都变（本来就该重画），
关着时一次都不读（默认就是关的）。计分板几乎不变，等于零成本。

## 5.13 已落地（阶段 3：主菜单 / 世界列表的**整页镜像**）

`ui2d/menuScreen.ts` 的 `MenuScreen2D`：把一块**已经写好的静态 DOM 界面**原样画到 canvas ——
读每段文字（矩形 + 计算样式的颜色/字号/字重/对齐）与每块底色/边框（含圆角），按原位重画；
DOM 只把 `opacity` 设 0 让位像素。已接：主菜单 `home` 与世界列表 `worlds`（`?ui2d=1`）。

### 与前面几块的根本区别

| 块 | 几何从哪来 | 像素谁排 | DOM 的交互 |
| --- | --- | --- | --- |
| 快捷栏 / 血条 | 量 DOM | **自己画**（像素级复刻） | 留着（`opacity: 0` 或 `visibility`） |
| 设置页 / 暂停菜单 | 自己算 | **自己画控件** | 留着（动作靠 `button.click()` 转发） |
| **主菜单（本批）** | 量 DOM | **照原位重画，不排版** | 留着（完全不动） |

### 为什么这里选"镜像"

主菜单是**静态**的，而且以后还会长东西（迷你游戏、资源包、账号…）。把布局抄进 canvas
等于每加一个按钮写两遍，而抄错的表现只是"有点歪"，没有断言抓得到。镜像不需要知道界面上
有什么：加按钮、改文案、换语言全部自动跟上。

### 三条边界（别越线）

- **`opacity: 0` 让位，不用 `visibility` / `display`** —— 按钮必须继续可点（与快捷栏同一条，
  `TIPS.md` 有记）。**滚动、焦点、输入、下拉展开全留在 DOM**，镜像层一概不管。
- **带 `<input>` 的视图不镜像**（`create` / 多人面板）：`<input>` 的当前值不在 `textContent`
  里，镜像过去是空框，比不迁移更差。
- **两处已知近似**：渐变底退化成纯色（世界卡片的缩略图偏暗 —— D22）、
  四边不等宽的像素斜角只能画一种颜色（按钮凸起感弱一点）。

### 签名与刷新

菜单没有"打开/切视图/滚动"的事件，所以 `MenuScreen2D` 每 4 帧比一次签名
（视口尺寸 + 所有可滚动元素的 `scrollTop` + 整块 `textContent`），变了才重读计算样式；
`main.ts` 另用 200ms 轮询发现"菜单开了 / 关掉了"（`WorldScreen` 不暴露这些事件）。

## 5.14 已落地（阶段 3 的硬骨头：文本输入 / 输入法）

`ui2d/textInput.ts` 的 `CanvasTextInput`：**屏幕外放一个看不见但可聚焦的 `<input>`**
承接所有输入（含中文输入法），canvas 只画 `value` / 光标 / 选区 / 组合态下划线。

三条不能破的约束（都是"看起来能跑、真机不能用"的形状）：

| 约束 | 为什么 |
| --- | --- |
| 用 `opacity: 0`，**不能用 `display: none` / `visibility: hidden`** | 那样元素拿不到焦点，移动端也不会弹软键盘 |
| `pointer-events: none` | 它只是"收字的管子"，不能让它在屏幕上拦点击；聚焦靠调用方显式 `focus()` |
| 组合态靠 `compositionstart/update/end`，**不靠 `value`** | 拼音阶段的字母已经在 `value` 里了，但"哪一段还没上屏"只有事件知道；下划线要画在那一段下面 |

其它细节：`Enter` 提交 / `Esc` 取消时**先看 `event.isComposing`**（组合中这两个键归输入法，
抢了就变成"打拼音时按回车直接提交了半截"）；退格按**码点**切（`Array.from`），
否则删 emoji 会留下半个代理对；文字超宽时 `visibleSlice` 只在光标顶到右边界才滚动。

断言：`tests/ui2d-textinput.test.ts` **18 条**（光标位置与夹取、插入/替换/退格、码点退格、
可见窗口与滚动、选区与光标矩形、闪烁周期）。

⚠️ **还没接进游戏**：新建世界表单、聊天空格、多人面板都还是 DOM 输入框。这一层是它们的
前置件 —— 接线要按"点在某块矩形上 → `open()`，每帧 `render(ctx, rect)`，提交时写回设置/消息"来做，
属于下一批。真机输入法（尤其安卓各家 WebView 的候选栏位置）也只能在真机验。

### 顺手修掉一个"只在游戏里才炸"的 bug：覆盖层的 z-index

`Ui2DOverlay` 的默认 `zIndex` 是 `1`（跟着 `#app` 里的 WebGL 画布走，那个位置是对的）。
但镜像的宿主是 `document.body`，而被镜像的目标自己带高 z-index：

| 目标 | 它自己的 z-index | 覆盖层必须 ≥ |
| --- | --- | --- |
| `#world-screen`（主菜单） | 40 | 45 |
| `#chat`（聊天） | 8 | 12 |

上一批主菜单镜像用的是默认 1 —— **在预览页（`#stage` 是定位元素）看着完全正常，
在游戏里会被 `#world-screen` 的背景整个盖住**，表现就是"点了 `?ui2d=1` 主菜单直接没了"。
现在 `MenuScreenOptions.zIndex` 显式传，两个调用点各自写明理由。

> 这类"层叠上下文"问题离线断言查不到、预览页也照不出来，只有把它放到真实 DOM 里才会暴露。
> 记住判据：**镜像哪棵树，覆盖层就要排在它的层叠顺序之上**。

## 5.20 已落地（阶段 4 / M26 第一步：背包**整页镜像**）

背包 / 工作站这一版走**整页镜像**（与主菜单同一套 `MenuScreen2D`）：`.inv-panel` 设
`opacity: 0` 让位像素，canvas 把面板底、3px 斜面、每个槽位的底与斜面、**物品图标位图**、
数量、耐久条、标题按原位重画。交互（拖拽分配 / 长按分堆 / 连发 / 悬停提示）全部留在 DOM。

### 为什么先镜像，而不是直接自绘

背包有 **19 种工作站**（合成 2×2/3×3、熔炉、铁砧、附魔台、织布机…），自绘要先把这些布局
一个个搬过来；镜像**一次覆盖全部**，因为它不需要知道界面上有什么。自绘版
（`ui2d/InventoryPanel2D.ts` + `inventoryModel.ts`）继续在预览页里演进，等规则与视觉稳定再切换。

### 这一批新补的能力：把 DOM 里的 `<canvas>` 搬过去

镜像原来只搬"文字 + 底色/边框"。背包的**物品图标是位图**（`ui/ItemIcon.ts` 画进一张
`<canvas>`），不搬的话画出来是"有边框、有空位、没有图标"的背包。于是新增
`readCanvasBlits()` / `drawCanvasBlits()`，绘制顺序定为 **底 → 位图 → 文字**
（与 DOM 里"槽位底 → 图标 → 数量"一致）。

### 一个签名抓不到的坑：只换了图、没换字

`MenuScreen2D` 的签名只看"文字 / 输入框的值 / 滚动位置"。背包里**把一格石头和一格剑对调**时，
两边数量都不显示（都是 1），`textContent` 一模一样 → 签名不变 → canvas 一直显示旧图标。
所以加了 `pollMs`（背包用 120ms）：定期强制重读兜底。面板是模态的，这个开销可以接受。

### 边界

- 每个槽位的**悬停高亮**是 CSS `:hover`，镜像里看不到（`opacity: 0` 仍触发 hover，但我们不重画）；
  要用就得自己命中 + 画高亮，留给自绘版。
- **tooltip / 物品名浮标**仍走 DOM（全局委托），不受影响。
- `#inv-held`（拿在手上那一叠）在面板外面，用一条 `html.ui2d-inv #inv-held { opacity: 0 }` 藏掉。

## 5.3 调试遮罩：一块黄色告诉你"这块是谁画的"

`?ui2d=1&ui2dtint=1`（只在 `ui2d` 打开时生效）。屏幕上**每一块黄色的地方就是 canvas 画的**，
其余颜色来自 DOM / WebGL。预览页同理：`tools/preview/hotbar.html?tint=1`、
`tools/preview/hud.html?only=boss&tint=1`。

- 实现只有一句（`ui2d/debug.ts`）：所有绘制结束后把 `globalCompositeOperation` 切成
  `source-atop`，整块刷一层半透明黄 —— 合成器只染"**已经有像素的地方**"，
  于是不用维护"这一帧画了哪些矩形"，将来新增控件自动被覆盖。
- 为什么需要它：迁得对的时候**外观与 DOM 一模一样**，看的人根本分不出哪块换了
  （阶段 0 的教训，用户原话"改的这几个地方都不太明显"）。遮罩把"进度"从
  "肉眼比像素"变成"数黄块"。
- ⚠️ 三条边界：① 只是调试开关，**不进设置页**；② **不跟 `ui2d=1` 绑定** ——
  多一次全屏填充会让帧率 A/B 失真，颜色也不对，真机验收时容易被当成 bug；
  ③ 它是"整层"的，同屏多样东西时看不出哪块对应哪个控件（要点名得另加标签，本批不做）。
- 一个反直觉但正确的现象：**红闪打开时整屏都是黄的** —— 因为红闪本身就是全屏 canvas 填充，
  遮罩忠实地把整层都染了。

## 6. 判定不搬 / 搬法特殊（写清楚，免得下次重新踩）

| 东西 | 结论 | 原因 |
| --- | --- | --- |
| **准星** `#crosshair` | **不搬**（阶段 0 已排除） | 靠 `mix-blend-mode: difference` 与下层画面差值混合，属于 DOM 合成器能力；2D canvas 的 `difference` 只在本图层内合成，叠到 WebGL 上就是白十字，浅色场景反而看不见。真要搬：单独一张 canvas 并保留那条 CSS。 |
| **文本输入**（聊天/告示牌/铁砧/搜索/世界名） | **DOM 必须留** | canvas 无法唤起系统输入法（IME）。方案：**隐藏 `<input>/<textarea>` 收字 + canvas 显示**，自己处理 composing 下划线、光标、选区、粘贴。`ui/Keyboard.ts` 的 `--kb-inset`（键盘不挤压画面）要在 canvas 版重新对齐。 |
| 长按/拖拽/连发 | 搬（阶段 4） | 现在靠 DOM 元素级 pointer 事件 + 定时器；canvas 里要自己记"按下的是哪个区域、手指移出即取消"（`Ui2DInput` 已经按这个语义写）。 |
| **快捷栏的点击/长按**（阶段 1.5） | **画在 canvas、命中仍走 DOM**（过渡） | 覆盖层的 `pointer-events` 是**元素级**的：铺满全屏，打开就吃掉 `#touch-look` 的视角手势。区域级穿透要等阶段 6 重做手势层，这一批不值得冒险 —— 所以格子设 `opacity: 0`（**不是** `visibility: hidden`，那会连命中一起关掉）。 |
| 原生控件（`<select>`、滚动条、tooltip 的 title） | 搬（自己画） | 没有等价物；下拉要挂到最上层避免被裁切（DOM 版挂 `body` 也是这个原因）。 |
| 无障碍（`role` / `aria-label` / 键盘 Tab） | **会退化** | canvas 对读屏是一张图。缓解：保留一层不可见的镜像节点（`aria-hidden` 之外），或至少在开关打开时给出可访问的替代入口。这条要写进发布前的检查表。 |
| 全屏 / 剪贴板 / 文件下载 / 指针锁 | DOM API 不变 | 这些本来就不是"绘制"，`ui/Fullscreen.ts` 等模块继续用。 |

## 7. 迁移 checklist（每个面板都要过一遍）

1. **色值只抄不猜**：`widgets.ts` 的 `PALETTE` 与 `index.html` 的 `--mc-*` / `--hud-*`
   必须一一对应；改一处要同步另一处（迁移期两边并存，色漂是最难发现的一类回归）。
2. **文案必须走 `t()` / `tp()`**：canvas 没有 `textContent` 给 i18n 审计扫，
   所以 `audit:i18n` 看不到的漏翻会直接画到玩家脸上。新面板的文案一律先进 `locales/`。
3. **绘制单位是 CSS px**：不要自己乘 DPR（`overlay` 已经 `setTransform`）。
4. **`pointer-events` 默认关**：只有真有可点区域时才打开（`Ui2DInput.setRegions` 自动做），
   否则铺满全屏的层会吃掉触摸端的视角手势。
5. **手机横屏是第一场景**：所有断点先在 844×390 下看，再回去看 PC。
6. **关掉开关必须能完全回退**：每个面板迁移时保留 DOM 实现，直到该阶段真机验收通过再删。

## 8. 门禁与测试改写（这条最容易被低估）

- `tools/ui-test.ts` 约 **6,400 行**断言，其中很大一撮是**对源码文本与 CSS 做字符串匹配**
  （例如"设置行容器不再用 label"、"dropdown 必须挂 body"、`index.html` 里的某条样式）。
  面板一旦搬到 canvas，这些断言会**成片变红**，而且红的原因不是功能坏了。
- 处置顺序：**先加新的**（对 `Ui2DOverlay` 的绘制描述 / 布局纯函数做断言），
  **再删旧的**（DOM 实现删除的同一次提交里删掉对应断言）。不要先删后加 —— 中间那段空窗期
  等于没有回归保护。
- 阶段 0 已经示范了正确的粒度：把"排版决策"（折行/截断）与"几何换算"（Boss 条宽度、
  进度条位置）做成纯函数，断言打在这两处，而不是打"某一个像素长什么样"。

## 9. 现在的风险清单

1. **真机帧率未知**（最大风险）：DOM 合成层 vs 多一张全屏 canvas，谁更便宜要在真机上量。
2. **输入法**（阶段 3 的硬骨头）：隐藏 input 的光标/选区/composing 体验，安卓各家 WebView 差异大。
3. **背包交互**（阶段 4）：4 天能过、8 天也正常；它的交互全是点/拖/长按/连发的组合。
4. **门禁红灯期**：阶段 2~5 期间 `ui-test` 会持续有失败项，必须"边迁边绿"，不能攒到最后。
