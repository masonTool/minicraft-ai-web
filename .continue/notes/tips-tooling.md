# 工具链与框架操作的坑（从 TIPS.md 拆出）

> 拆出原因：`TIPS.md` 有 500 行预算（合并工作树后又加了 4 条到 531 行），而下面这些坑**不属于任何游戏模块**——
> 它们只在改 continue-do 框架、提交动作、文档门禁时才用得上，按模块 grep TIPS 的人不需要它们。
> 格式与收录门槛同 [`../TIPS.md`](../TIPS.md)：症状 → 根因 → 处置 → 适用面。
> 入口：`../TIPS.md` 的「工程与基础设施」节首有一行指针指回这里。

---

### 自己写文件再引用它：`git commit -F` 复用旧消息、提交守卫被自激改动刷红

- 症状：① 提交成功但 message 是上一次的（正文也对不上）；② 钩子递任务时把条目改成 `[~]`，之后每轮 Stop 的提交守卫都报"有未提交改动"，反复催人提交——那点改动是**钩子自己**刚写的。
- 根因：① `git commit -F .tmp/m.txt` 与 `cat > .tmp/m.txt` 是**两条命令**，前者被取消/失败时文件里还是上一次的内容；② `auto-commit` 用 `git status --porcelain` 判脏，而钩子每轮都会改 `.continue/doing/` 下的队列——"改动 = 有待提交的工作"对**自己写文件的自动化**不成立。
- 处置：写消息与提交放**同一条**命令里（或提交前 `head -3 .tmp/m.txt` 核对）；判脏前过滤掉自己会动的路径（`.continue/doing/`）。
- 适用面：任何"自动写文件 + 再用它 / 检查工作区"的组合（-F/-t 提交、格式化钩子、代码生成、日志落盘）。

## 工程与基础设施

### 队列文件逼近 60KB 时，先压"已完成条目"的说明

- 症状：提交守卫 `docs` 项报 `doing/<sid>.md 61KB > 上限 60KB`，而条目还没做完。
- 根因：每条完成说明都有"做了什么 / 为什么 / 验证"三行、越写越长；上限按**字节**算
  （`61KB` 里的 `KB` 是 1024 进制，所以红线是 61440 字节，不是 60000）。
- 处置：优先压**已完成**条目里重复的括号解释（保留结论与数字），**不要**删未完成条目的
  计划；压完留出几百字节余量——本轮压到 61353，下一轮再加内容就又会红。
  想长期解决：让 `[x]` 条目在收尾前就搬进 `DONE.md` 的草稿区（框架目前是收尾才搬）。

### 决策记录的「为什么」必须正好是 `- 为什么：`

- 症状：提交守卫的 `ids` 项报 `doing/<sid>-decision.md 的「D35」缺 - 为什么： 一行`，
  而文件里明明写了一行以它为开头的内容。
- 根因：`audit-ids` 对三行是**严格前缀匹配**（`- 决定：` / `- 为什么：` / `- 影响：`），
  写成 `- 为什么照抄而不是共享：` 或 `- 为什么只这四类：` 都不算——它按"缺一行"报，
  文案很容易被读成"你忘了写"，于是又去补一段，仍然红。
- 处置：**冒号前的字一个都不能多**。想解释得更细就写在冒号后面，或者另起一行普通列表。
  （本批连踩两次：D32、D35。）

### vitest 的磁盘缓存会被 IDE 的"安全删除"守卫拦住，整套测试启动即失败

- 症状：`npm run check:fast` / `npx vitest run` 直接抛
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":1002,"threshold":500,...}`，
  栈顶是 `FileSystemModuleCache.clearCache`，一行测试都没跑。`npm run typecheck` 正常，
  于是很容易误判成"vitest 坏了"。
- 根因：vitest 把编译缓存写在 `node_modules/.vitest-cache`（一千多个文件），每次启动
  会校验并**清空**过期缓存；而 IDE 注入的 `safe-delete` shim 对"一次删除 >500 个文件"
  要求人工确认 → 清理失败 → 启动失败。`rm -rf` 也会被同一个 shim 拦（`scope: "turn"`）。
- 处置：`vite.config.ts` 的 `test` 里加 **`cache: false`**（本项目测试 1 秒内跑完，缓存
  收益不值这个风险）。已经存在的缓存目录可以 `mv` 走（改名不触发删除守卫），
  之后不会重建。

### 往 `DONE.md` 插批次节，只能按行锚点切，不能用裸子串

- 症状：`DONE.md` 头部的说明行被写成 `> \`## 批次 ## 批次 20261023-0823 · …`，
  新批次整节被塞进了引用块里。于是 `^## 批次` 匹配不到它，`audit-ids` 报
  「批次索引有 X 但 DONE 没有」——**而这条当时只是 warning，于是通过（1 个提示，不阻塞）**，
  坏标题就这么留了一整天，直到下次核对才发现。
- 根因：收尾时用 `text.partition('## 批次 ')` 找插入点。裸子串的第一个命中在**文件头部那段说明**里
  （`> \`## 批次 <号> · 日期 · 会话 <前 8 位>\`` 这行），插入点因此落在引用行中间。
- 处置：① 切分一律用**行锚点**正则 `/^(?=## 批次 )/m`（`archive-done.mjs` 就是这么写的），
  或先按行找 `lines.findIndex(l => l.startsWith('## 批次 '))`；② 插完立刻跑
  `node .continue/hooks/audit-ids.mjs`，它现在会把这类半截收尾判红。
- 适用面：任何"往文档里按标题插入"的脚本；尤其是标题格式**本身写在文首说明里**的文档。

### 改机制的"半套改动"窗口里，钩子会 import 崩溃——而宿主把崩溃当"未阻止"

- 症状：改完 `lib.mjs`（删了一个导出）、还没来得及改 `auto-continue.mjs` 的 import 时，下一个 Stop
  就静默失效：任务不再下发、收尾指令也不发，**整个对话一声不吭**，队列状态纹丝不动。
  表现只是"它不动了"，看上去像"没待办"或"AI 不听话"。
- 根因：钩子 import 阶段 `SyntaxError` → node 以 **1** 退出；宿主只认 **2 = 阻止**，
  其它非 0 一律当"未阻止"**静默放行**。而 `test:hooks` 只在你主动跑检查时生效，
  崩溃窗口恰恰在"两次提交之间"。
- 处置：① 所有注册命令经 `.continue/hooks/run.mjs`，它把非 0/2 的退出翻成 exit 2 + 告警；
  ② 改钩子期间 `touch .continue/auto.off`，改完跑 `node .continue/hooks/check.mjs hooks` 再删。
- 适用面：任何"外部进程按退出码决定是否拦截"的钩子体系；也是"半套改动"这一类事故的通用形态。

### 改共享钩子时没挂刹车，别的会话会撞上"改了一半"的逻辑

- 症状：编辑 `.continue/hooks/*.mjs` 的途中，另一个会话的 Stop 钩子照常触发，跑到半截的代码可能
  语法错或逻辑半截——轻则那一轮报错，重则误判队列状态（"它把别人的队列当自己的收尾了"）。
- 根因：钩子是**每次事件单独 spawn 的进程**，读的是磁盘上的**当前**文件，没有"正在编辑"的概念；
  多会话共享同一棵树时，编辑窗口就是危险窗口。同理，两个会话同时改 `DONE.md` / `TASKS.md` 也会互相覆盖。
- 处置：动钩子前 `touch .continue/auto.off`，改完跑完检查再 `rm`。它同时挡住"改了一半的逻辑"与
  "并发会话抢同一份共享文档"。要真正并行（而不是轮流）就开工作树，见 `HANDOFF.md` §4。
- 适用面：任何多会话共享同一工作区的仓库；改 `config.json` / `.codebuddy/settings.json` 同理。

### 自检夹具比生产"短一行"，绿得毫无意义

- 症状：旧版计划机制上一批 43 项自检全过，但真实用的是"绑定写了等于没写"——队列头第 6 行的
  `> 计划：` 永远读不到（解析只看前 5 行），计划模式一次都没触发过。
- 根因：自检的 `planQueue()` 夹具少写一行 `> 创建：`，`> 计划：` 落在**第 5 行**；
  而 `queue-init` 注入的真实头部是 6 行。夹具比生产短，测的就不是那件事，
  而且它**不会自己报错**——只会让人更相信那套断言。
- 处置：夹具一律照抄生产模板（哪怕多一行没用的），并**显式断言关键行的位置**
  （窗口数字只在 `QUEUE_HEAD_LINES` 一处定义）；改头部模板时先问"夹具跟上了吗"。
  计划文件已移除（里程碑改写在队列里），但"夹具与生产同构"这条照样适用。
- 适用面：所有"构造输入再断言输出"的测试；尤其是文件格式、协议头部、配置层级这类
  **位置敏感**的结构。

### 门禁查两条上限、归档命令只守一条，超的那条永远修不掉

- 症状：`DONE.md` 315 行 / 49KB，`archive-done.mjs` 说"未超过上限"或只搬一个批次，
  而 `audit-docs` 判红「41KB > 上限 40KB」——两头打架，只能手工剪贴。
- 根因：`audit-docs` 同时查**行数 + 字节**（防"超长行绕过行数"），归档脚本只按行数算搬多少。
  完成说明写详细时，行数涨 52、字节涨 13KB，按行看永远"没超"。
- 处置：归档脚本改成**两条上限都守**（`over()` 同时判行数与字节，循环搬到两条都满足为止）。
  以后再加一条体量口径，记得在同一处判定函数里加，别让第二个脚本自己算一遍。
- 适用面：任何"门禁判 A、修复工具判 B"的组合（文档体量、包体积、缓存上限）。

### 钩子把 JSON 写 stdout 后立刻 `process.exit`，内容一长就被截断（零报错）

- 症状：`node .continue/hooks/check.mjs hooks` 红两条，报的是「首条应注入会话 ID」，
  可 stdout 里明明有 `"additionalContext":"【co…`；手工单跑同一个钩子却是好的。
- 根因：stdout 是**管道**时 `process.stdout.write()` 是异步的，紧跟的 `process.exit(0)`
  不等它冲完，超出管道缓冲的部分直接丢。注入文本从 3.5KB 涨到 5KB 后 JSON 从中间断掉，
  宿主侧 `JSON.parse` 抛错 → **静默丢掉整个注入**，表现只是"这个钩子没反应"。
  自检里 `ctx` 因此变成空串，报错指向"没注入"，与真实原因（没写完）差得很远。
- 处置：钩子写 stdout/stderr 一律用 `fs.writeSync(fd, text)`（`lib.mjs` 的 `writeFd`），
  不要用 `process.stdout.write` + `process.exit` 这套组合。自检断言里带上 `ctx.length`
  与 `r.out.slice(-160)`，一眼分清"没注入"和"JSON 坏了"。
- 适用面：任何"输出后立刻 exit"的钩子 / CLI；输出会随内容增长时（注入文本、报告、diff）必踩。

### HANDOFF 的"提交总数"是**自指**的：提交前要写成"当前数 + 1"，而且只有全量 `check` 抓得住

- 症状：一批做完跑 `npm run check`，`audit:tasks` 报「HANDOFF 的提交总数过期：写着 1702，实际 1715（差 13）」，
  前面 typecheck / 177 套离线测试全绿，白跑一遍。
- 根因：这一句要和 `git rev-list --count HEAD` 相等，而每个提交都会让计数 +1；`check:fast`（提交守卫）
  不含 `audit:tasks`，所以提交时永远拦不到，只有**全量** `npm run check` 会红。
- 处置：在**准备落地的那次提交里**把它写成"`git rev-list --count HEAD` + 1"（提交后正好相等）；
  一批多次提交时每次都要重算，别只在收尾改一次。没有脚本会自动写这个数字（`audit-tasks` 只读校验）。
- 适用面：一切"文档里的数字要与仓库状态自指相等"的锚点（提交总数、套件数、覆盖率）。

## `Number(x ?? fallback)` 会把"没给值"读成 0

- 症状：协议里"没带种子"被当成**种子 0**，于是两边生成的地形完全不一样，而且不报错。
  `Number(null)` 与 `Number('')` 都是 `0`，`0` 又是合法的整数种子——`Number.isInteger` 拦不住。
- 根因：`value ?? fallback` 再 `Number()` 只挡 `undefined`，挡不住 `null` / `''` 这类空值，
  而它们转换成**合法数字**。反向也成立：`Object.is(-0, 0)` 为真，别用 0 当哨兵。
- 处置：先判类型再收 —— `typeof v === 'number' && Number.isInteger(v)`；或统一用 `null` 表示"没有"。
  本项目 `src/net/RoomProbe.ts` 与 `src/net/NetClient.ts` 的 `welcome.world.seed` 都按这条改过，
  各配一条脏数据断言（`tests/room-probe.test.ts`）。
- 适用面：任何"缺字段 → 具体默认值"的协议收口；`0` / `false` / `''` 本身有意义时最容易中招。

## `tools/run-tests.mjs` 并发跑偶尔会红一套，单跑必绿

- 症状：`check:fast` / `check` 里偶发某套（`stray`、`mob` 各中过一次）报红，重跑或
  `node tools/run-tests.mjs --only <名字>` 单跑就全绿，代码一行没动。
- 根因：聚合器默认 `核数 - 1` 并发，几套重的（structure / guard / net / village）同时跑时
  单套会撞到自己的隐式超时或共享临时目录；套件本身没有资源隔离。
- 处置：先单跑确认，别急着改代码——真红会稳定复现。要复现得彻底就把 `--jobs` 调小。
  重复遇到时优先看那套是不是写了固定端口 / 固定 `.tmp` 文件名（本仓库已把 net 改成 `PORT=0`）。
- 适用面：任何"并发跑一套红、单跑绿"的报告，先当抖动查，再当 bug 查。

## 用脚本批量往六语言表里插文案，锚点只取"键名一半"会把行拆坏

- 症状：脚本跑完 `typecheck` 报一堆 `TS1005 ',' expected`，打开看是
  `'net.editNoHost'`（只有键名没有值）单独占一行，后面一行变成 `'net.roomClosed': '…',: '旧值',`。
- 根因：锚点写成了 `  'net.editNoHost'`（键名不带值），`replace` 把整行从中间切开，
  新内容插在"键名"和"`: 值`"之间。六种语言各坏一次，因为锚点是同一串。
- 处置：锚点一律取**整行**（含 `': ` 与值的开头）或改完立刻 `npm run typecheck`；
  真坏了就按行修：把裸键名行删掉、把下一行 `,: '…'` 的尾巴搬回 `键名: 值`。
- 适用面：任何"按行替换"的批量文本操作（i18n 表、TASKS/DONE 条目、CSS 变量表）。
