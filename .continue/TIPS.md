### `git commit -F <临时文件>`：命令被取消后，下次提交会**复用旧消息**

- 症状：提交成功，但 message 是上一次（另一个条目）的标题，正文也是旧的，和实际改动对不上。
- 根因：提交信息写在 `.tmp/m.txt` 里，`git commit -F .tmp/m.txt` 与 `cat > .tmp/m.txt` 是**两条命令**；
  前者被取消/失败时，文件里还是上一次的内容，下一次提交直接沿用它。
- 处置：把"写消息 + 提交"放**同一条**命令里；或提交前先 `head -3 .tmp/m.txt` 看一眼标题对不对。
- 适用面：任何"先写文件、再用 -F/-t 引用"的提交流程；临时文件跨命令复用时尤其容易踩。

### 钩子自己改工作区文件时，任何"脏检查"都必须把它排除，否则自激

- 症状：刚给钩子加了一条"递任务时把条目改成 `[~]`"，结果每轮 Stop 的提交守卫都报"有未提交改动"，
  反复催人提交——可那点改动是**钩子自己**刚写的，人根本没动过。
- 根因：`auto-commit` 用 `git status --porcelain` 判脏，而钩子每轮都会改 `.continue/doing/` 下的队列文件。
  "改动 = 有待提交的工作"这个前提，对**自己写文件的自动化**不成立。
- 处置：判脏前过滤掉自己会动的路径（这里是 `.continue/doing/`）；同理，凡是"检查工作区"的脚本，
  都要先想清楚"我/我的同伴是不是刚写过这些文件"。
- 适用面：任何"自动写文件 + 检查工作区"的组合（格式化钩子、代码生成、日志落盘）。

## 工程与基础设施

### 往 `DONE.md` 插批次节，只能按行锚点切，不能用裸子串

- 症状：`DONE.md` 头部的说明行被写成 `> \`## 批次 ## 批次 20261023-0823 · …`，
  新批次整节被塞进了引用块里。于是 `^## 批次` 匹配不到它，`audit-ids` 报
  「批次索引有 X 但 DONE 没有」——**而这条当时只是 warning，于是通过（1 个提示，不阻塞）**，
  坏标题就这么留了一整天，直到下次核对才发现。
- 根因：收尾时用 `text.partition('## 批次 ')` 找插入点。裸子串的第一个命中在**文件头部那段说明**里
  （`> \`## 批次 <号> · 日期 · 会话 <前 8 位>\`` 这行），插入点因此落在引用行中间。
- 处置：① 切分一律用**行锚点**正则 `/^(?=## 批次 )/m`（`archive-done.mjs` 就是这么写的），
  或先按行找 `lines.findIndex(l => l.startsWith('## 批次 '))`；② 插完立刻跑
  `node .continue/hooks/audit-ids.mjs`，它现在会把这类半截收尾判红。
- 适用面：任何"往文档里按标题插入"的脚本；尤其是标题格式**本身写在文首说明里**的文档。

### 改机制的"半套改动"窗口里，钩子会 import 崩溃——而宿主把崩溃当"未阻止"

- 症状：改完 `lib.mjs`（删了一个导出）、还没来得及改 `auto-continue.mjs` 的 import 时，下一个 Stop
  就静默失效：任务不再下发、收尾指令也不发，**整个对话一声不吭**，队列状态纹丝不动。
  表现只是"它不动了"，看上去像"没待办"或"AI 不听话"。
- 根因：钩子 import 阶段 `SyntaxError` → node 以 **1** 退出；宿主只认 **2 = 阻止**，
  其它非 0 一律当"未阻止"**静默放行**。而 `test:hooks` 只在你主动跑检查时生效，
  崩溃窗口恰恰在"两次提交之间"。
- 处置：① 所有注册命令经 `.continue/hooks/run.mjs`，它把非 0/2 的退出翻成 exit 2 + 告警；
  ② 改钩子期间 `touch .continue/auto.off`，改完跑 `node .continue/hooks/check.mjs hooks` 再删。
- 适用面：任何"外部进程按退出码决定是否拦截"的钩子体系；也是"半套改动"这一类事故的通用形态。

### 改共享钩子时没挂刹车，别的会话会撞上"改了一半"的逻辑

- 症状：编辑 `.continue/hooks/*.mjs` 的途中，另一个会话的 Stop 钩子照常触发，跑到半截的代码可能
  语法错或逻辑半截——轻则那一轮报错，重则误判队列状态（"它把别人的队列当自己的收尾了"）。
- 根因：钩子是**每次事件单独 spawn 的进程**，读的是磁盘上的**当前**文件，没有"正在编辑"的概念；
  多会话共享同一棵树时，编辑窗口就是危险窗口。同理，两个会话同时改 `DONE.md` / `TASKS.md` 也会互相覆盖。
- 处置：动钩子前 `touch .continue/auto.off`，改完跑完检查再 `rm`。它同时挡住"改了一半的逻辑"与
  "并发会话抢同一份共享文档"。要真正并行（而不是轮流）就开工作树，见 `HANDOFF.md` §4。
- 适用面：任何多会话共享同一工作区的仓库；改 `config.json` / `.codebuddy/settings.json` 同理。

### 自检夹具比生产"短一行"，绿得毫无意义

- 症状：旧版计划机制上一批 43 项自检全过，但真实用的是"绑定写了等于没写"——队列头第 6 行的
  `> 计划：` 永远读不到（解析只看前 5 行），计划模式一次都没触发过。
- 根因：自检的 `planQueue()` 夹具少写一行 `> 创建：`，`> 计划：` 落在**第 5 行**；
  而 `queue-init` 注入的真实头部是 6 行。夹具比生产短，测的就不是那件事，
  而且它**不会自己报错**——只会让人更相信那套断言。
- 处置：夹具一律照抄生产模板（哪怕多一行没用的），并**显式断言关键行的位置**
  （窗口数字只在 `QUEUE_HEAD_LINES` 一处定义）；改头部模板时先问"夹具跟上了吗"。
  计划文件已移除（里程碑改写在队列里），但"夹具与生产同构"这条照样适用。
- 适用面：所有"构造输入再断言输出"的测试；尤其是文件格式、协议头部、配置层级这类
  **位置敏感**的结构。

### 门禁查两条上限、归档命令只守一条，超的那条永远修不掉

- 症状：`DONE.md` 315 行 / 49KB，`archive-done.mjs` 说"未超过上限"或只搬一个批次，
  而 `audit-docs` 判红「41KB > 上限 40KB」——两头打架，只能手工剪贴。
- 根因：`audit-docs` 同时查**行数 + 字节**（防"超长行绕过行数"），归档脚本只按行数算搬多少。
  完成说明写详细时，行数涨 52、字节涨 13KB，按行看永远"没超"。
- 处置：归档脚本改成**两条上限都守**（`over()` 同时判行数与字节，循环搬到两条都满足为止）。
  以后再加一条体量口径，记得在同一处判定函数里加，别让第二个脚本自己算一遍。
- 适用面：任何"门禁判 A、修复工具判 B"的组合（文档体量、包体积、缓存上限）。

### 钩子把 JSON 写 stdout 后立刻 `process.exit`，内容一长就被截断（零报错）

- 症状：`node .continue/hooks/check.mjs hooks` 红两条，报的是「首条应注入会话 ID」，
  可 stdout 里明明有 `"additionalContext":"【co…`；手工单跑同一个钩子却是好的。
- 根因：stdout 是**管道**时 `process.stdout.write()` 是异步的，紧跟的 `process.exit(0)`
  不等它冲完，超出管道缓冲的部分直接丢。注入文本从 3.5KB 涨到 5KB 后 JSON 从中间断掉，
  宿主侧 `JSON.parse` 抛错 → **静默丢掉整个注入**，表现只是"这个钩子没反应"。
  自检里 `ctx` 因此变成空串，报错指向"没注入"，与真实原因（没写完）差得很远。
- 处置：钩子写 stdout/stderr 一律用 `fs.writeSync(fd, text)`（`lib.mjs` 的 `writeFd`），
  不要用 `process.stdout.write` + `process.exit` 这套组合。自检断言里带上 `ctx.length`
  与 `r.out.slice(-160)`，一眼分清"没注入"和"JSON 坏了"。
- 适用面：任何"输出后立刻 exit"的钩子 / CLI；输出会随内容增长时（注入文本、报告、diff）必踩。

### 队列条目写成 `[T1]` 会被门禁当成需求号，提交直接被拒

- 症状：新建队列用 `- [ ] [T1] …` 编号，`git commit` 被 continue-do 的 `ids` 检查拒掉：
  「引用了 T1…，但 TASKS.md 里没有这些需求」，整套 `--fast` 白跑 15 秒。
- 根因：`audit-ids.mjs` 用 `/\bT(\d+)\b/g` 扫**队列条目行**，把 `[T1]` 当成跨文件需求引用；
  而本项目的需求号是 `A1`~`O16`，`T<n>` 只是框架模板里的占位写法。
- 处置：队列条目用中文前缀（`[引导1]` / `[创造2]` / `[小游戏3]`）或任何非 `T+数字` 形式；
  已经写成 `[Tn]` 就改前缀重提，**不要**用 `--no-verify` 绕。
- 适用面：每次新建队列都会撞上，属机制性坑，不是一次性错误。

### 用 shell 双引号包多行文档改文件，反引号会被求值掉

- 症状：`node -e "..."` 里写带反引号的 Markdown，跑完提示一串 `command not found: NOTES.md`
  （zsh 还会说"没有那个文件"），而**文件已经被写坏了**——反引号里的内容被当成命令执行、替换成空串，
  几百字只剩骨架，退出码还是 0。
- 根因：双引号里 `$` / 反引号 / `\` 仍会被 shell 展开（命令替换先于 node 执行）；单引号能挡，
  但单引号包不住正文里的单引号。
- 处置：改文档一律走编辑工具；确实要脚本拼接就把正文先写成临时文件（`.tmp/xxx.md`），
  脚本里只 `readFileSync` 取来拼接——**全文交给工具，shell 只传路径**。已经写坏就
  `git checkout -- <file>` 回滚重来（比手改污染体快得多）。
- 适用面：本仓库文档大量含反引号（路径 / 命令 / 字段名），凡"把多行文本塞进 shell 参数"的场合都会中招。

### 重装 continue-do 会覆盖 `hooks/`，本项目改过的口径会被悄悄改回去

- 症状：重装框架之后**每次 `git commit` 都被拒**，报 `TASKS.md N 行 > 上限 600`；或队列目录又变成
  `queues/`、踩坑文档又说 `EXPERIENCE.md`。功能一行都没改，门禁却全红。
- 根因：安装器对 `.continue/hooks/*.mjs` 与 `.continue/.gitignore` 是**总是覆盖**（不覆盖等于升级失效）；
  `config.json` 只补缺失的键（所以 `checks.*` 会保留）；业务文档内容不同时只**另存** `*.continue-do.md`。
  所以"在 `lib.mjs` 里放宽 `DOC_LIMITS`"这类局部改动必然被抹掉，而且报错不会告诉你是本项目改过的。
- 处置：① 装完立刻跑 `npm run check`；② 本项目把放宽项记在 `tools/audit-docs.mjs` 的
  `PROJECT_DOC_LIMITS`（`TASKS=7000`），被改回去时它当场报出"应为 N"；③ 装完把 `*.continue-do.md`
  备份并进正本后**删掉**——两份指令并存时 AI 会读到冲突的两套规则；④ 钩子配置在会话启动时拍快照，
  改完要**重启会话**。
- 适用面：任何一次 `.codebuddy/skills/continue-task` 的重装 / 升级。

### 本仓库复制一份"框架行为断言"，迟早与框架脱节

- 症状：`npm test` 里 `test:hooks` 整片红，而钩子其实工作正常——断言在找旧文案（"三个收尾选项"、
  `NOTES`+`EXPERIENCE`、`queues/<sid>.md`）。
- 根因：`tools/hooks-test.mjs` 是照抄框架行为写的（581 行）；框架一升级，它守的契约就没了。
  这与"文案字面量断言"是同一类病：**守着别人的实现细节**。
- 处置：框架自己带 `selftest.mjs`（在临时副本里灌事件，覆盖递任务 / 注入 / 提交守卫 / pre-commit），
  本仓库只保留一行委派：`"test:hooks": "node .continue/hooks/check.mjs hooks"`。**键名留着**，
  这样 `run-tests.mjs` / `audit-tasks.mjs` 的 `NON_SUITE_KEYS` 名单不用动。
- 适用面：任何"给第三方框架写自测"的场景——要么委派给它的自检，要么只测**你自己那层**的胶水。

### 钩子日志会被清掉，所以"断点"不能只记在 logs/ 里

- 症状：问"这套自动续跑的机制为什么停了"时，`.continue/logs/<sid>.md` 只剩一行 `Init`，
  几小时前还读到的 20 多条 `Stop · 递任务` 全没了（目录里也没有 `.1`/`.2` 轮转文件，
  说明不是 512KB 轮转，而是文件被整个移除后重建）。于是"到底停在哪一条"没法自证。
- 根因：`logs/` 被 `.continue/.gitignore` 排除，只在**本机**；`appendLog` 只追加、从不清空，
  所以清空一定来自外部（清理脚本 / 手工 / 目录被删后重建）。这类运行时目录天生不可追溯。
- 处置：排查"为什么停了"时，**别把 logs/ 当唯一证据**——它能被删。可靠的做法是让证据跟队列一起进仓库：
  ① 看队列文件的 `[ ]`/`[~]` 状态（AI 每轮改、随任务提交）；
  ② 看 `git log` 里最后一个带 `批次 <号>` 的提交（做到哪一步一目了然）；
  ③ 需要更细的，再翻 `DONE.md` 的归档（整份队列原文照搬，含 `[阻塞]`）。
- 适用面：任何"只写在本机 gitignore 目录里的运行日志"——它是一个便利设施，不是审计日志。

### 用行数给文档设预算，会被"超长表格"绕过

- 症状：`TIPS.md` 499 行 / 190KB，行数门禁显示 499/500"快满但还能过"；按 token 算它是 `README.md` 的六倍，整份读会直接吃掉大半上下文。
- 根因：行数只度量"条目数"，不度量"单行长度"。一张 379 行的两列表，每行几百字，行数看着正常、字节已经爆炸。
- 处置：文档预算同时设"行数 + 字节"（`DOC_BYTE_LIMITS`）；大表格 / 历史清单整段迁 `notes/`，主文件只留指针；`audit-docs` 两条都查。
- 适用面：任何"用行数限制上下文成本"的门禁，尤其是 Markdown 表格、长列表、自动生成台账。

### IDE 终端里的删除会被 safe-delete 垫片"删一半"，并发跑同一套测试还会互相清场

- 症状 A：e2e 的 `milestone`/`journey`/`worktree` 报 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":500,"threshold":500,...,"targetCount":1}`——报错指向的只是删一个 `run.md`。
  症状 B：某个场景目录只剩几个文件、断言全红（`main` "钩子一次都没跑起来"），可脚本里没人删过它。
- 根因：IDE 终端用 `NODE_OPTIONS --require` 注入 safe-delete 垫片，`fs.rmSync` 和 `PATH` 里的 `rm` **都**被接管：
  按 `toolCallId` 累计删除条数（阈值 500），超了就**删到一半停下**并把文件挪进系统废纸篓（不是真删）。
  整个 e2e 跑在**一个 tool call** 里，"清上一轮"一次就能贡献 499 条；两轮 `--all` 并发时，后一轮的"先清场"直接删掉前一轮正在用的目录。
- 处置：脚本自己删东西一律用**绝对路径** `/bin/rm`（不过 shell 函数、不过 PATH 垫片）；删完校验"真的没了"，删不掉就停；
  跨轮次的资源（现场目录 / 锁）加 `.e2e/.lock`，且**锁要早于清场**。事故记录见 `DONE.md` 批次 20261023-1603。
- 适用面：任何在 IDE 终端里清目录的脚本（不只 e2e），尤其"删完就当成功"（不看退出码）的写法——半删的现场比不删更误导人。

### 扫源码找"这段文案有没有被用到"，别用成对引号切字面量

- 症状：`npm run audit:i18n` 报"73 条文案没被引用"，实际只有 4 条是真的。典型误报：
  `inventory.recipeBook` 明写在 `InventoryScreen.ts:1038`；`settings.opt.fps30/fps60` 由
  `t(\`settings.opt.fps${n}\`)` 拼出来；`settings.group.*` 由 `t(\`settings.group.${g}\`)` 拼出来。
- 根因：判据是"成对单引号之间算一个字符串"。一行里反引号模板与单引号混排时**配对会错位**，
  后面整段都被切乱；模板拼键更是完全看不到（键在运行时才诞生）。
- 处置：① 引用判据改**子串包含**（`code.includes(key)`），不解析引号；② 另收一遍
  `` t(`前缀${…}`) `` 的前缀，`key.startsWith(prefix)` 算引用，前缀短于 4 字符不收
  （`settings.` 会把整片键洗白）；③ 把前缀打进报告，过宽前缀一眼可见。修完 73 → 0。
- 适用面：任何"扫源码统计字符串使用"的脚本（覆盖率、死代码检测、文案去重）。

### 两个 `romanLevel` 同名不同口径：`StatusEffects` 吃 amplifier（0→I），`enchantments` 是 1 起始

- 症状：「力量药水 II」被印成「力量药水 I」、「缓慢药水 IV」印成「III」—— 差整整一级，而**不报错**。
- 原因：`itemNames.ts` 里用的是 `enchantments.romanLevel`（1 起始），药水的 `amplifier` 是 0 起始；
  `potions.ts` 用的是 `survival/StatusEffects.romanLevel`（直接吃 amplifier）。两处注释都警告过，
  但键化药水名时照样抄混了一次（批次 20261024-0020，靠"改造前后逐字 diff"才发现）。
- 判据：**跨模块搬数字前先看它旁边那个 `romanLevel` 是从哪个文件 import 的**；
  更省事的办法是照抄项目里已有的做法 —— `itemNames.ts` 里所有 `+ 1` 都是在补这个差。
- 兜底：这类"名字由数字拼出来"的改造，跑一次"改造前后全量逐字 diff"（105 瓶 + 35 支箭 diff 为 0 才算过）。

### 说明类文案存"字符串"还是"函数"：存字符串 = 只在加载那一刻的语言下正确

- 症状：把 `DESCRIPTIONS[key]` 里的中文挪进语言表之后，切到德语界面**说明仍然是中文**；
  而语言表 100% 覆盖、`audit:i18n` 也不报、`satisfies` 也过。
- 原因：`DESCRIPTIONS[key] = \`...\${t(...)}...\`` 是**模块加载时求值**的字符串 —— 记下来的是
  "那一刻的语言"（默认中文）。工具 / 盔甲 / 珊瑚 / 药水那几族一开始就写成 `() => tp(...)`，
  所以从没暴露；食物那 13 条（苹果、牛肉、腐肉、金苹果…）原来拼的是纯中文常量，
  "反正只有中文"看着没问题，一搬进表就露馅（批次 20261023-2217 实测）。
- 判据：凡是"由 `t()` / `tp()` 参与拼装、又要随语言变"的值，**必须存函数**，由渲染处调用
  （`itemDescription()` 已经是 `typeof value === 'function' ? value() : value`）。
- 自查一行：`grep -n "DESCRIPTIONS\[" src/core/registry/itemNames.ts`，看赋值右侧是不是 `() =>`；
  另有 `useState`-式的延迟表（`ADVANCEMENT_TEXT`、标签表）同理。
- 为什么容易漏：**静态表条目会遮住动态表**。同族 36 条里 23 条有 `item.desc.<id>` 静态条目、
  13 条没有 —— 只翻静态条目的那部分，问题看起来"已经没了"。

### 分批切语言表：切完必须"按组核对"，一个组整组等于英文 = 整组漏了

- 症状：法语表"键集 100% 齐、`satisfies` 过、`test:i18n` 全绿"，但界面上 226 条标签
  （效果 / 群系 / 附魔 / 职业 / 外观）全是英文。没有任何检查会报 —— 占位值本来就能通过一切"键集"检查。
- 根因：分批时按"界面层 / 背包 / 物品 / 命令 / 说明"切，**某一组掉在两批之间没人认领**。
  德语、俄语的 `label` 都在各自第二批，法语重写清单时切法变了，就漏了。
- 判据（一行）：按组统计 `table[key] === enTable[key]` 的条数，**某组 90% 以上相等就是整组漏翻**。
  已固化成 `test:i18n` 的"巡查 <lang>：没有整组仍是英文的组"。
- 适用面：任何"分批搬迁/翻译一张大表"的活；也别只信"覆盖率 100%"那一栏。

### 加语言 / 改文件名时，这些断言一定要跟着挪（否则红得莫名其妙）

- 三类会同时炸，且报错信息都指不到真正原因：
  1. **"没做表的语言"的例子**：`ru` → `pt` → …每加一种真实语言就往后挪一格；六种都有表之后
     只能造一个码（`'xx' as LocaleCode`），并断言**它不会漏进语言选择器**（清单只认 `LOCALES`）。
  2. **"支持 N 种语言"的计数**：`availableLanguages().length < LOCALES.length` 这类"还有语言不能选"
     的断言，在最后一种语言上表时必然红 —— 改成"六种都能选"。
  3. **源码里硬编码的文件名**：`boot()` 换 manifest 时按语言拼文件名了，断言却还在检查
     `'./manifest.en.webmanifest'` 这个字面量 → 改成检查 `manifest.${uiLang}.webmanifest` 的拼法。
- 适用面：语言清单、"可选/不可选"、静态资源按语言分支这三处。

### 多语言断言别写"译文必须不同于原文"——语言中性的条目会被误判

- 症状：`test:i18n` 报"这三条回执没翻成英文"，实际它们**本来就该一模一样**：
  `{name} Health = {value}`、`{key} set to {value}` 这类只由占位符与专有名词组成的句子。
- 根因：判据写成了 `t(key,'zh') !== t(key,'en')`。中文里没有汉字可翻的句子，
  英文值就是同一串；用"必须不同"当漏翻判据，等于假设每条文案都含可翻译的自然语言。
- 处置：判据改成**"中文里含汉字时，英文才必须不同"**——`/[\u4e00-\u9fff]/.test(t(key,'zh')) && t(key,'en') === t(key,'zh')`
  才算漏翻。同一处坑在 P0-6（判英文表完整性）和 P1-6（判回执是否翻译）各踩了一次。
- 适用面：任何"译文完整性/覆盖率"断言；P2 的物品名与生物名里会有更多语言中性条目（`TNT`、`Elytra`）。

### 把常量表搬进语言表时，`key in TABLE` / `TABLE.size` 这类"直接读表"的判断必须一起改

- 症状：文案明明一条没动（全量 diff 为零），但十几套测试一起红，报"没有中文名 / 没有说明"。
- 根因：判断"有没有这条文案"的地方不是走查表，而是直接读常量表：
  `hasDescription()` 的 `key in DESCRIPTIONS`、`knownNameCount()` 的 `NAMES.size`、
  `missingBlockNames()` 的 `NAMES.has(key)`。表搬走后这些判断全部变成 false，
  于是"文案还在、只是换了地方"被读成"文案没了"。
- 处置：抽一个 `hasXxx(key)` 判据，**两处都查**（语言表 + 还没搬走的旧表），
  判断统一走它。搬完最后一批再把旧表那半删掉。
- 适用面：任何"表正在被分批搬迁"的迁移（i18n 文案、注册表、标签表）。
  同一处坑在 P2-2（物品名）与 P2-3（物品说明）各踩一次，第二次仍漏了 `hasDescription` ——
  所以搬迁时**先 grep 一遍所有读表的地方**（`in TABLE`、`.size`、`.has(`），别等测试红。

### 加一种语言时，复数表最容易漏 —— 而且漏了不会报错

- 症状：德语界面上出现「1 Blöcke」（应为「1 Block」）。`tn()` 找不到该语言的复数表时会**回落到 `t(key)`**，
  于是一条写死的复数形式就这么印出来了，测试全绿。
- 根因：`PLURAL_TABLES` 里只登记了 `en`。德语的 one/other 恰好被英文的 `t()` 兜住，**一直没人发现**，
  直到俄语开始写复数表（4 类：one/few/many/other）才暴露。
- 处置：`locales/<code>/plural.ts` 与语言表**成对存在**，登记进 `PLURAL_TABLES`（静态导入 —— `tn()` 必须同步拿到它，
  而它只有几行）；断言盯**具体数字**而不是"有没有表"：
  `1 блок | 2 блока | 5 блоков | 21 блок`、`1 Block | 2 Blöcke`、`0 blocks | 1 block | 5 blocks`。
- 适用面：任何带数量词的文案（`{count} 格`、`可烧 N 次`、`还剩 N 次酿造`）。

### 模板拼名时，先问"这门语言的形容词要不要变格"——要变，就别用平坦模板

- 德语能拼：`Diamantspitzhacke`、`Weißwolle`（复合词永远不算错），所以 `{material}{kind}` 直接成立。
- 俄语不能拼：`алмазная кирка` / `алмазный топор` —— 形容词要随名词的性、数变。平坦模板必然错一半。
  同样的坑还有颜色 16 色 × 10 族（`Шерсть (Белый)`）。
- 处置：**能自然拼的走模板**（木材词干 `Дубов` + `ое/ые/ый`、珊瑚 `Трубчатый коралловый блок`），
  **拼不了的走"括号归属式"**（`Кирка (алмаз)` / `Плита (Камень)` / `Шерсть (Белый)`），语法正确 > 风格统一。
- 判据：如果一个"词"在目标语言里会因为后面的名词改变拼写，它就不是构件，而是句子的一部分。

## 界面与音频

### 测试断言按"字面量"匹配，文案一搬进表就会成片变红

- 症状：把界面文案接进 i18n（只换取值方式、不动行为）之后，`test:ui` 一次红了 7 条、`test:i18n` 红 3 条，
  断言原文形如 `src.includes("this.showMessage('绑定诅咒：这件装备取不下来');")`。
- 根因：这些断言当时想守的是"这条路径会给出提示"，但写法是**匹配那句中文**；
  文案搬走后源码里没有这句话了，断言必然失败——它失败的原因与"功能坏了"完全无关。
- 处置：这类断言一律改成**按文案键**匹配（`includes("t('inventory.bindingCurse')")`），
  迁移一次、之后随文案改动免疫。同一次改动里还要补一条**负向守卫**（源码字面量里不再有中文），
  否则"搬了一半"没人看得见。⚠️ 守卫自身的边界：它按**字符串字面量**判，
  所以行尾注释里的英文引号（`// 保持"按下"态`）也会被当成字面量——那种注释改用中文引号。
- 适用面：任何"文案进表 / 换模板引擎 / 改占位符命名"的重构，先 grep 一遍 `test:*` 里有没有匹配原文的断言。

### 挂在 `#hud` 里的可点元素，会被触摸端的全屏视角面吃掉点击

- 症状：按钮看得见、事件也绑上了，手指点下去毫无反应；反倒"点哪挖哪"，把身后的方块挖了一块
  （引导卡的收起键/「不再提示」、批次 95 的快捷栏都这样）。
- 根因：`#hud` 是 `pointer-events: none`，子元素靠 `pointer-events: auto` 单开；而触摸操作层
  `#touch-ui > #touch-look`（`position: absolute; inset: 0`）在 DOM 里**排在 `#hud-right` 之后**，
  两者都没有 `z-index` 时后出现的在上层，命中测试先落到视角面。
- 处置：可点元素要 `pointer-events: auto` **加** `z-index`（并加 `position: relative`，别依赖
  "flex 子项也适用 z-index"这一条细节）；新增 HUD 可点元素先问"它在 `#hud` 里还是 `<body>` 里"，
  前者一律抬层。
- 适用面：任何挂在 `#hud` / `#hud-right` 里的按钮、卡片、徽章。⚠️ 这个坑**只在触摸端暴露**
  （桌面端指针锁定期间 HUD 本来收不到事件），离线断言查不到——要兜就断言 CSS 里有 z-index。

### 「部分图标空白」多半是缓存毒化：图集没铺像素时画一次，就永久空

- 症状：某几件方块的图标在**所有**界面（快捷栏 / 创造栏 / 分类栏 / 建造工具条）都是空的，
  切分类、重开背包都不恢复；同一屏里其它方块与物品全正常。
- 根因：主菜单阶段的图集是 `deferPaint` 的空画布。`BlockIcon` 用图集拼等轴图标并把结果按
  `blockId` 缓存（只按 `atlas.revision` 失效），于是"在铺像素之前画过的那几个方块"缓存里是
  **全透明的 34×34**，之后没有任何路径会重画。2026-10-22 实测 9 件：沙 / 原木 / 树叶 / 木板 /
  圆石 / 玻璃 / 工作台 / 箱子 / 砖块 —— 正好是 `BuildToolbar` 的图标，而它在
  `atlas.ensureUploaded()` 之前构造。
- 处置：① 进世界先 `atlas.ensureUploaded()`，**排在任何 UI 构造之前**；② `blockIconCanvas`
  在 `!atlas.isPainted` 时返回 null（宁可空一次，也不写坏缓存）；③ 进世界 `clearBlockIconCache()`
  让旧会话的坏条目自愈（不必刷新页面）。
- 判据：先分清"画不出来"（图集空 / 缺贴图 → 全量都空）还是"没重画"（固定几件、重开无效）——
  后者一律查缓存与构造次序。离线只能断言"代码形状"（`test:textures` 的 4 条），
  视觉复验要在浏览器里量 canvas 的不透明像素数。
- 适用面：任何"按 id 缓存位图"的 UI（方块图标、成就图标、小游戏素材）＋任何"构造时就画图"的组件。

- **小游戏柱子的间距必须大于方块边长**：`gapMinStart 1.4` + `blockSizeStart 1.8` 时两根柱子互相重叠，整屏只剩一根——玩家看不到"要跳哪"，而逻辑与单测全绿（纯几何重叠，断言覆盖不到）。判据：`gapMin > blockSizeStart`，用截图或按分数扫一遍生成结果。
- **宿主在 stage 上 `setPointerCapture` 会把 click 也重定向到 stage**：结算面板的"再来一局 / 退出"因此点不动，而 `document.elementFromPoint` 明明命中按钮。修法是面板那层 `pointerdown / pointerup / pointermove` 全部 `stopPropagation`，宿主就不会拿捕获。这类问题纯逻辑测试永远发现不了，只能靠 Playwright 真点。
- **绝对定位元素别塞进同样 absolute 的 HUD 容器**：`.jump-hint` 挂进 `.jump-hud`（两者都是 absolute）后会相对 HUD 定位，跑到左上角与分数叠在一起；挂到 stage 上才是"底部居中"。

## 渲染与光照

### `meshBoxes` 与 `collisionBoxes` 是两套盒子，判据不能互相照抄

- 症状：门一开就"整扇消失"（还能听到开门声），玩家以为门被删了；上下半切换时只剩一半。
- 根因：`meshBoxes('door')` 直接抄了 `collisionBoxes('door')` 那句 `isDoorOpen ? [] : [doorBox(state)]`。
  碰撞侧"开着没有碰撞体积"是对的（原版能穿过门洞），渲染侧却成了"开着不画"；`doorBox` 里
  写好的开态几何（绕门轴转 90°）因此一行都执行不到。
- 处置：渲染盒永远返回 `[doorBox(state)]`，碰撞盒保持 `isDoorOpen ? [] : ...`；断言要同时盯两侧
  （"碰撞为空" **且** "渲染盒 1 个、薄边从 Z 转到 X"），只写一条的话再抄回去也没人发现。
- 适用面：所有"同一形状两种物理行为"的方块（门 vs 活板门 vs 睡莲的 `flat`/`lily_pad`）——
  加形状时两套盒子各写各的，**别复制粘贴另一侧**。

## 交互与方块操作

### 红石是"整体重算"，别让它按当前电平覆盖玩家的手动状态

- 症状：手动开关木门只响一声、门却"半扇"（上半透明、下半还挡着），再点也不恢复；
  活板门、栅栏门同样开不了。
- 根因：`RedstoneEngine.applyOpenableLoad` 每次 `recompute` 都把负载按**当前输入电平**重写一遍，
  而手动开合**不改变电平**；`main.ts#toggleDoor` 又是"先写下半、再写上半"的两次写入，各触发一次
  重算 → 下半被关回、上半留下来。再叠上"开着的门不画"，就成了"上半透明"。
- 处置：负载改成**电平沿触发**（记上次电平，只有变化才动门）；`onBlockChanged` 顺手删掉"已不是
  可开合方块"的记录；换维度清空（坐标只在维度内有意义）。判据：**状态只由输入决定**的（灯、活塞）
  才可以无脑重写；**玩家也能改状态**的（门类，以后还有别的）必须认"变化"。
- 适用面：任何"无状态重算 + 玩家可改状态"的组合（红石负载、告示牌、命令方块…）。
