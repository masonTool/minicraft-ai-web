# 决策记录 · 会话 974b55535f2b4ea3aa2e740f93a49c0b

> 批次：20261023-2351 · 创建：2026-10-24

## D1 · 房间模型

- 决定：一房一世界，房间码放在连接参数/URL 里；服务端按 room 分区，世界种子由房间决定。
- 为什么：游戏大厅可以推迟，但“房间”是协议层的概念——现在不预留，将来大厅只能在协议上打补丁。房间码还顺带解决了“两个朋友各自开服互不串味”。
- 影响：服务端从单例 `players/edits/items` 改成按 room 持有的结构；老客户端不带房间码时落到默认房间，行为不变。可撤回（房间默认单例）。

## D2 · 存档归属

- 决定：联机世界在本地按 roomId 派生独立存档库；服务端另存一份权威的 edits/容器/时间/天气。
- 为什么：现在 `setBlockAndUpdate` 会把收到的远端改动直接写进 `world.edits`，等于污染单机档（T5/T6 要修的就是这个）。两边各存一份是“客户端可离线、服务端可重启”的最小代价。
- 影响：`WorldRegistry` 多一类世界 id；断开联机要切回原单机世界。不可撤回的只有“已经在单机档里的历史远端改动”，不做迁移。

## D3 · 一致性模型

- 决定：继续“客户端模拟 + 服务端存真相 + 合理校验”，不做服务端权威 tick；实体先广播位置/血量/状态，AI 仍各端跑。
- 为什么：这是现有架构的直接延伸，也是好友联机最划算的取舍。改成权威 tick 要重写物理、AI、方块交互，收益只有防作弊，而本项目没有公共服需求。
- 影响：随机刻/红石/生物 AI 在长时间游玩后可能分叉，这条写进差异台账；`T12` 只统一“方块写入”这一条硬通道。可撤回（将来加权威 tick 是替换层，不是重写调用方）。

## D4 · 玩家身份

- 决定：昵称 + localStorage 的 clientId，无密码；房间可加可选密码。
- 为什么：好友场景不需要账号体系；clientId 只用于断线重连复用 id，不作鉴权用。
- 影响：昵称可伪造、可重名（重名只影响显示）；T26 的密码是房间级，不是账号级。

## D5 · 大厅推迟

- 决定：本轮只做房间码 + 最小连接入口（地址/昵称/连接/断开/状态），不做房间列表/匹配/邀请/准备/观战。
- 为什么：大厅是机制之上的薄壳；机制没对齐时做大厅只会把错误放大。最小入口是必需的——手机上目前没有任何联机入口（只有 `L` 键）。
- 影响：分享靠“地址 + 房间码”口头传递；联机9 的界面刻意不做列表，避免提前绑定大厅的交互。

## D6 · 重复 clientId 的处理

- 决定：同一个 clientId 已经在线时**拒绝新连接**（`error.code='duplicate'`，关闭码 4003），不做“新连接顶掉旧连接”。
- 为什么：现在没有鉴权，顶号等于“谁抄到 id 谁就能把别人踢下线”；而“重连复用 id”是联机8 的 grace 会话，前提是旧连接已经消失，两者不冲突。
- 影响：同一个浏览器开两个标签页会看到“这个 clientId 已经在线”，关掉一个再连即可。可撤回（改成顶号只需在 join 里把旧连接 close 掉）。

## D7 · 种子冲突的重载方式

- 决定：走“删库 + 回主菜单重开”，不做“原地逐项重置”（chunk/edits/实体/时间/位置）。
- 为什么：chunk 由种子重现、edits/容器/时间/玩家全在同一个 IndexedDB 库里，删库一次清干净；逐项重置必漏（这个仓库见过太多次“清了一半”）。而换种子必须新建 `World`（种子在构造时定死、Worker 也是那时起的），本来就不可能原地改字段。
- 影响：视觉上是“回主菜单再进来”，不是无缝重载；无缝需要 `resetWorld()`，已拆成联机34。

## D8 · 断开联机时怎么处理存档

- 决定：关掉联机库并把 `save` 置空（本局不再落盘），**不**切回单机库。
- 为什么：内存里的世界还是联机地形（区块/edits/容器都被队友改过），这时写单机档等于把联机世界存进单机档。宁可这一局不保存，也不能污染单机档。
- 影响：断线后提示“重进世界即回到单机存档”；真正无缝回切要等世界原地重载（联机34）。可撤回（改回切单机库只需一行）。

## D9 · 方块广播保留散点调用点还是只靠事件

- 决定：两条路都留——40 处散点 `queueBlockChange` 调用点保留，同时在 `World.events.onBlockChanged` 上再挂一条，靠漏斗“同格只留最后一稿”去重。
- 为什么：事件在写入**之后**触发、读的是最终值，理论上可以取代散点；但那 40 处里有“写入前发将要变成什么”的（骨粉/耕地那类），逐处核对语义的成本高于收益，删错一处就是静默不同步。双路的代价只是漏斗里多一次 Map.set。
- 影响：不会重复发包（同 key 覆盖）；如果将来发现某处调用点发的是错值，事件那条会把它纠正，行为更稳。

## D10 · 服务端快照里装什么

- 决定：只落盘服务端**已经有权威**的三样——方块增量、容器内容、时间；天气与掉落物不落盘。
- 为什么：天气还没有服务端权威（联机35 才做），存了也无从恢复；掉落物是短命对象（几分钟后自然消失），重启后还留着反而怪。容器必须连 `welcome` 下发一起做，否则"存了但没人看得到"等于废数据。
- 影响：重启后地形与箱子都在，地上那堆东西没了。可撤回（在 `worldSnapshot()` 里加字段即可）。

## D11 · 时间怎么跨重启

- 决定：把"存档那一刻的 timeOfDay"当作重启后的新起点（停机期间世界时间是停的）。
- 为什么：按真实时间补算会让"关一晚上再开"直接变成白天，与原版服务器关闭的行为不符；用起点重置实现最简单，不需要维护额外增量。
- 影响：只在服务端重启时体现；客户端那边照旧按联机10 收敛。可撤回。

## D12 · 快照裁剪的半径与裁剪范围

- 决定：`welcome` 只带**同维度 + 切比雪夫距离 ≤ 8 区块（128 格）**的方块改动；容器与掉落物仍全量下发。`MAX_EDITS` 满时淘汰最旧的一条并限频告警（每 100 条报一次）。
- 为什么：跑久了的房间能攒十几万条 edits，一次发给手机就是几 MB，而玩家真正看得见的只有几百格。半径取 8 区块（比默认视距还大一圈）是"覆盖可见范围"与"别发太多"的折中。容器/掉落物体积小（几十~几千条），裁剪它们的收益不大、而丢内容更难发现。告警限频是因为一炸就是几千行日志，反而看不出关键信息。
- 影响：半径外的旧改动新玩家收不到，走过去也不会补——这需要按视野补发（联机27），已记进台账。测试里"重启后方块还在"那条的坐标因此从 300 收到 60（否则被裁掉）。

## D13 · 容器同步覆盖哪些、同步什么

- 决定：只覆盖条目点名的 9 种共用储物（箱子/木桶/熔炉/高炉/烟熏炉/酿造台/发射器/投掷器/漏斗，其中木桶与潜影盒算在 `Chest` 里）；只同步**槽位内容**，不同步计时器（燃烧进度/酿造进度/冷却）。绑定时机从"打开界面"提前到"容器实例建出来"。
- 为什么：铁砧/织布机/讲台/制图台是"操作台"，内容不是玩家共用的储物，同步它们只会把消息量放大；计时器各端自己跑是现有架构（服务端不 tick）的直接结果，强行同步要新增消息类型与权威状态，超出本条范围。
- 影响：熔炉两边进度条可能差几秒（产物会通过内容同步补上，不会双份）；操作台里的摆放仍然各看各的。可撤回（`isSyncedContainer` 里加类型即可扩）。

## D14 · 牌子/展示框怎么同步

- 决定：新增两条独立消息 `sign`（4 行文字）与 `frame`（`item` + `rotation`），服务端留副本 + 随快照落盘 + `welcome` 下发；只同步**文字与物品**，不同步染料颜色/发光/多件拼贴。
- 为什么：与容器同构（内容按坐标存），但语义不同，塞进 `container` 会让"27 格槽位"这个形状对牌子毫无意义。只做实时转发不够——新玩家进来还是看不到队友写的牌子，所以必须留副本并下发；既然留了，顺手落盘（否则重启就没了，与联机13 的理由相同）。颜色/发光本项目存档里本来就没存，同步它们等于新增数据格式。
- 影响：牌子行截到 64 字符（客户端还会按 `SIGN_LINE_LENGTH` 再规整）、最多 4 行；转格子会多发一条（内容是同一件物品）。可撤回。

## D15 · 玩家外观同步到哪一步

- 决定：协议与数据链路做满 9 个字段（随 `move` 一起发、服务端白名单转发），渲染只接**手持物 / 挥手 / 着火**三项；潜行/骑乘/睡觉只存状态，副手与盔甲**不发**（没有数据源）。
- 为什么：远端玩家用的就是 `MobRenderer` 的方块人骨架，支持 `equipment`（手/盔甲槽）、`attackAnim`（摆臂）、`ignite`（着火），这三项接上去成本低、可见度高；而下蹲/骑乘姿势要改骨架，属于渲染层大改，应该单独一条（联机37）做并配套真机看效果。副手槽与玩家盔甲栏这个项目本就没有独立数据（盔甲只是 `armorColors` 简化模型），硬编 0 发过去等于告诉队友"我空着手"。
- 影响：队友能看到你手里的东西、挥手和着火；看不到你蹲下/骑马/睡觉，也看不到你的盔甲与副手。可撤回（渲染部分都在 `applyRemoteAppearance` 一个方法里）。

## D16 · 队友昵称牌：范围、衰减、池子

- 决定：归属队友昵称的字典半径是 **64 格**（生物 32 格），**32 格起线性渐隐到 64 格**；名字牌池从 12 加到 16；昵称直接写进 `Mob.customName`，复用已有的名字牌链路（含队伍颜色/前后缀）。
- 为什么：生物名字牌是"命名牌起名"的结果，原版不渐隐；队友昵称在 64 格外还很亮会让画面很挤，渐隐之后远处退成背景、近处才清晰。复用 `customName` 而不是新开一条通路，是因为名字牌渲染、宽度计算、队伍色、伪语言这些全都已经围绕它做好了——另起一套必然漂。池子加 4 个而不是改成"按需新建"：每张牌是一个 CanvasTexture，按需建会在人多时反复创建/销毁。
- 影响：视野里"有名字的生物 + 队友"超过 16 个时，最远的会被挤掉（原版无限）；`MobNameTag.show` 多一个可选参数，生物传 1 不受影响。可撤回。

## D17 · 联机19 为什么这一轮不做

- 决定：不动 19 的实现（状态保持钩子标的 `[~]`），插入前置条目 `联机38`；本轮转去做掉上轮插的 `[发现]`（net 套件偶发红）。
- 为什么：① 两端生物是**各自随机生成**的（`MobSpawner` 按群系随机挑种类与位置），"同一只生物"在两端对不上，没有可匹配的键；② 服务端不跑实体模拟、没有实体 id 空间（`items` 的 `owner:localId` 只适合"客户端自有对象"）；③ 硬做会让玩家看到**双份怪物**或看到别人的怪原地乱飘。这三条都是架构前置，不是实现细节。
- 影响：19 需要先在 `联机38` 里定"谁权威 / 全局 id / 影子抑制"，之后才有可落地的最小版本。这一轮的实际产出是 `net` 套件的时序加固（5 次连跑全绿）。

## D18 · 生物同步只做"命中"，不做位置

- 决定：实现 `mob-hit`（类型 + 坐标 + 伤害 + 着火），接收方按"同类型 + 3 格内最近"认自己世界里那只；**不同步生物位置**，也不做远端插值/降频。
- 为什么：两端生物各自随机生成（`MobSpawner` 按群系随机挑种类与位置），服务端没有实体 id 空间。同步位置会让两个独立 AI 互相拉扯（抖动/瞬移），按远端坐标再画一份又会出现双份怪物。而"伤害/着火"是**事件**，不需要两端状态一致，只要落到附近那只同类怪身上就有真实的联机感（队友帮你打怪，怪真的掉血）。
- 影响：队友打得动你身边的怪、能给怪点火，但看不到队友那边的怪在哪儿（各端视野里的怪本来就不一样）。位置同步需要"权威端 + 全局 id + 影子抑制"，留在联机38。

## D19 · 分级关注只作用于"位置"，不作用于状态

- 决定：`RemoteAoiGate` 只管远端玩家的**位置**目标更新（16 格 100ms / 32 格 250ms / 更远不更新）；昵称、外观（联机17）、维度、牌子的存在与否仍每条都更新。
- 为什么：位置是唯一"每秒几十次、且远处看不清"的量；而状态类字段一旦同门控，远处队友会冻住（名字不更新、外观卡在空手），用户会以为是 bug。另外这条只能在接收侧省成本——真正的带宽节流要服务端按距离决定发给谁（联机27）。
- 影响：32 格外的队友位置会停在上一次；走近后立刻恢复（远档不写时间戳）。可撤回（门控只在 `onNetPlayer` 一处）。

## D20 · 拾取仲裁：本地不预加，等回包

- 决定：客户端走近别人的镜像时发 `item-take`，**收到 `ok` 才加进背包**；服务端原子地"查还在 → 删 → 回 ok"，同时广播 `item-remove`。并发两个请求只有一条能删成功，另一条拿 `gone`。
- 为什么：本地先加再等服务端通知，两个人都会各拿一份（本地已经是既成事实）；而"客户端之间互相让"需要时钟同步，做不到。服务端删 Map 这一步天然原子（Node 单线程），是最省也最可靠的锁。
- 影响：捡别人的东西多一个 RTT 的延迟（局域网十几毫秒，可接受）；**自己的**掉落物仍走本地权威（自己捡、再发 `item-remove`），不走这条。可撤回。

## D21 · PvP 只在近战做，友伤两端各判一次

- 决定：近战可以打远端玩家（3 格内 + 视线前 25° 锥），伤害走 `player-hit`（服务端只转发给被击者）；友伤判定用新增的 `Teams.canHurt(attacker, victim)`，**攻击者本地判一次、被击者收到后再判一次**。箭/投掷物打人这一版不做。
- 为什么：远端玩家不在 `entities` 里，准星系统摸不到他们，用"距离 + 视锥"近似比改射线系统省得多；两端各判一次是因为队伍表**各端各存一份、不同步**（谁也不知道对方那边的规则），被击者那一侧才是"我会不会掉血"的最终依据。箭/投掷物要同步飞行体，那是联机23 的活。
- 影响：能近战互砍、同队默认免伤（`/team friendlyfire true` 才开）；死亡提示只会说"受到伤害"（`DamageCause` 没有 `pvp`）。可撤回（判定都在 `tryAttackRemotePlayer` / `onNetPlayerHit`）。

## D22 · 其余实体只同步"箭"与"TNT"

- 决定：箭与 TNT 用**事件 + 坐标/速度**同步（各端自己模拟）；经验球、船、矿车不做。
- 为什么：箭和 TNT 都是"一次动作产生、短命"的，坐标/速度就是够用的键；经验球与生物同属"各自生成、没有 id 空间"（联机38 的前置），载具还牵扯骑乘归属与摆放冲突。不做的那三类写进协议文档与差异台账，不是漏掉。
- 影响：队友射的箭、点的 TNT 都看得到（箭的落点会差几厘米）；经验球/船/矿车仍各看各的。可撤回（挂钩都在 `spawnArrow` 与 `PrimedTnt.onPrime`）。

## D23 · 方块校验的范围：上界而不是精确白名单

- 决定：`MAX_BLOCK_ID = 2000`（上界）+ `state ≤ 255` + `y ∈ [-64, 320)` + 水平距玩家 ≤ 64 格；容器也卡 y 与距离，但不校验"那一格是不是容器"。
- 为什么：精确白名单要把客户端注册表同步到服务端（生成文件或接口），而注册表每个版本都在长；而上界只需要一条测试守住漂移——`tests/net-block-validation.test.ts` 断言真实注册表最大 id < 2000，长过它时测试变红、逼着调上界，而不是悄悄拒收合法方块。距离上限 64 格（比视距 128 小）能挡住"隔空改主城"，但玩家坐标本身也是客户端报的（`move` 没校验），所以它挡的是"完全不相关坐标"，不是精心伪造。
- 影响：**现有测试里所有"隔空改方块"的坐标都得改到 64 格内**（快照裁剪那条要改成"先走过去再写"，否则它测到的会变成"拒收"而不是"裁剪"）。正常玩法无感。可撤回（常量在 `server/protocol.mjs`）。

## D24 · 限频只迁三类到令牌桶，其余保持原样

- 决定：新增 `server/ratelimit.mjs`（通用令牌桶），只给 `block` / `container` / `chat` 接上；掉落物、生物命中、拾取、箭与 TNT 继续用各自手写的"1 秒窗口 + 计数"。`maxPayload` 设 64KB。
- 为什么：那四条链路已经各有测试覆盖并通过（限频行为已验证），迁到桶上等于同时改四个已验证的行为——收益只是"代码更整齐"，风险是四个地方都可能错。`maxPayload` 取 64KB 是因为最大的合法消息（`blocks` 一批 256 条约 8KB、容器 8KB 上限）远小于它，而 `ws` 默认 100MB 意味着一条手工消息就能让服务端先分配 100MB。
- 影响：方块限频按**条数**计费（红石连锁一次几十格正常，持续每帧几百格才被限）；聊天每秒 5 条。异常刷屏现在会被静默丢弃（不回错误，免得被刷屏者利用）。可撤回（常量在 `ratelimit.mjs`）。

## D25 · 房间用 key 前缀隔离，不用"每房一套 Map"

- 决定：房间名做数据表 key 的前缀（`房名|dimension|x,y,z`），`broadcast` 强制带房名；客户端从地址解析房间（`ws://host:8787/red?pw=1234`），口令明文走 `join`。种子仍全服一个。
- 为什么：用前缀只需改 key 的拼法，而"每房一套 Map"要把四张表搬进 Room 对象、改几十处引用——改错一处的表现是"某功能跨房串台"，比 key 拼错难查得多。地址里带房间而不是界面加输入框：联机9 的面板只有两行（横屏塞不下），而发给队友的本来就是一整条地址，复制粘贴最省事。种子不分房是刻意的：分了要改地形，等于让已有房间的存档对不上。
- 影响：两个房的数据（方块/容器/牌子/展示框/掉落物/玩家）完全隔离，跨房拾取被挡；地形相同。`broadcast` 的房名参数**没有默认值**——给了默认值，漏传的地方会静默变成"发给所有人"。快照落盘数组末位加 `room`，旧格式读档归默认房（可撤回）。

## D26 · 广播范围只管坐标类消息

- 决定：`broadcast` 多收一个 `{x, z, dimension}`，方块/容器/牌子/展示框/TNT/掉落物/生物命中/箭按"8 区块 + 同维度"过滤；`player`/`chat`/`time` 不过滤。范围用**切比雪夫**（方形），与 `welcome` 的裁剪半径、渲染的区块加载范围同一个口径。
- 为什么：`player` 位置一旦过滤，远处队友会直接从世界里消失（模型与名字牌都没了），而它本来就被 `move` 的 100ms 限频压着；聊天是文字、时间是全局时钟，过滤它们只会造成"远处的队友听不到你说话"这类怪现象。用方形而不是圆形：渲染的区块本来就是方形的，圆形会在对角线方向少发一圈。
- 影响：远处（>128 格）的人不再收到方块/容器/掉落物等更新，省掉 O(n²) 的无效流量；走近后第一帧就能收到后续更新（判据是实时位置，不缓存）。可撤回（`broadcast` 的第 4 参默认 null = 旧行为）。

## D27 · 部署形态与默认地址

- 决定：`ws` 移进生产依赖；服务端用 http server + `WebSocketServer({ server })`，同一端口提供 `/healthz`；客户端默认地址按页面协议分流（https → `wss://<同源>/ws`，http → `ws://<hostname>:8787`，`?server=` 覆盖）；新增 Dockerfile（只装生产依赖）+ `notes/multiplayer-ops.md`。
- 为什么：https 页面连 `ws://` 会被浏览器当混合内容拦掉，而同源反代是唯一不需要额外开端口、也不需要客户端改代码的做法；镜像只装 `ws`（服务端唯一运行时依赖，`three`/vite/测试工具都是打包期的东西）；健康检查与 WebSocket 同端口（容器/反代只暴露一个口）。**没有内置 TLS**：证书交给反代，服务端不碰。
- 影响：以前 `defaultServerUrl()` 在 Pages 上必然连不上（README 里写着"联机不可用"），现在挂一条 `/ws` 反代就能用；`?server=` 覆盖让子路径部署也能连。可撤回。

## D28 · 关掉 vitest 磁盘缓存

- 决定：`vite.config.ts` 的 `test.cache = false`。
- 为什么：vitest 的缓存目录有一千多个文件，IDE 注入的 safe-delete shim 对"一次删 >500 文件"要人工确认，导致**整套测试启动即失败**（本轮亲历：`check:fast` 直接抛 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，`typecheck` 却是绿的，很容易误判成 vitest 本身坏了）。本项目测试 1 秒内跑完，缓存收益不值这个风险。
- 影响：重复运行的启动慢一点点（可忽略）；不再依赖机器环境的删除策略。已记进 `TIPS.md`（工程与基础设施）。

## D29 · "TPS" 用消息速率代替，丢包用应用层 ping 估

- 决定：服务端统计**入/出字节与消息速率**（每 10 秒一行日志 + `/healthz` 的 `traffic`），不做真正的 TPS；客户端延迟/丢包用**应用层 ping/pong**（每 2 秒一条、3 秒没回算丢），F3 面板显示。速率用**每秒一个桶的 5 秒窗口**，不是累计平均。
- 为什么：服务端不跑 tick（世界由各客户端模拟），没有"每秒多少 tick"可报，硬造一个数字只会误导；消息速率与吞吐才是这条链路真正的负载。累计平均在断线重连后永远是历史值，看不出"现在很卡"。丢包只能在应用层估：WebSocket API 不暴露重传/丢包，协议层 ping 帧浏览器也不让发。
- 影响：F3 面板多一行（没上线时不占行）；服务端空房间不打日志。可撤回（统计类不参与游戏逻辑）。

## D30 · 聊天：客户端本地回显 + 服务端不回传

- 决定：服务端 `chat` 只发给**同房间的其他人**（`broadcast(..., player.id, ...)`），发送者的显示靠客户端自己的本地回显。
- 为什么：另一种做法是"服务端回传、客户端不回显"（消息只有一处真相），但那样自己发的字要等一个 RTT 才出现在屏幕上（局域网十几毫秒、跨网络就明显了），手感远不如"按下回车立刻显示"。代价是"服务端因限频丢了这条，发送者仍看到自己发的"——在被限频（每秒 5 条）的情况下这本就是刷屏行为，可接受。与方块/容器"广播给其他人"也是同一个口径，统一后不必记两套规则。
- 影响：自己发的消息只出现一次；发送者看不到服务端的时间戳/改名（现在也没有）。可撤回（改回 `null` 即可）。

## D31 · 掉落物的维度跟着消息走，不跟接收者

- 决定：`item-spawn` 与 `NetItemState` 都带 `dimension`（服务端用**发送者上报的维度**记下来），`welcome.items` 只带"同房 + 同维度"的，客户端收到维度不匹配的镜像直接跳过。
- 为什么：坐标在两个维度里是同一套数，所以"下界掉的东西"会被画在主世界同一个位置——这不是渲染 bug，是数据里根本没有维度。也可以"按接收者当前维度推断"，但那等于替消息编造事实（发送者可能正好在换维度）。`item-remove` 不加维度：`owner:localId` 已经全局唯一，加了也是冗余。
- 影响：下界的掉落物只在下界可见；跨维度时不再出现"幽灵堆"。可撤回（多一个字段，老客户端不带时回落 `overworld`）。

## D32 · 补建容器只扫增量表，且只扫"自己会动"的四类

- 决定：区块加载后从 `ChunkEdits.serialize()` 里挑出容器方块补建实体，只在联机状态做；范围限漏斗 / 投掷器 / 发射器 / 潜影盒。
- 为什么：从增量表挑是因为一个区块 384×256 格、扫整块找漏斗是几万次读，而增量只有被改过的几十格；只做四类是因为箱子/熔炉的内容只有玩家打开界面时才有意义（`containerOfBlockAt` 懒创建，提前建反而白占内存）；只联机做是因为单机的漏斗在放下那一刻就建好了。
- 影响：队友经增量补上的漏斗现在会搬东西了；箱子的内容仍要等打开（但打开时会懒创建，行为不变）。可撤回（一个调用点）。

## D33 · 世界原地重载只做清单，不做执行路径

- 决定：本轮只产出 `src/game/worldReset.ts`（25 项清单 + 漏项检测）与其单测，**不接 `resetWorld()` 执行路径**，并插 `联机39` 作为前置（让 `world` 与渲染器可换）。
- 为什么：`main.ts` 的 `world` 是 `private readonly`，`ChunkRenderer` 又把 `world` 作为 `private readonly` 参数绑定——换世界必须重建渲染器（连带 GPU 缓冲与 worker 池）。这条路径**只能在浏览器里验证**，而一旦清漏一项，伤的是玩家存档所在的世界（属于退不回去的那一类）。现有替代路径（联机5 的删库重开、联机6 的断开停写）已经保证了数据正确性，本条只是省掉一次"回菜单再进"，不值得用半成品去冒险。
- 影响：本条**未完成**（保持 `[~]` 等用户定夺）；新增 `联机39` 前置。清单本身不参与运行时，零风险。

## D34 · 原地重载用 `World.reset()`，不换实例

- 决定：给 `World` 加 `reset()`（清 chunks/wanted/loading/pending/edits/containers/light，**保留 worker 池与 seed**），渲染侧用已有的 `ChunkRenderer.disposeAll()`；`main.ts` 新增 `reloadWorld()` 按 `WORLD_RESET_TARGETS` 清单逐项清并自检，接在 `leaveMultiplayerSave()` 上（切回单机库 → 重载，失败则 `exitToMenu`）。
- 为什么：原计划（联机39）是"去掉 `readonly world` + 让渲染器可换"，但真正需要的只是"世界内容可清空"。换实例要重建渲染器（连带 GPU 缓冲与 worker 池），风险与工作量都高得多，而 `reset()` 达到同样效果。在途的生成请求也不用取消：清空 `wanted` 后回包会在 `onGenerated` 的 `wanted.has` 处被丢掉。
- 影响：断开联机后不再"本局不落盘"，而是真正回到单机世界（这是联机6 承诺过的那一半）；`/netseed reload` 仍走回菜单重开。失败有兜底（回主菜单），不会把联机地形留在内存里。可撤回（`reset()` 不影响任何离线逻辑）。

## D35 · 天气规则在服务端照抄一份，用一致性测试兜住

- 决定：`server/weather.mjs` 照抄客户端 `WeatherState.ts` 的规则；客户端 `Weather.setAuthority(false)` 时只渲染、不推进状态机；服务端每 2 秒推进一次并在**种类变化时**广播。各房间共享同一个天气。
- 为什么：服务端是纯 `.mjs`（不进打包），客户端是 TS（过类型检查/i18n），没有共同运行时，所以规则只能照抄一份；代价是"改规则要改两处"，所以配了 `tests/net-weather.test.ts`——同一串随机数下逐条比对两端结果，改漏一处立刻变红（本轮它当场抓到我把 `STORM_SECONDS_*` 写成 180~420、实际是 120~300）。为什么不每房一套天气：天气是"这个世界的天"，房间只是分区，各房天气不同会让人困惑，而且每次切换要按房广播（已经这么发了，成本一样）。
- 影响：联机时两人一定同天气；断线后回本地掷骰子。切换广播没有 e2e 覆盖（要等 8~16 分钟真实时间），靠一致性测试兜底。

## D36 · 远端姿势只做下蹲/骑乘，20/21 拆单等用户拍

- 决定：只做 `联机37` 的 ①（下蹲/骑乘姿势，纯渲染层 + 一个纯函数），②盔甲逐槽、③副手槽拆成 `联机40` / `联机41`；睡觉姿势也不做。
- 为什么：②③ 都要改存档格式（现在是 `armorColors` 简化模型、没有副手槽），旧存档要迁移，属于"退不回去"的那一类，按规矩必须用户拍板；①恰好**不用改协议**——`sneak`/`ride` 从联机17 起就在 `move` 里传，缺的只是渲染没人用。睡觉要三轴旋转 + 贴地 + 床朝向，比下蹲大，而收益低。
- 影响：队友蹲下/骑乘现在看得见了；盔甲与副手仍是简化表现（不影响数据正确性）。可撤回（`MobPose.ts` + `MobRenderer` 三行）。
