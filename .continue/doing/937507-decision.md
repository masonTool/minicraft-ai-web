# 决策记录 · 会话 937507d0458d4277ba340bcb48207050

## D1 · 方块表二进制的字段布局：定长 14 字节/块 + 共享字符串表

- 决定：头部 16 字节（魔数 / 版本 / 保留 / blockCount / stringCount / crc32），随后是一张**全局去重字符串表**，再是每块定长 14 字节（nameIdx、3 个贴图下标、flags、light+lightOpacity 合成 1 字节、shapeIdx）。
- 为什么：724 个方块实测 41107 字节 / gzip 11048 字节，且方块区严格定长——解码不需要任何分支，越界检查只看一次总长度。字符串表必须**全局共享**（1431 段 30.2 KB）；按块内联名字+贴图会到几百 KB，既涨体积又把"复制者要的数据"原样留在网上。选定长而不是 varint：解码简单到不会写错，体积差不到 2 KB，不值得为省这点字节引入变长解析（这类解析最容易出"读偏一个字节，后面全错"的静默 bug）。
- 影响：格式一旦发出去，加字段就必须升 `BLOCK_TABLE_VERSION` 并走「请更新应用」；不能靠猜兼容旧文件。收益是体积与可预测性，代价是格式演进要显式做版本。

## D2 · `shape` 存字符串表下标，不存"形状序号表"

- 决定：`BlockShape` 用字符串表索引编码，不在编解码器里维护一份 `SHAPE_ORDER` 数组。
- 为什么：维护序号表意味着「新增一个形状忘了往表里加 → 生成脚本抛错」，而这份表本身没有信息量（45 种形状的名字本来就要进字符串表，进一次 ≈ 315 字节）。用字符串下标后新增形状**不需要改编解码器**，只有真正的格式变更才需要动版本号。
- 影响：解码出的 `shape` 是 `string as BlockShape`，理论上篡改文件可以塞进不存在的形状名；靠 CRC32 挡"意外损坏"，靠后续的签名挡"故意篡改"。字段级白名单被放弃了，这是有意的取舍。

## D3 · 加 crc32（头部 12 → 16 字节）

- 决定：头部加 4 字节 CRC32，覆盖头部之后的全部载荷；不一致直接抛。
- 为什么：写测试时发现了真问题——`copy.fill(0, half)` 这种"长度不变、内容被补零"的损坏**能照样解码**，解出来是"贴图空、形状错"的垃圾表：游戏不崩，静默变成一片空白方块。这类失败比启动报错贵得多（用户看到的是"世界坏了"，你拿到的是没有堆栈的差评）。4 字节换"宁可启动失败"。
- 影响：多 4 字节；生成与解码各多一次全量扫描（41 KB，微秒级）。CRC 只防意外损坏，**不防篡改**（谁都能重算），防篡改是 P1 的签名，别把这两件事混起来。

## D4 · id 不写进二进制

- 决定：第 N 条记录就是 id=N，文件里不存 id。
- 为什么：`buildBlockTable()` 已经强制"id 从 0 连续，有空缺就抛"，所以 id 是冗余信息；存了反而给了"文件里 id 与下标不一致"这种自相矛盾的状态。编码时仍会校验 `block.id === 下标`，一旦不成立立刻抛。
- 影响：解码器无法表达"id 稀疏"的方块表；将来若真要留空洞，必须升版本并重新引入 id 字段。

## D5 · 只搬 `blocks.ts`，不动 `items` / `recipes`

- 决定：本批只把方块表搬出去；物品表（1871 行）、配方表（200+ 条）留在 bundle 里，等实测收益再决定。
- 为什么：方块表是"核心且恒定"里最典型的一份（724 条、五千多行、字段结构稳定），也是复制者最想要的地基；而配方表会随版本频繁调整，搬进 APK 就等于"改配方要发 Play 版"，与更新性直接冲突。先做一个拿到真实数字（体积降多少、加载慢多少），再决定要不要扩大范围。
- 影响：主包里仍存在物品/配方明文；如果实测收益明显，后续按同一套格式再搬一次，解码器可以复用。

## D6 · 宿主2 与宿主3 分两刀：先做注入 seam，再搬闭包

- 决定：本批（宿主2）只把 `BLOCKS` 变成可注入的表，并固化 46 个带行为方块的行为快照；把"46 个闭包搬进 `BLOCK_BEHAVIORS`"与"从 `core.bin` 装载"一起留到宿主3。
- 为什么：这两件事的失败模式完全不同——搬闭包错了是**静默渲染错**（正脸贴反、亮灯不发光），装载错了是**白屏/空表**。一次做两件，出问题时无法判断是哪一半；分开做，宿主2 用 encode→decode→install→查询 证明"缝"成立，宿主3 有快照逐块指名。另外 46 个闭包分布在十几个 `*_SPECS` 工厂里（含 16 色旗帜这种按色循环的家族），实测比预想的大，硬塞进一批会把风险集中到一次提交里。
- 影响：`blocks.ts` 里 `SPECS` 暂时仍在 bundle 内（宿主3 才搬走），所以本批**没有体积收益**；`BLOCKS` 从 `const` 变 `let`，任何"模块顶层读 `BLOCKS[...]`"的写法都会在装表前拿到空表——已核对现存 0 处，并写进注释约束后续新增模块。

## D7 · `installBlockTable` 允许重复调用，且失败必须保持旧表

- 决定：不做"只能装一次"的限制；空表 / id 不连续 / 无名项一律抛，且**抛之前不改 `BLOCKS`**。
- 为什么：测试要还原表、将来热重载也要重装，锁死一次会让这两条路都别扭。反过来，"装失败却把表换掉了"是最坏的形态：世界还在跑，但每个方块都成了空气——宁可整体失败。校验成本 724 次下标比对，可以忽略。
- 影响：调用方拿到异常时必须视为"装表失败"，按宿主3 的约定走落地页/重试，而不是继续启动。

## D8 · 本批让 SPECS 继续留在 bundle 里（体积收益推到宿主4）

- 决定：宿主3 只做"行为搬走 + 从二进制装载 + 门禁"，**不动 `blocks.ts` 里 SPECS 的位置**，所以主包体积这一批不降。
- 为什么：`SPECS` 与 50 多个 `*_ID` 常量交错写在 `blocks.ts` 里（`WOOL_ID_START` / `WOOD_BLOCK_ID_START` / `SLAB_ID_START` … 全在这一段导出），224 个文件从 `blocks.ts` 引用它们。要把 SPECS 挪进独立模块，等于同时搬运这批导出并加一层再导出，动一次就得全量回归；而宿主4 的核心验收是"主包 gzip 显著低于 338456 + dist 里不得出现 core.bin"，那正好是这步的判据。分开做，每一步都有独立可测的结论。
- 影响：**门禁已成立、体积未降**。这几个批次的中间状态是"浏览器拿不到核心数据（玩不了），但 JS 里仍能看到方块数据"——安全目标要等宿主4 才真正落地。这一点必须让用户知道，不能当成"已经加密好了"。

## D9 · 门禁用"魔数"判定，不用 HTTP 状态码

- 决定：`boot.ts` 拿到响应后先验 `MCTB` 头 4 字节；不符按"没有核心数据"（安装引导）处理，只有魔数对但解码失败才提示"版本不匹配"。
- 为什么：静态托管普遍有 SPA 回退——`vite preview` 与 Cloudflare Pages 都会把不存在的路径返回 `200 + index.html`。只看 `response.ok` 会把它当成"文件在"，然后在解码时报魔数错，于是浏览器看到的提示是"请更新应用"（误导），而不是"去装应用"。实测确认过：`curl /__host/core.bin` 在 `vite preview` 下就是 200 + 141 KB 的 HTML。
- 影响：门禁的判据从"请求成不成"变成"内容对不对"，因此在任何托管上行为一致；代价是每次启动多读 4 个字节（可忽略）。

## D10 · dev 中间件只服务 `npm run dev`，preview 与生产不带 core.bin

- 决定：`vite.config.ts` 里加 `apply: 'serve'` 的 `hostCoreDev()`，把 `.tmp/hostcore/core-v1.bin` 挂在 `/__host/core.bin` 上，**只用于开发内循环**；不往 `public/` 里放文件（那样 `vite build` 会把它拷进 `dist`，门禁当场失效）。
- 为什么：开发时没有这个文件，页面就永远停在落地页，整个内循环废掉；而放进 `public/` 是"最省事但最危险"的做法——一次误提交就把核心数据发到线上了。中间件放在配置里，构建产物里根本不可能出现它。
- 影响：`npm run dev` 与真机行为一致（都能进游戏），`dist` 里没有 `core.bin`（已实测）。宿主4 会把"dist 里不得出现 core.bin"写成构建期的硬断言，防止将来有人改用 `public/`。

## D11 · `blockBehaviors.ts` 与 `blocks.ts` 循环引用，靠"求值期只构造闭包"保证安全

- 决定：接受 `blocks.ts → blockBehaviors.ts → blocks.ts` 的循环，并在文件顶部写下硬约束：本模块在**模块求值期只构造闭包**，绝不在顶层调用来自 `blocks.ts` 的函数（`bannerPatternTile` / `railTileFor`）。
- 为什么：行为里要复用 `bannerPatternTile` / `railTileFor`，把它们搬到 `blockBehaviors.ts` 会造成第二处定义（两处迟早漂）；而 ESM 的函数声明是提升的，只要不在求值期调用就安全。这个约束是隐性的、将来容易被破坏，所以写进注释。
- 影响：安全但脆弱——新增条目若在顶层"先算出个结果"，会拿到未初始化的绑定并抛 TDZ 错误（好在是启动即崩，不是静默错）。`test:behaviors` 覆盖了全部 46 块，能兜住这类误用。

## D12 · 发布构建改成"脚本后处理 + 断言"，而不是加一个打包器插件

- 决定：`build:app` / `build:web` 都是 `SOURCEMAP=0 vite build` 之后接 `node tools/release-check.mjs --mode app|web`；压缩、形态、断言三件事全在这一个脚本里。
- 为什么：这三件事的共同点是"做了不会让构建报错，不做也不会让构建报错"——`.map` 泄漏、`core.bin` 混进 app 形态、产物没压缩，全都静默。放在后处理脚本里，它们天然是**退出码**而不是"记得别忘"；而且不绑定打包器版本（这一轮的 Vite 8/rolldown 已经在 `minify` 默认值上让人误判过一次）。
- 影响：发布链路多一步 `node tools/release-check.mjs`（约 2 秒，主要花在把 4 MB JS 读进内存再压一遍）；`npm run dev` / `build:fast` 不受影响。退回方式：删掉两条 npm script 即可，产物本身不变。

## D13 · 主包体积基线改用"当前实测 + 余量"，不再沿用 338456

- 决定：`MAIN_GZIP_BASELINE = 740000`（实测 733200），并在注释里写明"338456 是批次 85 的旧数字，项目此后长了一倍多"。
- 为什么：那个数字是写 `tools/bundle-budget.mjs` 时量的，此后方块表从 200 多涨到 724、测试从 91 套涨到 178 套、还加了村庄/要塞/联机。拿它当"显著低于"的目标，无论怎么优化都到不了，等于把断言变成噪音。真正有意义的判据是**同一构建形态**下"数据搬走前 vs 搬走后"的差（预计 −20~30 KB gzip），那要等 `[发现]` 那条做完才有对比。
- 影响：现在的断言只能防"涨"（主包 > 740000 就红），防不了"该降没降"。这一点已在条目完成说明里明写，收尾时会弹窗让用户定夺是否接受。

## D14 · 回退"独立 boot 入口 + 动态 import main"，改回单入口

- 决定：撤销 `src/boot.ts` 作为入口，改成 `src/core/hostCore.ts` 提供 `ensureHostCore()`，由 `main.ts` 末尾的异步 IIFE 先过门禁再 `boot()`。
- 为什么：动态 import 让 `blocks.ts` 同时被入口 chunk 与 main chunk 引用，rolldown 在两个 chunk 里**各打一份**：实测主包 2.0 MB / gzip 556 KB + 额外一次请求，而单入口是 1.2 MB / 338 KB。另外"浏览器连 JS 都拿不到"其实不是必需品——没有核心数据，那份 JS 本来跑不起来；而体积翻倍是每次启动都要付的钱。
- 影响：浏览器仍会下载 JS（但拿到 404 后只显示提示屏、不启动引擎）。若将来确实需要"连 JS 都不给"，应当回到 Worker 网关（D9 之前讨论过的那条路），而不是靠打包器的 chunk 拆分——那会重新引入这份体积代价。

## D15 · esbuild 压缩显式带 `charset: 'utf8'`

- 决定：`release-check.mjs` 里 `esbuild.transform(..., { minify: true, charset: 'utf8' })`。
- 为什么：默认 `charset: 'ascii'` 会把全部中文与全角字符转成 `\uXXXX`，实测体积**反涨 14%**（4114.7 KB → 4676.0 KB）。这类"压缩反而变大"的行为不会报错，只会让人以为"压缩没生效"而去找别的原因——这一轮就绕了一次。
- 影响：产物保持 UTF-8（与现有产物一致）；若哪天要发布到对字符集有要求的 CDN，需要另议。

## D16 · 版本自报走 UA 尾部，不走 JSBridge

- 决定：宿主在 UA 末尾拼 `MinicraftHost/1.0 core/N`；页面用 `/MinicraftHost\/[\d.]+\s+core\/(\d+)/i` 读。
- 为什么：判定发生在**启动最早**的时刻，那时 JSBridge 还没建好；而 UA 在第一个请求里就有，不需要为一个整数引入一套异步消息通道，也不需要处理"桥没响应"的超时。伪造 UA 的收益也有限——伪造者最多把自己变成"版本未知"，而未知的处置是继续正常流程，最终仍会撞上 404。
- 影响：UA 长度增加约 30 字节；若将来要传递更多宿主能力（屏幕密度、是否支持某 API），UA 会变得难维护——那时应当转成 `x-minicraft-*` 自定义头（`loadUrl` 的首请求头），而不是继续往 UA 里塞。

## D17 · 版本判定是三态，`unknown` 绝不能落到"请更新应用"

- 决定：`evaluateHostVersion()` 返回 `ok` / `outdated` / `unknown`；`unknown`（浏览器或解析失败）继续正常流程，只有 `outdated` 才显示"请更新应用"。
- 为什么：二态写法（`hostVersion < min` 即拒绝）会把浏览器判成"太老"，于是网页访客看到"请更新应用"——而他根本没装过应用。这类提示错一次，用户会以为是自己设备的问题。三态写法把"没装"和"装旧了"分开，正好对应两种不同的落地页。
- 影响：多一个枚举值；`version.json` 取不到时回退到最宽松下限（不阻塞启动），代价是"清单挂了就暂时失去版本闸门"——比"清单挂了谁都进不去"划算。

## D18 · 两站用两个 Pages 项目物理隔离，而不是"同一个项目的两个目录"

- 决定：`minicraft-app`（宿主专属，无 `core.bin`）与 `minicraft-web`（完整前端，有 `core.bin`）是两个独立项目、两条独立流水线、两个域名。
- 为什么：两站产物只差一个 40 KB 的文件。放到同一个项目里（比如 `/app` 与 `/web` 两个子目录），"发错"的成本是**零成本且看起来正常**——游戏能玩，门禁失效，没有任何报错。物理隔离之后，发错只剩"workflow 里 `--project-name` 写错"这一个人为动作，而且两条流水线里该字符串各出现一次、写死、review 可见。
- 影响：多一个 Pages 项目与一条流水线（都免费）；域名要两个。退回方式：删掉 `deploy-cf-web.yml` 与 B 站项目即可，A 站不受影响。

## D19 · 灰度用"部署级两段式"，不引入 Workers

- 决定：`workflow_dispatch` 带 `channel=preview|production`；preview 部署挂到独立 URL（生产域名不动），验收通过再发 production。
- 为什么：Cloudflare Pages 没有百分比流量能力，真正的灰度要 Workers 的 `wrangler versions deploy --percentage`，而那意味着产物从"静态托管"变成"Worker 读 R2/私有资源"——一份新的运行时与新的故障面。现阶段用户量小，两段式已经能挡住"发出去才发现白屏"这类事故；等真的需要按比例放量再迁，迁移是**纯加法**（不影响现有门禁与产物形态）。
- 影响：没有真正的 A/B 分流能力；回滚依赖 Dashboard 的 "Rollback to this deployment"（秒级）或重发旧提交（一次构建时间）。这条限制已写进文档第 3、4 节。

## D20 · 把 `deploy-pages.yml` 从 `build` 改成 `build:app`（顺带修掉一个线上泄漏）

- 决定：GitHub Pages 的流水线改跑 `npm run build:app`。
- 为什么：原来跑 `npm run build`，而 `vite.config.ts` 的 `sourcemap` 默认**开着**（`SOURCEMAP !== '0'`），也就是线上一直挂着 `.map`——等于把全部 TypeScript 源码公开。这一条与本批次的目标直接冲突，属于"顺手发现就必须修"的那类；改完之后 Pages 上就是 A 站形态（浏览器只见落地页），与"不能在纯网站上运行"的要求一致。
- 影响：**上线内容发生可见变化**——GitHub Pages 从"能玩"变成"只有落地页"。这是预期行为（A 站定位），但需要用户知道；想在浏览器里玩要用 B 站。若用户希望 Pages 保持可玩，把这一行改回 `build` 即可，代价是源码继续公开。

## D21 · 新增 `public/_headers`（仅 Cloudflare Pages 生效）

- 决定：在 `public/` 下加 `_headers`，把 `core.bin` / `version.json` 设 `no-store`，`index.html` / `sw.js` 设 `no-cache`。
- 为什么：Cloudflare Pages 默认对 HTML 也做缓存。而这几类文件"旧一点"就会出事：`core.bin` 旧了是**静默错方块**，`version.json` 旧了是版本闸门停在上一版判断，`index.html` 旧了配新 assets 会白屏。GitHub Pages 会把它当普通文件忽略，两地都不报错。
- 影响：只影响 CF 托管；`dist` 里多一个 300 字节文件（已被 release-check 的断言覆盖：不参与 JS 体积统计）。

## D22 · 方块表数据外置**暂不做**：它卡在三处模块初始化期派生依赖，不是"搬 60 个声明"

- 决定：本轮核对后**不动代码**，把这条按"需要改描述"退回给用户定夺；随附已探明的两步路径。
- 为什么：
  1. `SPECS` 的构造过程**有副作用**：`WOOD_ID_MAP` / `WOOD_SHAPED_MAP` 是在 `WOOD_SPECS`、`WOOD_SHAPED_SPECS` 的构造体里被 `set()` 填充的（`blocks.ts:333` / `blocks.ts:416`，填充发生在 `flatMap` 与立即执行函数内部）。
  2. 这些 map 又在**模块初始化期**被读成活值：`export const Wood = Object.fromEntries(EXTRA_WOODS.map(...WOOD_ID_MAP.get...))`（`:386`）、`export const WoodShaped = Object.fromEntries(WOOD_SHAPED_MAP)`（`:483`）、`export const JUNGLE_LOG_ID = Wood.jungle!.log`（`:5008`）。这三处在 `SPECS` 为空时会得到 `undefined` 或直接 `TypeError`，**导入即崩**，不是运行到某功能才坏。
  3. 还有求值顺序问题：若 `blocks.ts` 静态 `import { SPECS } from './blockSpecs.ts'`，按 ESM 规则 `blockSpecs.ts` 的模块体**先**求值；而它的数组字面量要读 `blocks.ts` 的 `WOOL_ID_START` 等常量——此时那些绑定还在 TDZ，直接 `ReferenceError`。也就是说"把声明搬过去 + 加个 import"这一步本身就跑不起来，必须先解决求值顺序。
  4. 而 `SPECS` 又必须**整体**搬走（不能只搬大的那些）：`buildBlockTable()` 要求 id 从 0 连续，任何一半留在 JS 里都会让"第 N 条就是 id=N"这条不变量失效。
- 已探明的两步路径（各约 1 个批次）：
  1. **先把木材 id 映射从 SPECS 里解耦**：让 `WOOD_ID_MAP` / `WOOD_SHAPED_MAP` 在装表后由 `BLOCKS` 按方块名推导（8 种木材 × ~10 个 id，按名字完全可推），并让 `Wood` / `WoodShaped` / `JUNGLE_LOG_ID` 变成装表后可得的懒值。这一步做完，`SPECS` 才是"纯数据、无副作用"，可以被整体搬走。
  2. **再搬 SPECS**：`blockSpecs.ts` 只留数据；`blocks.ts` 用**动态 import + 顶层 await**（或构建期 alias 换成空实现）拿到 SPECS，从而绕开 TDZ；生产构建里 `SPECS` 为空、由 `hostCore` 从 `core.bin` 装表，`build:app` 的主包 gzip 应当从 716 KB 掉到 ~690 KB。
- 影响：本轮**零代码改动**，门禁（浏览器打不开）与体积（716 KB）都维持现状。若用户不同意这条路径，另一条可选项是接受"数据仍在主包里"，把这条降级为长期待办。
