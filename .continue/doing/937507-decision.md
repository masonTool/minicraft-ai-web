## D1 · 用「全量快照 + 小增量」，不用「APK 只放基础方块」

- 决定：APK 内嵌**全量** 724 条快照（`core.bin`），线上只放变化的 `core-delta.json`。
- 为什么：id 必须 0..N-1 连续，所以"只挑一部分进包"只能按**前缀**切。而按前缀切会把最值钱的那批（各种变体的硬度/光照/形状）公开挂在网上，保密反而更差；且改基础那批仍要发版。放全量快照 + 增量，保密面最小（线上只有变化条目），可迭代面最大（改属性、加方块都能热更）。**放弃的方案**：先冻结再固化（用户明确表示还要迭代）。
- 影响：仓库里多一个 40 KB 的 `host/core-baseline.bin`（增量对谁生效的唯一依据）；每次发 APK 后必须把它更新成 APK 里那份，否则增量会被指纹校验拒绝（不会错方块，但新方块白发）。退回方式：删掉 `coreDelta.ts` 与 `hostCore` 里那一次 `await applyRemoteDelta()` 即可，基线行为不受影响。

## D2 · 增量失败一律降级，绝不阻断启动

- 决定：`applyRemoteDelta()` 内部 catch 一切（404 / JSON 坏 / 版本不符 / 指纹不符），只 `console.warn`，用基线继续跑。
- 为什么：增量是"可选优化"，它不该拥有"让游戏起不来"的能力。另外用 `warn` 而不是 `error`：控制台门禁把 error 当失败，而"线上没有增量"是最常见、完全正常的状态。
- 影响：用户可能看不到新方块但没有任何提示（只有控制台一行 warn）。这是刻意的取舍——弹窗提示"增量加载失败"对一个正在进游戏的玩家没有意义；排查时看控制台即可。

## D3 · 增量用 JSON 而不是二进制

- 决定：`core-delta.json`（人可读）。
- 为什么：它本来就**公开**（线上文件），不需要靠二进制增加阅读成本；而 JSON 让"改了什么"在 git diff 里一眼可见——发布前 review 增量是正确的最后一道关。体积也不是问题：几条改动 ≈ 几百字节，gzip 后更小。
- 影响：解析要多做一层类型校验（`parseCoreDelta`），已覆盖 15 条断言（越界/长度/未知字段/空 set 都抛）。
