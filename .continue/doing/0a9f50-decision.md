## D14 · 水流不同步：先验"服务端不丢包"，再上日志，不靠猜
- 决定：不给 `FLUID_DBG` 之外的"猜测性修复"，先把可判定的那段钉死——用 `net-test` 压真实形态的突发批量（3 包 × 60 格），确认服务端限流桶（200/s·容量 400）、`MAX_BLOCKS_PER_MESSAGE`、距离闸都不丢合法突发；然后只在两端加计数日志。
- 为什么：静态读下来整条链（`setBlockAndUpdate → onBlockChanged → queueBlockChange → BlockFunnel → sendBlocks → 服务端 blocks → 客户端 case 'blocks' → onNetBlock → applyRemoteBlock`）是通的，三处"可能断"的地方（不广播 / 服务端丢 / 加入端不写）在画面上表现完全一样。按本项目约定（`MEMORY` 里那条"定位不了就加带 tag 的日志"），再多猜一轮只会把水搅浑。
- 影响：这条仍标 `[~]`（未完成），等用户贴一次 `[FLUID_DBG]` 就能二分定位到唯一分支。日志每 2 秒一行、只在有水方块往来时打，平时不刷屏；确认根因后应连同日志一起删掉（或降级为 `diag.event`）。

## D15 · `net-test` 里模拟"非房主的方块编辑"必须把坐标放在发送者附近
- 决定：突发批量用例的坐标从 `(40..49, 70, 40..45)` 改到 `(-5..4, 70, 0..5)`。
- 为什么：服务端 `blockEditRejection` 对**非房主**有距离闸（`withinEditReach`），远处坐标会被判 `distance` 静默丢掉——第一次跑出来只有 165/180，很容易误判成"限流桶在丢包"。这不是产品 bug，是测试用例站错了位置。
- 影响：用例现在真的在测"突发能不能整包送达"。以后写任何方块同步用例，坐标先算一遍到发送者的距离。
