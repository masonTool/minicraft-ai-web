## D1 · 快捷栏的几何从 DOM 实测来，不抄 CSS 常量
- 决定：`Hotbar2D` 的输入是 `getBoundingClientRect()` 量出来的面板与 9 个格子矩形（相对覆盖层画布），不在 canvas 侧再写一份 `--hotbar-slot / --hotbar-gap / --hotbar-pad`。
- 为什么：这三个变量在手机上还会跟断点走，安全区 `env(safe-area-inset-bottom)` 更是只有浏览器算得准。抄一份常量就等于埋一个"转屏后错 3px、刘海机上错 20px"的回归面，而且没人会写断言盯着它。不确定的地方：DOM 排版是异步的，`buildHotbar` 里第一次量可能拿到 0 宽 —— 用"量到 0 就置 pendding、下一帧再量"兜住。
- 影响：canvas 与 DOM 永远同一套几何，改 CSS 不需要改 canvas；代价是每次量 10 个 rect（只在 build / refresh / resize 时量，不进每帧）。

## D2 · 命中与提示继续借 DOM：格子设 `opacity: 0`，容器保持可点
- 决定：`?ui2d=1` 时把 `.slot` 的 `opacity` 设成 0、`#hotbar` 自己的背景/斜角/描边设成透明（边框宽度保留，避免两侧按钮位移）。点击、长按看物品、触摸切槽仍走原来的 DOM 绑定。
- 为什么：`Ui2DInput` 的 `pointer-events` 是**元素级**的 —— 覆盖层铺满全屏，一旦打开就会把 `#touch-look` 的视角手势全吃掉（`TIPS.md` 里"按钮看得见、点了没反应"的 canvas 版）。区域级穿透要等阶段 6 重做手势层，这一批不值得为它冒险。
- 影响：视觉 100% 由 canvas 画，交互 100% 还是原来那条路（零回归）。DOM 那 9 个格子仍在排版与合成里，所以**这一版不能用来量"省了多少 DOM 开销"**，只能看观感与一致性。

## D3 · 状态签名不变就不重画，每帧只 blit 一次快照
- 决定：`Hotbar2D` 把整条快捷栏画进一张离屏画布（`dpr` 倍背板，只覆盖面板范围 + 一圈发光余量），签名（矩形 / 选中 / 数量 / 图标引用 / 耐久档位与比例）不变时每帧只 `drawImage` 一次。
- 为什么：9 个格子每帧重画是 9 次图标 `drawImage` + 二十几次矩形填充 + 十几次文字，静止站着玩也要付这份钱；而快捷栏的变化率极低（换槽、捡东西、掉耐久）。缓存之后稳态开销与阶段 0 的红闪同级（一次 blit）。
- 影响：`Hud2D` 的"什么都没画就不清屏"这条优化对快捷栏不成立（它一直在），所以覆盖层现在是**每帧都清一次**；代价可接受，但记在这里免得以后有人以为它还是空闲零成本。

## D4 · 图标沿用现成的 `.slot canvas`
- 决定：canvas 侧画图标时不自己实现"图集裁切 + 等轴立方体"，直接把 `main.buildHotbar` 建好的那张 32×32 图标画布当 `CanvasImageSource` 传进去。
- 为什么：`ui/ItemIcon.drawItemIcon` 是这个仓库**唯一**的图标入口（背板倍率、块状物的等轴立方体、`image-rendering: pixelated` 都在里面），另写一份必然漂。而且 `src/ui2d/` 的约定是"不许依赖 `ui/`"，传 image source 正好不破坏这条：main 负责取图，ui2d 只负责画。
- 影响：图标清晰度与原版一致；`drawItemIcon` 的缓存照旧生效，等于零额外成本。若将来图标改由渲染层直接出纹理，只换 main 里传进来的 source。
