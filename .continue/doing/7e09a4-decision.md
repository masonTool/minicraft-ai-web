# 决策记录 · 会话 7e09a4a8365643649a615314c874b57e

> 上架 Google Play 的版权 / 商标处置。逐条都是用户在对话里拍板的，不是我的推断。

## D1 · 应用名保留 `Minicraft Multiplayer`

- 决定：商店名与 `src/core/brand.ts` 的 `BRAND` 都不动，只清对外文案里的商标字样。
- 为什么：用户明确说「不换」。我提示过 `Minicraft` 与 Notch 2011 年同名作品撞名、且与 Minecraft 字面近似（Play 假冒政策 + 账号连坐），用户仍选择保留。
- 影响：Play 侧「名称风险」长期敞口。对冲手段只能落在别处——上架时 `applicationId` 不带 `minicraft`（包名发布后永久不可改）。

## D2 · 成就标题只改「英文与原版逐字相同」的 33 条

- 决定：100 条成就标题里只重写 33 条（`★` 那批），其余 67 条是项目自创进度，标题本来也是自创，不动。
- 为什么：侵权面集中在「逐字照抄官方本地化」，自创标题不在保护客体上；全量重写会白改 67 条并牺牲玩家熟悉度。
- 影响：6 语言共 198 条字符串。advancement id / 触发条件 / 描述都不变，所以玩法与存档零影响。

## D3 · 方块 / 物品术语表（668 条）不动

- 决定：`src/core/registry/itemNames.ts` 与 `locales/*/item.ts` 保持现状，不换译名、不加前缀。
- 为什么：单条短名称不受版权保护，整表复制的维权成本高、判赔低；换名对可读性伤害大。用户也考虑过「每个名称前加一个字母」，我说明过这不产生独创性且体验崩坏，最终选不改。
- 影响：风险留档为「已知且接受」，后续不再重复讨论。

## D4 · 10 幅画全部改名 + 重画

- 决定：7 幅 1×1（kebab / aztec / alban / aztec2 / bomb / plant / wasteland）+ 3 幅多格（donkey_kong / skeleton / match）全部换成自创构图与新名字，贴图名随名字一起换。
- 为什么：这 10 幅一一对应 Zetterstrand 的署名画作（名字也照抄），「近似到能认出是哪一幅」属于改编；`donkey_kong` 还叠加任天堂 IP。用户原打算不改，听完风险说明后改为重画。
- 影响：`paintings.ts` 的 `name` 会进存档（多格画按名字存），改名后旧存档里的画读不回来——与 T5 的容错一起兜。玩法（按尺寸自适应、随机挑一幅）不变。

## D5 · 内部 `minecraft:` 命名空间改成自有前缀

- 决定：方块 / 物品 / 命令 / 联机协议 / 存档里的 `minecraft:` 前缀全部替换。
- 为什么：用户说「可以改，因为现在还没上线」。我保留了不同意见（内部 id 属于功能性互操作用语，收益低而改动面大），但按用户决定执行，排在队列最后一项单独提交。
- 影响：**旧存档 / 旧协议不兼容**。必须配 T5 的容错（不认识的 id 跳过并记日志），否则用户浏览器里的老档直接崩。

## D6 · 资源包（`.mcpack`）入口保留 + 加免责

- 决定：不删除 `src/core/resourcepack/` 的导入入口，只在设置页说明「只能导入你自己拥有的资源包」，且不提供任何下载入口。
- 为什么：不预置官方素材、不帮忙分发时，这一项的被追概率很低；删掉会损失「换外观」这个实用功能。
- 影响：只加文案与一处免责说明，功能零变化。

## D7 · 对外文案只清「安装提示 / 包元数据」，工程文档保留技术表述

- 决定：`public/manifest.webmanifest` 的 description 与 `package.json` 的 description 去掉「《我的世界》基岩版 1.18 复刻」；`README.md` 与 `AGENTS.md` 保留「Minecraft 1.18 复刻」这句技术定位（它们已有免责与版权归属段落）。
- 为什么：用户说「可以删」，但 `docs/store/` 六份文案里已经没有商标字样了（唯一出现 Mojang / Microsoft 的地方就是那句免责声明，删了反而更糟）；README 是给后续会话看的工程文档，抹掉技术定位会让 AI 接手时失去上下文，而它第 126-127 行已经写清「与 Mojang / Microsoft 无关联、相关名称与素材版权归 Mojang Studios」。
- 影响：真正会出现在用户设备上的只有 manifest description，已清。若用户要求 README 也清，改文案即可（一行）。

## D8 · 33 条里「维度专名 + 品牌名」那 3 条不改

- 决定：`story/root` 保持品牌名 `Minicraft`（只把英文副本里原版的 `Minecraft` 改掉）、`nether/root` 保持「下界」、`end/root` 保持「末地」；实际重写 30 条。
- 为什么：这三个词不是"照抄一段文案"，而是**我们自己的术语表里就有的专名**（D3 已判定术语表不动）。只改成就里的「下界」而界面别处仍写「下界」，会变成同一概念两个名字，玩家与后续会话都会混乱。`story/root` 的标题本来就是品牌名，不属于原版内容。
- 影响：这 3 条的可识别性保留（维度名很难换，换了等于换整套术语）；如果以后要彻底去联想，得连术语表一起换，那是 D3 的翻案，不在本批范围。

## D9 · 换画时**只换画面与名字**，尺寸档位与 1×1 的顺序一律不动

- 决定：1×1 仍是七幅、下标 0~6 的对应关系不变；多格画仍是 4×4 / 4×3 / 2×2 各一幅。
- 为什么：尺寸决定"墙够不够大才挂得上"，是玩法（不受保护的机制），改动它要重算放置与跨格占用的测试；而 1×1 的**变体号存在方块状态 bit3-5** 里，一调序，老存档里已经挂好的画就会集体换脸——不崩但玩家会以为自己的画被换了。
- 影响：这次换素材对存档零影响（单格画看下标、多格画看名字）。退得回去：画面与名字都在表里，改回来即可。

## D10 · 旧的多格画名保留成**只读别名**，不写进新存档

- 决定：`LEGACY_MULTI_NAMES` 把 `donkey_kong/skeleton/match` 映射到 `mural/banner/chart`，`multiPaintingByName()` 读的时候先查别名；写存档仍写新名字。
- 为什么：多格画是按**名字**存进存档的（`world/Paintings.ts` 的锚点表），改名会让老存档里那面墙静默变空白。尺寸档位没变，所以一对一映射没有歧义。
- 影响：老存档读得回来；新存档只会出现新名字。别名表有断言盯着「目标都在 MULTI_PAINTINGS 里」且「现用名字不在别名键上」，防止它自指或写错。

## D11 · 「非官方」声明放**设置页底部**，不恢复首页页脚

- 决定：`settings.notice` 挂在设置页 footer（恢复默认按钮之上），首页保持用户要求的干净。
- 为什么：用户此前明确删过首页页脚（批次 20261024-1152，理由是"碍眼"），恢复会与用户审美冲突；但商店审核与权利人投诉需要一个**可见、可指出**的声明位置，设置页是玩家一定会去、又不占首屏的地方。两条文案都做成 10px 灰字，不抢注意力。
- 影响：只加文案与两个 DOM 节点，无行为变化。若以后要回到首页，把 `makeFooterNotice()` 挪到主菜单即可（一条键复用）。

## D12 · 不认识的 id：**跳过 + 记账**，绝不抛错、也绝不写进世界

- 决定：方块 id 不存在 → 该格不写（保留地形）并记一笔；物品 id 不存在 → 丢掉并记一笔；画名认不出 → 跳过并记一笔。账本随诊断日志导出，打开另一个世界时清零。
- 为什么：读档失败是最糟的体验（整档打不开），所以任何单条坏数据都只能跳过。但"跳过"必须可追查：原本三条路径全是静默的，玩家看到"房子少了块 / 背包少件东西"时，导出日志里查不到原因。记账本刻意做成纯数据（不碰 DOM/console）——手机上看不到控制台，项目既有的取日志路径就是「设置 → 日志 → 导出」。
- 影响：正常存档零变化（只有坏 id 才会进账本）。32 种上限 + 溢出计数，避免"整体偏移"这类坏档把导出文件撑爆。退得回去：删掉三个 `noteSaveIssue` 调用即恢复原行为。

## D13 · `LICENSE` 选「保留所有权利」，不选 MIT

- 决定：仓库授权写成 proprietary（保留所有权利，禁止改名二次上架与商业分发）；第三方库照旧按 MIT 保留声明。
- 为什么：这个项目要上架带广告的商店版本，"MIT 自己的代码"等于允许任何人原样打包上架、与你自己竞争；而 MIT 的义务只出现在**第三方库**上，二者不冲突。以后要开源可以随时替换成 MIT/Apache，反过来（从 MIT 收回）做不到。
- 影响：只影响他人复用，不影响你自己发布；`README` 与 `LICENSE` 已互相指向。

## D14 · 隐私政策放 `public/privacy.html`（自身站点），且按「无广告 SDK」的现状写

- 决定：隐私政策做成站点内的静态页（`/privacy.html`），中英双语；文案明确写"当前构建不含广告与统计 SDK"。
- 为什么：Play 需要一个可公开访问的 HTTPS 链接，用本项目自己的域名最不容易失效；文案必须与代码一致——仓库里**确实没有任何广告/统计 SDK**，若照抄"我们使用广告服务"反而会在 Play 的数据安全表单里自相矛盾。
- 影响：一旦真的接入广告 SDK（可能在 Android 壳里），必须回来改这一页 + Play 的数据安全表单，否则属于虚假声明。联系方式一栏目前是占位符 `<请填写你的联系邮箱>`，**发布前必须填**。

## D15 · 命名空间用 `minicraft:`，旧前缀只保留在**读**路径上

- 决定：全部注册名改成 `minicraft:<短名>`；`registry/ids.ts` 的 `normalizeId()` 负责把旧前缀归一化，只用于读（老存档、老命令文本、老资源包）。
- 为什么：全局替换本身很机械，真正的坑在"读进来还是旧写法"的三处——进度存档按 id 字符串存、命令方块里存着玩家当年敲的 `/give minecraft:stone`、资源包 manifest 可能带前缀。给它们一个统一入口比在每个调用点写一遍兼容判断可靠。
- 影响：新写出去的一律新前缀；旧文本仍然可用（`command-test` 里 `/locate structure minecraft:village` 那条继续当回归用例）。**退不回去的是"新存档拿到旧版本里"**——旧版本不认识 `minicraft:` 前缀，会把达成记录当未知跳过（有 T5 的容错兜底，不会崩）。

## D16 · 进度页第一个页签从「我的世界」改名「方块世界」

- 决定：页签 id `minecraft` → `world`，中文标题「我的世界」→「方块世界」，英文 `Minecraft` → `Block World`。
- 为什么：这是本次改名过程中**唯一真正摆在玩家眼前**的商标文本（进度页顶部那个页签名），比内部的 `minecraft:` 前缀重要得多。同时它和 D1"保留应用名"的取舍不冲突——页签名是内容标题，不是产品名。
- 影响：纯显示文案 + 一个内部 id；进度数据的 id 里 `story/*` 前缀不变，所以存档与触发逻辑零影响。
