## D1 · `drawerFits()` 的判据改成「基准尺寸不打折 + 格子 ≥44」，而不是「装不下就保持折叠」

- 决定：`drawerFits()` 只在「基准抽屉 360×196 被视口压小」或「格子缩到 44 以下」时返回 false；
  返回 false 的处置交给 `BuildToolbar`（网格内部滚动），不再有"保持折叠"这条分支。
- 为什么：抽屉形态下已经没有可折叠的展开列（折叠态只剩一颗总开关，与抽屉无关），
  旧的 `buildToolbarFits()` 语义在新形态里没有对应动作。原计划里写的"240 高给 false"是以旧口径
  （236px 竖条塞不进 240 高）推的；实测按新口径，320×240 确实是 false，但原因是**宽度** 304 < 360，
  而 844×240 这种"矮但不窄"的视口是能完整装下的（暂停条下还有 202px），所以断言按真实原因写，
  不为了凑那条结论去加一条假的判据。
- 影响：只影响 `drawerFits()` 的语义与两条断言；`buildDrawerBox()` 仍会把盒子压进视口（不越界）。

## D2 · 格子上限随 `touchScale` 缩放，下限 44px 恒定

- 决定：`buildCellSize()` 的上限 84×68 乘 `touchScale`（0.8x → 67×54，1.4x → 118×95），
  下限恒为 44×44；抽屉的内边距 / 头部 / 间隙同样按 `touchScale` 缩放。
- 为什么：44px 是平台最小手势尺寸，缩小它等于让手指按不准；但"放大"没有这个约束，
  不跟着触摸缩放走会得到"按钮变大了、抽屉还是小的"这种割裂感。
- 影响：`BuildToolbar` 与 CSS 必须用同一组数字（CSS 用 `calc(… * var(--touch-scale))`）。

## D3 · 把文案条目（原 B3）提到 DOM 改造（原 B2）前面做

- 决定：队列里这两条对调，文案先落地，抽屉的 DOM/CSS 随后。
- 为什么：`audit:i18n` 把"源码里 `t()` 了但表里没有"判成硬错误，而 `audit:i18n` 在 `check:fast`
  里——抽屉头部要用 `buildtools.panel.title` / `.endBuild`，先写 DOM 会让每次提交都被门禁拦住，
  只能先塞临时字面量再回头拆，反而多一次改动。
- 影响：只影响本批两条任务的先后；条目标号沿用 B2/B3 不变（编号是位置，不复用含义）。
  面板的「返回」不再新增 `buildtools.panel.back`，直接复用已有的 `editor.back`（同一份文案表、6 语言齐全）。

## D4 · 抽屉的指针锁由 `onPanelChange` 单独管，不复用 `uiOpen`

- 决定：`BuildToolbar` 新增一个 `onPanelChange(open)` 回调，主程序在里面开面板时
  `exitPointerLock()`、关面板时按 `!uiOpen && !touch` 重新 `requestPointerLock()`。
- 为什么：走 `uiOpen`（`handleInventoryOpen`）会顺带清按键、收起触摸层、退锁再抢锁，
  每开关一次面板抖一下；而抽屉的遮罩已经吃掉了世界观交互，不需要那套副作用。
  两种做法都能"关掉面板后视角能转"，代价都不难撤回，取副作用最小的那个。
- 影响：指针锁只在桌面端有意义（`this.touch` 在时直接跳过）；面板开合不再影响
  `uiOpen`、背包、触摸层显隐。
