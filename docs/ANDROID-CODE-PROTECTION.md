# 安卓发版 · 代码保护方案

> 前言
>
> 一句话：**纯本地 APK 不存在"绝对安全"。** 代码一旦随安装包发到用户设备，拥有那台设备的人
> 原则上就能拿到它——root、脱壳、反编译只是成本问题。所以本方案的目标不是"让人拿不到"，
> 而是**把逆向成本抬到高于收益**，同时堵死"改个名字二次上架"这条路。
>
> 方向错了会花很多钱办没用的事。下面每一条都标注了「挡住什么」与「为什么值得/不值得」。

---

## 0. 结论先行

| 优先级 | 动作 | 挡住什么 | 工期 |
| --- | --- | --- | --- |
| **1** | GitHub 仓库转私有 + Pages 站点下线 | AI 完全绕开的最后一条路 | 10 分钟 |
| **2** | 关 WebView 调试 + `allowBackup=false` + 收紧流量 | 内存 dump 最省事的两条路 | 10 分钟 |
| **3** | 签名校验（2-3 处分散） | AI 自动重打包（实测 84% 成功率） | 半天 |
| **4** | 核心数据**改变形态**（非仅加密） | AI 认不出数据是什么 | 1-2 天 |
| **5** | 密钥运行时派生 | AI 静态分析失效 | 1 天 |
| **6** | R8 全量 + `.so` strip | 人和脚本小子 | 1 小时 |
| — | 反调试 / 反 frida / 商业壳 | — | **不做**，见 §5 |

**决定性的一步是第 1 项，不在任何技术方案里，在 GitHub 设置里。**

## 1. 现状盘点

### 1.1 已经做对的（这套仓库的既有设计）

| 已有的保护 | 位置 | 效果 |
| --- | --- | --- |
| 应用形态双构建 | `build:app`（`SPECS_STUB=1`） | 724 条方块表明文不进主包 |
| 核心数据外置 | `host/core-baseline.bin` → APK assets `__host/core.bin` | 浏览器打开是 404 落地页 |
| 发布断言闸门 | `tools/release-check.mjs` | 无 `.map` / 无明文 core.bin / 体积基线，退出码兜底 |
| 服务端逻辑下沉 | `server/rust` → `libminicraft_server.so` | 原生，比 JS 难得多 |
| 法务声明 | `LICENSE` 明确禁止二次打包上架 | 配合商店投诉，真正管用 |

**关键认知**：`release-check.mjs` 把"产物里不该有什么"做成了退出码断言。这类保护**必须**是 CI
断言，靠人记一定会失效。后续所有加固都应当沿用这个模式。

### 1.2 必须先补的四个漏洞

| # | 问题 | 现状 | 风险 |
| --- | --- | --- | --- |
| 1 | **没有 release 签名配置** | `app/build.gradle` 里无 `signingConfig`，只有 `assembleDebug` | 发不出正式包；debug 签名包任何人不需密钥就能重签覆盖 |
| 2 | 包名不一致 | `capacitor.config.json` 是 `com.minicraft.app`，`hostCore.ts` 的 `PLAY_STORE_URL` 写的是 `com.minicraft.game` | 上架后落地页引流到不存在的应用 |
| 3 | `allowBackup="true"` | `AndroidManifest.xml` | `adb backup` 能整份拖出应用数据 |
| 4 | `minifyEnabled false` + `allowMixedContent true` + `androidScheme: http` | `build.gradle` / `capacitor.config.json` | Java 层零混淆；明文流量；WebView 走 http |

### 1.3 最严重的敞口：核心数据已公开

> ⚠️ **这一条比任何技术手段都重要，必须先处理。**

`build.gradle` 的 `copyHostCore` 任务把 `host/core-baseline.bin` 拷进 APK 当 `core.bin`，
**而这个文件在 GitHub 上可匿名下载，哈希与本地完全一致**：

```
本地：bddd38c5…57293b9
线上：bddd38c5…57293b9   ← 同一个文件
```

`src/core/registry/blockSpecs.ts`（2305 行明文方块属性）同样公开可读。

因此：**在仓库公开的前提下，攻击者根本不需要"破解"，他直接下载。** 这是绕过，不是破解。
此时做多少加固都是零收益——加密的 `core.bin` 对他毫无意义，他手上是原始数据。

## 2. 威胁模型：攻击者会怎么做

按攻击者实际会试的顺序（**从最便宜的往里试**），并标注 AI 介入后的成本变化。

### 2.1 APK 的四层结构

| 层 | 内容 | 攻击入口 |
| --- | --- | --- |
| `assets/public/` | JS 与 HTML（已 minify，无 sourcemap） | 解压直读 |
| `assets/__host/core.bin` | 724 条方块表 | 当前是明文 |
| `lib/arm64-v8a/*.so` | Rust 服务端 | 反编译 |
| 运行时内存 | 解密后的明文 | **必然存在，无法根除** |

### 2.2 攻击路径与成本

| 攻击路径 | 纯手工 | AI 辅助 | 说明 |
| --- | --- | --- | --- |
| 下载公开的 `core.bin` | 1 分钟 | 1 分钟 | **完全绕开整套方案** |
| `clone` 仓库自建 APK | 10 分钟 | 10 分钟 | 源码完整，自己就能构建 |
| `unzip` 读 JS | 5 分钟 | 5 分钟 | minify 不是加密 |
| `jadx` + LLM 语义还原 | 1 天 | **30 秒** | 实测可准确还原命名与业务逻辑 |
| `adb backup` 拖数据 | 5 分钟 | 5 分钟 | `allowBackup=true` 时成立 |
| DevTools 挂钩内存 | 5 分钟 | 5 分钟 | **最致命**，直接导出明文方块表 |
| `apktool` 改包重签 | 2 小时 | **5.5-9 分钟** | 实测成功率 84%（闭源模型） |
| 反编译 `.so` 找固定密钥 | 2 天 | **1-2 小时** | AES S-box 是极强特征，AI 一眼认出 |
| `frida` hook 解密函数 | 1-3 天 | **10 分钟** | AI 直接生成 bypass 脚本 |
| XVM 代码虚拟化 | 2 周+ | 2 周+ | **AI 几乎不降效**，唯一真正有效的 |

### 2.3 关键判断：AI 改变了什么

**AI 让"读懂你的代码"几乎免费，但对"拿到你的数据"没有本质帮助——除非数据就在 APK 里。**

这对方案有直接影响：

- 藏一个**固定密钥** → AI 1-2 小时定位（AES 常量太好认）
- 让密钥**运行时派生** → 静态推理失效，必须动态调试，成本回到 3 天
- 商业壳 XVM 把代码编译成**私有指令集**，AI 没有训练数据、无从下手——这是唯一对 AI 真正有效的

**可利用的弱点**：AI 会自信地给出错误答案（幻觉）。**防护越强，AI 越可能给出自信但错误的解释。**
本次，AI 的幻觉站在防守方这边——见 §3.4 的"改变数据形态"。

**新增的现实威胁**：AI 破解已经**工业化**。2026 年 9 月 Symantec 与 Checkmarx 披露，
有团伙批量爬取 1840 万个 APK 反编译后灌进 LLM 提取硬编码凭据。这意味着不是"某个高手针对你"，
而是"被扫到就自动处理"。**推论：APK 里不能有任何硬编码的密钥、token、API key。**
本项目是纯离线单机，本来就没有云端凭据，这是天然优势，但发版前要确认没有残留。

## 3. 分层方案

### 3.1 第 1 层 · 堵漏（必做，半天，收益最高）

| 动作 | 说明 |
| --- | --- |
| **仓库转私有** | 一票否决项。同时确认 Pages 站点是否暴露核心数据 |
| release 签名 | 生成 keystore，`signingConfig` 从 `local.properties` / 环境变量读，**密钥绝不进仓库** |
| R8 全开 | `minifyEnabled true` + `shrinkResources true`，补 Capacitor 与 `@JavascriptInterface` 的 keep 规则 |
| 关调试 | `setWebContentsDebuggingEnabled(false)`（release），当前**未显式设置，依赖 Capacitor 默认** |
| 关备份 | `allowBackup="false"` |
| 收紧流量 | `androidScheme` 改 `https`；关 `allowMixedContent`；`usesCleartextTraffic` 只留调试 flavor |
| 包名统一 | 选定一个包名两处对齐（建议 `com.minicraft.app`，配置里已是它） |

**为什么这一层先做**：零运行时开销，纯赚。且第 1 项不做的前提下，后面所有工作都可能白做。

> ⚠️ **keystore 的前置决策**：本地新生成还是已有现成的？这个不要由 AI 代为生成密钥材料——
> **一旦丢失，应用再也无法更新，只能换包名重新上架。**

### 3.2 第 2 层 · 核心数据加密（收益/成本比最好，1-2 天）

现状：`core.bin` 是**明文二进制**，`unzip` 拿到后对着 `blockTableCodec.ts` 反着解就能读出全部
724 条方块属性。**这是目前最值钱的数据资产。**

做法：

1. `core.bin` 用 AES-GCM 加密后放 assets
2. **解密密钥编译进 Rust `.so`**，不从 Java 层传、不落 JS
3. 运行期：JS 请求 `__host/core.bin` → Java 拦截 → 调 JNI 解密 → 明文回 WebView

**为什么密钥放 Rust 而不是 Java**：Java 字节码反编译成本极低，`strings` 一把就能捞出来。
放进 `.so` 后要定位密钥得反汇编 ARM64，成本差一个数量级。

**配套改动**：`build:app` 增加加密步骤；`baseline.json` 的 fingerprint 改成对**明文**计算，
保证增量机制（`gen:delta`）不受影响；`release-check` 追加断言——assets 里那份必须是**密文**
（检查 magic header）。

### 3.3 第 3 层 · 防重打包与完整性（半天）

| 动作 | 挡住什么 |
| --- | --- |
| 签名校验（读 `PackageManager` 签名哈希比对） | AI 自动重打包（84% 成功率那条） |
| assets 密文哈希校验 | 替换数据包 |
| 校验点**分散 2-3 处** | 单点 patch 的成本太低，分散后 AI 漏一处就失效 |

**注意**：Java 层的校验基本是"防君子"。要真正抬高成本，校验点应有一处放在 `.so` 里且被多处调用。
但**不要为此过度设计**——做到 2-3 处分散即可。

### 3.4 第 4 层 · 让数据"不是数据"（强烈推荐，1-2 天）

**这一招比加密更有效，且更便宜。**

加密的信号太明确了：AI 看到高熵二进制 + AES 常量，立刻知道该干什么。改变形态的做法：

- `core.bin` 字段不按结构连续排列，而是**按藏在代码里的置换表打散**
- 数值不存原始值，而是经过一次**看似业务逻辑的变换**（如存 `id XOR hash(name)`）
- 解码逻辑**分散在三个看似无关的模块**（伪装成存档序列化 / 网络协议打包 / 渲染缓存）

效果：AI 拿到解码器也**不知道自己在解什么**，可能给你一个自信但错误的结构猜测。
**攻击者要理解的是"你的设计意图"，而不只是"你的密钥"。**

### 3.5 第 5 层 · 密钥运行时派生（1 天）

从设备特征 + 时间 + 代码段哈希拼出密钥，不存固定常量。**把 AI 从"静态找常量"逼到"动态调试"，
成本从 1-2 小时抬回 3 天。**

### 3.6 第 6 层 · R8 + strip（1 小时）

R8 全量混淆 + `.so` strip（去掉符号表、字符串常量、panic 信息）。

**注意**：R8 对 AI **几乎无效**（AI 靠结构推断，不靠命名）。它仍是必做的——拦脚本小子、减包体、
免费基础盘。**但别把它当防线。**

## 4. JS 混淆：先测量再决定（选做）

### 4.1 反对意见

`javascript-obfuscator` 的强混淆（控制流平坦化、死代码注入）对 2 MB 主包会带来
**30%-100% 体积膨胀和明显启动变慢**，而收益只是让逆向上手慢几小时。

**本项目已有体积基线闸门**（`release-check.mjs`，当前基线 1.5 MB，容差 0.5%），
强混淆会直接顶爆它。

### 4.2 折中做法

- **不做**全局强混淆
- **只对** `src/core/registry`、`src/core/net`、`src/core/save` 做轻量混淆（标识符重命名 + 字符串数组）
- **必做**的是让 `build:app` 断言产物里不含关键字符串（如 `blockSpecs` 字段名、协议字段名），
  把"能否被 grep 出来"变成 CI 门禁
- **先测 baseline**（体积 + 启动耗时），超阈值就退回去

## 5. 明确不建议做的

| 手段 | 为什么不做 |
| --- | --- |
| 反调试 / 反注入 | 纯离线单机收益极低；AI 十分钟生成 bypass；且每次 Android 大版本都可能误伤真机 |
| 反 frida / 反 dump | **技术上无法根除**——只要游戏要跑，明文必然在内存里。投入是消耗战，打不赢 |
| VMP / 自定义壳 | 维护成本远超个人项目承受能力 |
| 整包加密前端 | WebView 必须能读到才能跑，会和加载链路直接打架 |
| Play Integrity | 需要联网，与本项目"纯本地"定位冲突 |
| 商业壳（DexProtector / XVM） | 唯一对 AI 真正有效，但要商业授权按年付费；本项目攻击动机是"抄一份上架"而非金融窃密，**投入产出比不成立** |

## 6. 落地检查清单

发版前逐项确认，**每一项都应是脚本断言或可验证的产物，不是"记得别做"**：

```
[ ] GitHub 仓库已转私有
[ ] Pages 站点已确认不含核心数据（或已下线）
[ ] APK 里无硬编码密钥 / token / API key
[ ] release 签名配置就位，keystore 不在仓库内
[ ] minifyEnabled true + shrinkResources true，Capacitor keep 规则已补
[ ] setWebContentsDebuggingEnabled(false)（release 生效）
[ ] allowBackup="false"
[ ] androidScheme=https，allowMixedContent 关闭
[ ] 包名统一（capacitor.config.json 与 hostCore.ts 的 PLAY_STORE_URL 一致）
[ ] core.bin 已加密（release-check 断言密文 magic）
[ ] 签名校验 2-3 处分散
[ ] .so 已 strip
[ ] npm run check 通过
[ ] npm run build:app 通过（含 release-check）
```

## 7. 最终判断

全做完之后，面对 AI 辅助破解，实际门槛是：

> **需要一台 root 设备 + 动态调试能力 + 3 天以上 + 逆向工程经验。**

而有这个能力和动机的人，不如直接自己写一个——**本项目的护城河是 181 套测试保证的行为一致性
和持续迭代速度，那才是 AI 抄不动的东西。**

方块表只是原料，不是游戏。
