# 机制说明 · README

> 这份文档是 continue-do 的**说明书**：文件分工、编号、队列格式、钩子行为、收尾流程、已知的坑。
> 读者是 AI。它只写**稳定规则**——当前进度不在这里（看 `doing/` 和 `DONE.md` 顶部）。
> 数量、耗时这类会变的事实不写在这里，要看就跑命令（`check.mjs --list`、`ls .continue/hooks`）。
> **这份文件由安装器覆盖，不要手改**——机制要改就改技能里的 `assets/.continue/README.md`；
> 手改会在下次重装时被冲掉（`check.mjs version` 会把"被本地改过"点出来）。

**用途**：给**大型项目的持续型 AI 开发**用——需求、队列、进度、踩坑都在 `.continue/` 里，
跨会话不丢；钩子逐条递任务、拦未提交改动、提交前跑检查。

**⚠️ 平台前提：这套机制依赖会话钩子。** 两个宿主的钩子都会跑，差别只在
**Stop 反馈每条用户消息能被采纳几次**（`loop_limit`，详见 §6）：WorkBuddy 一直续跑到队列空；
CodeBuddy IDE 缺省只采纳 1 次（安装器写 100，重启会话后连续推进）。上限为 1 时**不报错**，
症状是"对话停了"（钩子照样 exit 2，宿主丢了反馈）——日志里的 `续跑第 N 次` 是唯一的区别。

## 0. 为什么这样设计（七条原理）

后面每一节的规则都是这七条的落地。判断某条规则值不值得存在，用原理 3 那把尺子量。

| # | 原理 | 这个框架靠什么保证它 | 还只能靠人 |
| --- | --- | --- | --- |
| 1 | **单一事实源** | 一处登记：`config.json` 的检查命令、`check.mjs` 的 `CHECKS`、`settings.json` 的注册；跨文件核对：队列引用的 `T` 必须在 `TASKS`、`DONE` 与 `OVERVIEW` 的批次互相对得上、`TIPS` 模块名对得上 `OVERVIEW` | 队列协议的文字写在三处（本文、钩子注入、`AGENTS.md`），改一处要记得改另两处 |
| 2 | **派生即计算** | 条目号由脚本按文件顺序算（"第 N/M 条"）、批次号由 `queue-init` 生成、禁止写 `提交 n→m`；钩子写日志、人只看结论 | 文档里"默认 5 轮""最多拦 2 次"这类数字仍是从代码抄的，改了代码没人提醒 |
| 3 | **约束即代码** | 每次踩坑都落成一条会红的检查：`audit-ids` / `audit-docs` / `selftest` / `pre-commit`。本文 §7.1 每条规矩都标了"谁在查" | 收尾五步的顺序、判断"这条算不算坑"、拆分任务粒度——机器判断不了，本文 §7.2 明说 |
| 4 | **分层门禁** | 同一条 `checks.fast` 在三处跑：内循环（手动）、`pre-commit`（每次提交）、Stop 守卫（停下时工作区还脏）；安装器 `--ci` 可写 GitHub Actions 工作流，跑的是同一条 `check.mjs` | 别的 CI 平台要自己接（命令相同，直接照抄） |
| 5 | **进度外置** | 队列是文件、进版本库、跟着任务一起提交；队列没做完不让停（宿主允许续跑时，见 §6）；连续 N 轮没做完自动标 `[阻塞]` | 会话被强制中断时，最后一条的说明可能没来得及写 |
| 6 | **一个改动 = 一个提交** | 一次只递一条任务；`pre-commit` 拒绝一次勾掉多条队列条目；提交信息带 `[Tn]` | "这条改动是不是塞了两件事"仍要人判断 |
| 7 | **认知预算** | `audit-docs` 给每份入口文档和队列文件设行数硬上限，超了就红 | 超上限后的归档动作目前要人执行（`archive-done.mjs` 见 §6） |

**"讲出来"和"机制保障"的关系**：只讲不查 = 愿望；只查不讲 = 遇到灰色地带人和 AI 都不知道怎么判断，然后绕过它
（`--no-verify`、`auto.off` 都是现成的绕过口）。所以两层都要：原理写在这里、机制写在脚本里，
而**管不到的部分必须明确列出来**（§7.2），不许假装有保障。

## 1. 六份文件各管一件事

同一内容只写一处，别互相抄。

| 文件 | 回答的问题 | 组织方式 | 谁写、何时写 |
| --- | --- | --- | --- |
| `TASKS.md` | 接下来做什么（粗略需求） | 优先级 A / B / C，每条带 `T` 编号 | 用户提；AI 当场落 `[ ]` 并编号，收尾补 `[x]` |
| `doing/.worktree/todo/` | 下一批在**哪个会话**里做（交接） | `queue.md`（整份队列）+ `context.md`（中文上下文） | AI，`doing/` 里已有别的会话队列时才写；新会话接管后清空 |
| `doing/<sid>.md` | 这一轮做什么 + 每条**怎么做的** | 顺序 + 四态标记 + 里程碑节点；条目下方就地写完成说明 | AI，开工前建、边做边写 |
| `DONE.md` | 第 N 批做了哪些条目、各自怎么做的 | 时间线（批次倒序），整份队列原样搬运 | AI，收尾时 |
| `OVERVIEW.md` | 每个模块有哪些实现、哪些坑 | 按模块；实现挂 `T` + 批次，坑挂一行摘要 | AI，收尾时 |
| `TIPS.md` | 下次怎么避开 | 按大模块分节：症状 → 根因 → 处置 | AI，踩坑当场或收尾时 |
| `README.md` | 机制是什么（本文） | 规则分节 | AI，改机制时 |

判据一句话：

- 「只有这批需要知道」→ 写在**队列每条任务下方**，收尾时原样搬进 `DONE`；
- 「这个模块以后还要用」→ `OVERVIEW` 挂一行（实现带 `T` + 批次；坑带摘要），细节进 `TIPS`；
- 「下一步做什么」→ 只写 `TASKS`。

## 2. 编号：把三份文档串起来

**设计原则**：能派生的绝不手写，必须手写的必须能校验。手抄的数字一定会漂，手抄的编号一定会撞。

| 编号 | 形态 | 唯一性来源 | 谁写 | 规则 |
| --- | --- | --- | --- | --- |
| 需求号 | `T12` | 人工递增 + `audit-ids` 校验 | AI 当场落号 | **永不复用、永不改号**；写错就作废重开新号 |
| 条目号 | `第 2/5 条` | 脚本按文件顺序算 | 脚本 | 每轮注入告诉你；**不落盘、不用手写** |
| 批次号 | `批次 <批次号>` | 时间戳 + 撞号顺延 | `queue-init` 生成 | 一批一个号，开工定下后恒定 |

**批次号**：格式 `YYYYMMDD-HHmm`，开工时由 `queue-init` 生成并注入，AI 抄进队列头部 `> 批次：`。
`nextBatch()` 扫 `DONE.md` 与 `doing/` 里所有用过的号，撞了就顺延一分钟。
不用提交数当批次号：同一提交点开工的两个会话会撞号，一批里多次提交会让号漂移。
缺失时**不回退**：`auto-continue` 每轮显式告警，要求补上。

**条目号**：用来指代"这一轮做哪条"和隔离时精确定位。不用正文当身份——两条正文相同时会标错对象。
它**不是**需求号；需求号是条目里的 `[T12]`，指向 `TASKS.md`。

`[发现]` 条目可以暂时没有 `T` 号；收尾时用户确认要做的，再落成正式需求。

**号作废也要留痕**：提过但没采纳的号不会再使用，在 `TASKS.md` 里写一行 `作废编号：T9~T15`。
不写的话 `audit-ids` 会把这段空缺当成"手抄错号"一直提示——提示长期挂着，人就会学会无视它。

## 3. 队列与标记

每个会话一份：`.continue/doing/<session_id>.md`。文件名必须与会话 ID 一致——钩子只靠 ID 推导路径。

| 标记 | 谁写 | 含义 |
| --- | --- | --- |
| `- [ ]` | AI | 待办（规划时写） |
| `- [~]` | **钩子** | **进行中**：递给你那一刻就自动改好（不用你动手，也别改回 `[ ]`） |
| `- [x]` | AI | 完成 |
| `- [阻塞]` | **钩子** | 卡住：连续 N 轮（默认 5）没做完被隔离，等用户决策 |
| `- [ ] [发现]` | AI | 干活时撞见的新问题，有配额，必须写证据 |
| `- [ ] [自审]` | AI | **每批最后一条**：审三层目标（§8），不带 `T` 号 |

只认这四种。`[~]` 是"**正在做**"，不是"跳过"；跳过 / 放弃没有标记，走"回复里说明 + 用户决定"。
`[-]` 之类的其它写法会被钩子静默忽略，所以 `audit-ids` 直接判红。

头部两态（**只认文件前 6 行**，正文里提到这几个字不算）：

- `> 状态：执行中` —— 钩子开始递任务；
- `> 状态：讨论中` —— 放行不递任务（还没和用户确认方案时用）。

规则：

1. 讨论阶段不要建队列；要动手时才建，每条都要能独立验证、能单独提交。
2. 一次只做一条：钩子把这条标成 `[~]` 再递给你；**自测通过后**写完成说明再改 `[x]`（见 §4）。
   没验证不算完成——自测方式由各项目自己定，框架只管"有没有验、结果是什么"。
3. **收尾自动执行**：`[ ]` / `[~]` 都没了 → 钩子直接下令做完这五步（有 `[阻塞]` / 未验证条目时才先弹窗要用户拍板）：
   ① 整份队列**原样**写进 `DONE.md`（含 `[阻塞]` 和每条下方的完成说明，标题带 `批次 <号>`，不写 `提交 n→m`）；
   ② 更新 `OVERVIEW.md`：完成项按模块挂 `T` + 批次号，批次索引加一行，新坑加一行摘要；
   ③ 整份队列在 `TASKS.md` 里落地（已有条目改 `[x]`；当场任务补到 `C. 已完成`，
      项目若用 A~O 之类自有分节，就落在它自己的「当场任务」节）；
   ④ **自问一次**：这轮有没有会重复踩的坑 → 有就补 `TIPS.md`（按模块分节）；
   ⑤ **归档**队列文件（`node .continue/hooks/archive-queue.mjs <会话ID>` → `.logs/<会话ID>/`，不要 `rm`）。
   边界：新需求当场落成 `[ ]` 并编号，收尾只补 `[x]`，AI 不自创需求；遗留问题（`[阻塞]`、没做的 `[发现]`）
   在回复里列给用户，用户确认要做的才落成新 `T`；`TIPS` 只写"确实有"，**不写占位**。
4. 长期待办只写 `TASKS.md`；本文只记机制，不记待办、不记进度。
5. 不停下来等确认；遇到困难自己解决并记下结论（只有卡住 / 跳过 /「三类必须弹窗」才停，其余自己决定并写 decision，见第 11 条）。
6. `[阻塞]` 只有钩子写，AI 不写也不删；判断某条不该做时在回复里说明理由，交用户决定。
7. **批次号**从 `queue-init` 注入里抄，**一旦写下就不再变**，即使这批里提交好几次：
   `DONE.md` 标题写 `## 批次 <批次号> · 2026-10-22 · 会话 xxxxxxxx`，
   `OVERVIEW.md` 的条目挂 `批次 <批次号>`，commit message 统一以 `批次 <号> · [T<n>] ` 开头
   （钩子每轮注入的提交要求里已经拼好；带 `T` 号后 `git log --grep '\[T12\]'` 就是这个需求的时间线）。
8. **`DONE` 标题不写 `提交 n→m`**：`m` 要等收尾提交之后才知道，而写下它本身又是一次提交——
   自指，永远追不上。要数这批提交了几次：`git log --oneline --grep '批次 <号>'`。
9. **一批多长看行数，不看条数**：判据是"预计这批的完成说明（每条 4~6 行）> ~80 行"/
   "队列 > 500 行"/"这一阶段的目标已经变了"；条数只是经验值（通常 8~12 条），**不是上限**。
   换批要新号：`node .continue/hooks/queue-init.mjs --new-batch`（**不要自己编号**）。
10. **长任务在队列里插里程碑节点**（不另建计划文件）：预计 > 16 条、或能明显切成几段时，
   每 8~12 条之后写一个 `## 里程碑 MS1 · <名字>` + 一行 `- 验收：<这一段做完要跑的命令>`。
   它前面的条目全做完（未完成的 `[发现]` 不算）、而它还没有 `- 确认：已验收` 时钩子**硬停**：先跑验收、把结果贴出来，
   再弹窗问用户「继续下一段 / 调整队列 / 先收在这里」；只有拿到"继续"才补确认行、收尾本段、
   换批次号、删掉已完成的条目，然后接着做。**替用户写确认行 = 自己给自己验收**；
   最后一个里程碑验收完之后才走正常的五步收尾（含归档）。
11. **自己决定 vs 问用户**（与每轮注入同口径）：默认自己决定并把取舍写进
   `doing/<会话ID>-decision.md`（`## D<n> · 决策点` + 决定 / 为什么 / 影响，`audit-ids` 会校验）。
   **只有三类弹窗**：退不回去的动作、只有用户知道的信息、规矩要求他签字（里程碑 / `[阻塞]` / 增删需求）。
   "有多种做法""有歧义"**不是**理由——自己选，写清为什么，挑最可撤回的那个。

## 4. 队列格式与完成说明

```markdown
# 队列 · 会话 xxxxxxxx

> 状态：执行中
> 创建：2026-10-22
> 批次：<批次号>

- [ ] [T12] 给设置页加导入导出：`src/settings/io.ts` → `npm test` 全绿
- [ ] [T12] 补边界用例：`test/settings/io.test.ts` → 新增 3 条且全绿
```

**每条任务做完、改成 `[x]` 之前，先在它下面就地写完成说明**（缩进两格，用普通列表，
**不要用复选框**——`- [ ]` 会被解析成新任务）：

```markdown
- [x] [T12] 给设置页加导入导出：`src/settings/io.ts` → `npm test` 全绿
  - 做了什么：抽出 `exportSettings()` / `importSettings()`，旧的内联逻辑删掉
  - 为什么：导入要校验 schema，散在组件里得改三处才能对齐
  - 验证：`npm test` 12 条通过；手点了一遍导入旧版本配置文件
  - 批次：<批次号>
```

四条要求：

1. 写**怎么做的、为什么这么做、怎么验证的**——不要写"优化了一下"；
2. **`验证：` 是一行凭证，不是客套**：自测没通过、或者命令根本没跑起来，就不许把条目改成 `[x]`。
   项目用什么方式自测由项目定；配了 `checks.fast` 时提交前门禁会亲自再跑一遍，比自报更准；
3. 收尾时这段是**原样搬进 `DONE.md`** 的；
4. 只要结论与理由，**不要贴大段代码**（代码在 git 里，会漂）。

**写进 `TIPS.md` 的门槛**：调了很久才定位的；改了 A 却红了 B，或工具 / 平台的隐蔽默认值反直觉的；
不记下来下次一定重踩、且重踩代价明显的。
**不算坑**：语法记错、漏读文档导致的误判、临时的环境差异、一条命令就能查明的现象。**宁可少写**。

## 5. 走一遍完整流程

1. 用户提出需求 → 记进 `TASKS.md`，分配 `T` 编号；
2. 讨论到要动手 → 先看 `doing/` 里有没有**别的会话**在跑（§9 的前提）：
   - **没有**（空树）→ 按常规在 `doing/<sid>.md` 建队列，本会话直接干完；
   - **有** → 把整份队列写进 `doing/.worktree/todo/queue.md` + 上下文 `context.md`（条目挂 `[T12]`、最后一条 `[自审]`），然后**停手**；
3. Stop 钩子建执行树并开新窗口；新会话第一条消息自动接管，队列变成 `doing/<新会话>.md`；
4. 每轮钩子递一条 → `[~]` → 干活 → **自测通过** → 写完成说明 → `[x]` + 提交（队列一起提交），回复末尾留一行 `队列还剩 N 条 · 说「继续」接着做`（宿主截断 Stop 反馈时，这是唯一信号）；
5. 队列清空 → **自动收尾**：搬 `DONE` → 更新 `OVERVIEW` → 勾 `TASKS` → 自问 `TIPS` → 归档队列 → 一次提交（有 `[阻塞]` / 未验证条目时才先请用户拍板）。

## 6. 钩子怎么工作

注册在 `.codebuddy/settings.json`（安装器自动写入，登记表是 `install.mjs` 的 `HOOKS`；重装会重写这些 command，改过的 `--event=` 参数要一并写回登记表）。**每条注册都经 `run.mjs` 包装器**：钩子自己崩了（如 import 了已删导出）是 exit 1，宿主当"未阻止"静默放行、队列就此停摆且无提示，包装器把它翻成 exit 2 + 告警。外加一个 git 钩子：

| 事件 | 脚本（注册命令都带 `--event=<事件>`） | 做什么 |
| --- | --- | --- |
| UserPromptSubmit | `queue-init.mjs --event=UserPromptSubmit` | 每个会话**第一次**收到消息时，注入会话 ID、队列路径、批次号与协议；之后静默——**唯一例外是协议指纹变了**（`hooks/*.mjs` 被换过，典型场景是升级），此时重新注入一次并声明旧协议作废（手动跑 `--new-batch` 则直接打印一个新批次号） |
| UserPromptSubmit | `auto-continue.mjs --event=UserPromptSubmit` | 轮次计数归零（人工介入后重新计），并在日志记一行「收到用户消息 · 第 N 次」 |
| Stop | `dispatch.mjs --event=Stop` | 前提是 `doing/` 里已有别的会话队列：`todo/` 有待派发内容且没派发过 → 基于 HEAD 建 `doing/.worktree/worktree_<单词>_<YYYYMMDD>` + **同名分支**（单词取 `queue.md` 头部的 `> 树名：`，没写就退化成 `task`）+ 拉 IDE 窗口；空收件箱 / 本会话已有队列 / 没人在跑 / 同一份已派发 / 在树里 → 放行；**失败只告警不拦会话**（拦住会让 AI 在规划区开工） |
| Stop | `auto-continue.mjs --event=Stop` | 读本会话队列：没有队列 → 放行；有 `[ ]` / `[~]` → 递这一条；连续 N 轮没做完 → 标 `[阻塞]`；都没了 → **自动收尾**（有 `[阻塞]` / 未验证条目时才先请用户拍板） |
| Stop | `auto-commit.mjs --event=Stop` | 工作区有未提交改动 → 先跑 `checks.fast`，再提醒提交；没有 → 放行 |
| git pre-commit | `pre-commit.mjs` | 提交前跑 `checks.fast`，失败拒绝提交；**一次提交勾掉多条队列条目也拒绝**（见下） |

**`--event=` 是日志里事件名的来源**：同一个脚本挂在两个事件上时，光看脚本名分不清"用户说话触发的"
还是"停下触发的"；参数写在注册表里跟着事件走，缺参数（手动跑 / 自检）时退回按 payload 推断。

**Stop 的续跑上限（`loop_limit`）**：group 级字段（与 `hooks` 同级，形如
`{ "hooks": { "Stop": [ { "hooks": [...], "loop_limit": 100 } ] } }`），取**所有 Stop group 的最大值**，`-1` 不限、缺省 1。

- 安装器只写进**本框架自己的** group；和自定义钩子同组时不写、只告警（写进去会放宽它们的续跑次数）；
- 改完要**重启会话**（钩子配置在启动时拍快照）；`check.mjs` 不查这一项（宿主行为），
  要确认就跑一遍队列看日志里的 `续跑第 N 次`。

**队列标记由 AI 自己写，钩子只读。** 脚本唯一的写操作是"连续 N 轮没做完 → 标 `[阻塞]`"。
这样队列文件跟着任务进同一个提交；钩子若自己改勾，刚提交完工作区又脏，守卫会为"只改了一个勾"再拦一次。

**放行条件**（`auto-continue` 不拦，按判定顺序）：① 不是 Stop 事件 / 拿不到会话 ID；② 刹车开着
（`.continue/auto.off`）；③ 本会话没有队列（纯问答不打扰）；④ 头部是 `> 状态：讨论中`；⑤ 队列没有条目；
⑥ 没有 `[ ]` / `[~]`、**没有待验收的里程碑**，且**收尾指令已下发过**（自动收尾那次，或请用户拍板那次）。

**里程碑关卡**：`## 里程碑 MS1 · 名` + `- 验收：…` 是**硬停点**：它前面的条目全部 `[x]` / `[阻塞]`、
而它自己还没有 `- 确认：已验收` 时，钩子只下发"跑验收 → 问用户 → 拿到答复才继续"，不递后面的任务。
同一把钥匙（里程碑 + 批次）只提醒一次，连续 N 轮没推进就升级成「关卡卡住了」。

**做不完就隔离**：同一条连续 N 轮没勾掉 → 标 `[阻塞]`、跳过它继续下一条（中间换了一条就归零）。
这类条目收尾时必须单独摆给用户，**不自动丢弃、也不自动重试**；用户改回 `[ ]` 就重新得到 N 次机会。

**收尾默认自动**：`[ ]` / `[~]` 都没了 → 直接下令"按 §3 第 3 条做完五步"，**不弹窗问"要不要收尾"**
（记账没有取舍空间）。**只有两类才请用户拍板**：`[阻塞]`，以及打了 `[x]` 却缺 `验证：` / 自述"未验证"
的条目——这两类人没看过等于悄悄丢活，那时逐条问（改描述继续做 / 删除 / 先留着并收尾）。**只催一次**。

**不会因为"跑太久"中断**：钩子不看上下文长度，只在「三类必须弹窗」、或有卡住 / 未验证条目要拍板时才停。

**暂停与刹车**：

- 队列头部改成 `> 状态：讨论中` → 只停这一份队列的递送，改回来继续；
- `touch .continue/auto.off` → 两个 Stop 钩子都只放行（连提交守卫一起停），删掉即恢复，已 gitignore；
- 想彻底停就结束会话，队列不会丢。真要丢弃进度才删队列文件。

**一次提交只勾一条**：`pre-commit` 数暂存区里把 `[ ]` / `[~]` 改成 `[x]` 的条数，超过上限就拒绝——
给"一个回合把整批做完再一起提交"兜底（Stop 钩子只在停下时触发，看不见过程）。只算**已跟踪队列文件**，
新建队列、归档都不算。**提交守卫不会无限拦**：同一份改动（工作区指纹不变）最多拦
`AUTO_COMMIT_MAX_BLOCKS` 次之后放行；真动了文件指纹就变，重新计数。

**改了 `.codebuddy/settings.json` 不会热加载**：钩子在会话启动时拍快照，改完必须重启会话才生效。

**日志**：每个会话一份 `.continue/.logs/<session_id>/run.md`（归档的 `queue.md` / `decision.md` 在同一目录下），只在本机、已 gitignore。分两个区：

```md
## 任务递送（queue-init / auto-continue）
- 2026-10-22 09:14:10 +08:00 · [auto-continue · Stop] 递任务 · 剩 3 条 · 第2/5条 · [T12] 给地形加分块生成…
<!-- s:auto {"count":0,"stopSeen":7,"lastStopAt":"2026-10-22T01:14:52Z",…} -->

## 提交守卫（auto-commit）
- 2026-10-22 09:20:47 +08:00 · [auto-commit · Stop] 自测通过 · 3s · npm run check:fast
<!-- s:commit {"dirty":false,"stopSeen":12,"guard":{…},"check":{…}} -->
```

- **每次事件都留一行**：用户消息 / 递任务 / 拦截 / 隔离 / `空转 · <原因>`，状态行里有 `promptSeen` 与
  `stopSeen`。旧口径"空转不记"的代价是：正常连续放行在日志里一片空白，和"钩子压根没跑"分不出来；
- **时间用本地时区并带偏移**，行首 `[钩子名 · 事件名]` 标明来源（事件名来自注册命令的 `--event=`，
  缺省时退回 payload 推断）——不用换算 UTC，两个钩子并发写同一份文件也能一眼分清；`lastStopAt` 仍是 ISO，给脚本读；
- **纯问答会话也会有一份日志**：`queue-init` 的注入行与 `auto-continue` 的"收到用户消息"行就是它存在的理由——
  没有这两行，就没法回答"钩子到底跑没跑"；Stop 阶段没有队列时不往里写，文件因此不会无限长；
- `<!-- s:… -->` 是状态行，读取时取**最后一条**；
- Stop 上多个钩子并发：改写前抢 `run.md.lock`，抢不到降级为追加，内容不丢；每个区有行数上限，不分裂文件。

**`config.json` 的键**（由 `check.mjs` 与两个门禁读取；重装框架只补缺的键，改过的值保留）：

| 键 | 作用 |
| --- | --- |
| `fast` | 每次提交前跑的聚合命令，默认 `node .continue/hooks/check.mjs --fast` |
| `full` | 完整体检命令。钩子**不读**它，留给人和 CI：本地想跑全量时手动执行 |
| `timeoutSec` | 单条检查命令的超时秒数，要小于注册钩子时的 `timeout` |
| `project` | 项目自己的**快**检查命令（字符串或数组），由 `check.mjs` 在内置检查之后依次执行；`--fast` 与全档都跑。**安装器会自动探测并填入**（探不到就留空 + 给建议） |
| `projectSlow` | 项目自己的**慢**检查命令（字符串或数组，如 e2e / 集成测试）：**只在全档跑**，`--fast`（pre-commit、Stop 守卫）跳过 |
| `git.push` | 提交后是否自动 push（默认 `true`）：默认提交完就推到当前分支；设成 `false` 则只提交、推送交给用户。**手工 `worktree.mjs` 建树也听它**——`false` 时新分支只存在本地（想推自己 `git push -u origin <分支>`） |
| `worktree.auto` | 是否自动派发交接队列（默认 `true`）：`doing/` 里已有别的会话队列时，写 `todo/` → Stop 建树开窗；设成 `false` 只保留手工 `dispatch.mjs` |
| `worktree.openWindow` | 派发后是否自动拉 IDE 窗口（默认 `true`）：无 GUI / CI 设 `false`，只建树 |

**可调开关**（在注册的 `command` 前面加环境变量，如 `CONTINUE_BLOCK_AFTER=8 node .continue/hooks/auto-continue.mjs`）：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `CONTINUE_BLOCK_AFTER` | `5` | 同一条连续几轮没勾掉就标 `[阻塞]`（上文的 N） |
| `CONTINUE_DISCOVERED_LIMIT` | `5` | 队列里允许同时存在几条未完成的 `[发现]` |
| `QUEUE_INIT_STYLE` | 空 | 设成 `text` 时改用纯文本输出注入内容（平台不认 `hookSpecificOutput` 时用） |
| `AUTO_COMMIT_STYLE` | 空 | 设成 `json` 时改用 `{"continue":false,"reason":…}` 而不是 exit 2 |
| `AUTO_COMMIT_MAX_BLOCKS` | `2` | 同一份未提交改动最多拦几次 |
| `CONTINUE_MAX_ITEMS_PER_COMMIT` | `1` | 一次提交最多把几条队列条目勾成 `[x]` |
| `CODEBUDDY_SESSION_ID` | 宿主注入 | 只读：钩子用它推导本会话队列路径与日志目录（`<sid6>`）；**不再用它命名工作树**（树名见 §9）；不是给人设的开关 |
| `WORKBUDDY_SESSION_ID` | 宿主注入 | 同上，WorkBuddy 的等价变量 |

### 自测门禁

`config.json` 的 `checks.fast` 装完即指向框架自带的聚合入口 `node .continue/hooks/check.mjs --fast`。
它在**两处**被亲自执行：

| 位置 | 时机 | 失败时 |
| --- | --- | --- |
| git pre-commit | 每次 `git commit` | 拒绝提交，打印输出末尾 |
| Stop · `auto-commit` | 停下时工作区还脏 | 改发「先修，**不要提交**」 |

命令不存在 / 超时都**不算测试失败**（框架自己坏了不能卡死用户），但要如实写"未验证"。
**检查由脚本跑，不接受 AI 自证**——"我已经跑过了"没法验证，退出码可以。
紧急绕过 pre-commit 用 `git commit --no-verify`，并在提交信息里写明原因。

**内置的检查**（`check.mjs` 的 `CHECKS` 里登记，加检查 = 加一行；`--list` 看实时清单）：

| 名字 | 挡的是什么 |
| --- | --- |
| `ids` | 编号唯一、跨文件引用完整性、批次唯一与对齐、模块名对齐、`[~]` 重复、未知标记、队列文件名、模板污染、（框架仓库）技能完整性 |
| `docs` | 入口文档与队列文件的体量上限（行数 + 字节；上限值只在 `lib.mjs` 的 `DOC_LIMITS` / `DOC_BYTE_LIMITS` 定义一处）。`DONE.md` 超了就跑 `node .continue/hooks/archive-done.mjs`，它按同一个上限把最旧的批次整节搬进 `DONE.archive.md` |
| `config` | 配置一致性：README 开关表 ↔ 代码 `process.env` 双向核对；`config.json` 用到的键都有文档 |
| `hooks` | 钩子离线自检：临时副本里灌事件 JSON，断言各钩子的退出码与输出 |

**要加自己的项目检查**（比如 `npm test`），别改 `CHECKS`——那是框架的登记处，升级时会被覆盖。
写进 `config.json` 的 `checks.project`（字符串或数组），`check.mjs` 会先跑内置检查、再依次跑它们：

```jsonc
{
  "checks": {
    "project": ["npm test", "node scripts/lint.mjs"],
    "projectSlow": ["node scripts/e2e.mjs"]
  }
}
```

**区别只看"提交前愿不愿意等"**：`project` 必须秒级（`--fast` 与全档都跑），`projectSlow` 可以几十秒（只在全档跑）。
分档由**键**决定、不猜命令内容——慢命令写进 `project`，每条任务就都卡一次，没有别的兜底。

为什么要走这个口子、而不是把 `checks.fast` 指向自己的脚本：那样**删掉框架那一行不会有任何提示**，
编号审计和体量门禁就悄悄失效了。细节：`auto-commit` 按**工作区指纹**（`git diff HEAD` + 未跟踪清单）缓存，
同一份改动只跑一次；`timeoutSec` 要小于注册时给 `auto-commit` 的 `timeout`。

**钩子没反应时**：先 `node .continue/hooks/check.mjs hooks` 看离线自检；全绿再查注册与日志（`.logs/` 一直空 = 注册没生效，重启会话）。

## 6.5 从旧版升级 / 从已有文档迁移

旧名 `queues/`、`EXPERIENCE.md` 与旧版计划文件由 `migrateLegacyLayout()` 每会话首次启动时自动对齐/归档（幂等、不覆盖；旧计划搬进 `.logs/<会话ID>/plan.md`）。存量文档用 `<skill>/scripts/scan-docs.mjs` 只读扫描，按 `SKILL.md`「集成已有文档」合并：只搬结论不搬全文、原文件保留、不编批次号与 `T` 号，每段标一行 `> 来源：<路径>`（既是溯源，也是"已登记"标记）。

**技能升级**：重跑安装器即升级。**机制文档 `README.md` 与 `hooks/` 一样总是覆盖**（真身在技能模板）；4 份数据文档（`TASKS` / `DONE` / `OVERVIEW` / `TIPS`）实例不动、不生成备份，**只在 `.installed.json` 记录的模板哈希变了时报一次**（实例被填成什么样不影响判断——它与模板不同是定义上的必然，报出来只是噪音）。`node .continue/hooks/check.mjs version` 逐文件比对实例与模板，报出落后的框架文件（版本号不动也看得出来）。

## 7. 容易踩的地方

判据就是上面的原理 3：**这条规矩违反了，机器会不会红？不会，它就不是约束，只是愿望。** 所以这一节只留两类：已经有机器兜底的、和确实没法机械判定的。

### 7.1 已经有机器兜底

这些不需要你记住——违反了 `check` 会红，提交前门禁会拦。

| 规矩 | 谁在查 | 违反时 |
| --- | --- | --- |
| 一个 `T` 号只能有一条需求 | `audit-ids` | `✗ TASKS.md 里 T3 出现在 2 条条目行上` |
| 队列引用的 `[Tn]` 必须存在于 `TASKS.md` | `audit-ids` | `✗ doing/x.md 引用了 T99，但 TASKS.md 里没有` |
| 批次号全局唯一 | `audit-ids` | `✗ DONE.md 里批次 X 出现 2 次` |
| `DONE` 的批次与 `OVERVIEW` 批次索引表互相对得上 | `audit-ids` | `⚠ DONE.md 有批次 X，但 OVERVIEW.md 的批次索引表里没有这一行`（`--strict` 下为错误） |
| `TIPS` 的模块名必须在 `OVERVIEW` 里有同名小节 | `audit-ids` | `✗ TIPS.md 有模块「X」，但 OVERVIEW.md 里没有` |
| 队列文件名必须像会话 ID | `audit-ids` | `✗ doing/x.md 的文件名不像会话 ID` |
| 一条队列里最多一条 `[~]` | `audit-ids` | `✗ doing/x.md 里有 2 条 [~]` |
| 队列只用四种标记 | `audit-ids` | `✗ doing/x.md 有不认识的标记：「- [-] …」` |
| `DONE` 里记了完成的 `T`，`TASKS` 里也必须是 `[x]` | `audit-ids` | `✗ DONE.md 记了 T12 已完成，但 TASKS.md 里它还是 `[ ]`——收尾时忘了勾` |
| 一次提交最多勾掉 1 条队列条目 | `pre-commit` | `✗ 这次提交勾掉了 2 条队列条目（上限 1 条）` |
| 格式示例放进围栏代码块就不算任务 | `parseQueue`（机制） | — |
| `> 状态：讨论中` 只在前 6 行有效 | `parseQueue`（机制） | — |
| 文档与队列不能无限涨 | `audit-docs` | `✗ README.md N 行 > 上限 M 行` |
| 每批队列最后一条必须是 `[自审]`，勾掉时要三层凭证齐全 | `audit-ids` | `✗ doing/x.md 的最后一条不是 [自审]` |
| 钩子改坏了 | `selftest` | `✗ auto-continue · 有待办 → 拦住并递第 1 条` |

跑法：`node .continue/hooks/check.mjs`（`--fast` 只跑快档，`audit-ids.mjs --strict` 把提示也升级成错误）。

### 7.2 只有人能做对的

**一份队列只归一个会话**。两个会话同时改同一份队列，条目状态会错乱；钩子不知道"另一个会话是不是也在改它"。
默认路径是**交接模式**（§9）：`doing/` 里已有别的会话队列时，主工作区写 `todo/`、Stop 自动建树、新会话接管后队列归它一个人；`doing/` 空着就直接在本会话干。
手工并行仍可用 `node .continue/hooks/worktree.mjs <单词> --task="…"`：建 `.continue/doing/.worktree/worktree_<单词>_<YYYYMMDD>`（已 gitignore）、**分支同名**，把任务写进树里的 `doing/worktree.md` 并尝试拉新窗口；树里第一个会话自动把它改名接管（两份并存时不覆盖），树里还能再建树（层数会打印）。**必须在新路径另开会话**。
`<单词>` 由 AI 按这一批的需求取（`export` / `auth` / `perf` 这类英文词，2~16 位），日期由脚本加；同一天同一个单词撞了就追加 `-2`。

**收尾不合并**：工作树里这批做完、文档收尾提交完就结束了。`rebase` / `merge` / 删树都由用户自己处理——
框架既不自动做，也不在注入里要求 AI 做（2026-10-24 取消了原来的"提交后 rebase → merge → push"三步）。
原来那条链的代价是"收尾必须等父树干净、冲突要现场按语义解"，对"做完就交给人"的用法是纯负担。

**`[~]` 是「进行中」，不是「跳过」**。同时多条 `[~]` 机器能抓，但"用它假装跳过"这层意图机器看不出来。

**钩子命令里的 `.continue/hooks/…` 是相对路径**，要求钩子进程的 cwd 是项目根；`Cannot find module` 时把注册的 command 换成绝对路径。

**别人的未提交改动会让提交守卫拦你**（有次数上限）。它只让你提交本会话的文件：**不要硬提交别人的文件**，在回复里列出来，由人决定（提交 / 暂存 / `touch .continue/auto.off`）。

## 8. 持续迭代：三层目标与每批自审

每批队列的**最后一条**固定是 `[自审]`（`audit-ids` 查它存在且在最后；新条目与 `[发现]` 一律插在它前面）。
它审的三层，就是"这个项目还在变好"的全部判据：

| 层 | 问的问题 | 达标的证据 |
| --- | --- | --- |
| **L1 可测量** | 这一批新做的东西，有没有一条**坏了就会报错**的检查？ | 有门禁：检查名 + 跑一次的命令；没门禁：可重复的手动复现步骤 + 预期结果 |
| **L2 可对抗** | 它上一次被**故意弄坏**是什么时候？ | 一条先红后绿的用例；没有用例就真的改坏一次再改回，记下前后现象 |
| **L3 可外部** | 这批的判断依据里，几条来自真实使用者、几条是自己想的？ | 用户原话、真实接入、别人报的 bug；全自证就明写「0 条外部输入」 |

三层查的是**问题**，不限定项目形态：没有测试框架就降级成手动复现，**降级要写明，不能只写"无"**；下一批有机会再把其中一层升格成自动检查。

自审打 `[x]` 前要写三层结论（`- L1：` / `- L2：` / `- L3：` 各一句 + 证据）。都达标且确实找不到改进时，
写**排除记录**：从哪些角度找过、为什么它们不构成问题——**"没有建议"是要举证的结论，不是偷懒的默认值**。
有改进项：能当场修的**修一条**（一个提交一件事），其余落成新 `T` 号进下一批。

**收敛判据（停止条件）**：`DONE.md` 里**连续 3 批**自审都是"无改进项"且都带排除记录，才算"接近完美"。
三层全写成"无检查 / 没弄坏过 / 0 条外部输入"的批次**不计入这 3 批**——那是"没有可审的东西"，不是"审过了没问题"。

机器只查结构与凭证（在最后、三行齐全），**质量由人判断**——"AI 说它完美"永远不算证据，
这正是 L3 存在的理由：没有外部输入时，自证只能证到自己相信为止。

## 9. 交接模式：规划区 → 执行区

**触发条件**：主工作区里 `doing/` 已经有**别的会话**的未完成队列，且 `config.json` 的
`worktree.auto` 为 `true`。没有人在跑时**不走交接**——直接写 `doing/<sid>.md` 在本会话干完；
多开一个窗口只是把"一条命令能做完的事"拆成两步。

| 位置 | 谁在跑 | 干什么 |
| --- | --- | --- |
| 主工作区 | 原会话 | 讨论需求、拆条目；把整份队列写进 `.continue/doing/.worktree/todo/queue.md`、上下文写进 `context.md`，然后**停手** |
| （Stop 钩子） | `dispatch.mjs` | 基于 HEAD 建 `.continue/doing/.worktree/worktree_<单词>_<YYYYMMDD>`、**同名分支**，拉 IDE 新窗口（单词取 `queue.md` 头部的 `> 树名：`） |
| 新工作树 | 新会话 | 第一条消息由 `queue-init` 接管：`todo/queue.md` → `doing/<新会话前 6 位>.md`（批次沿用），`context.md` 附进注入并存档到 `.logs/<新会话>/handoff.md` |

五条规矩：

1. 主工作区**不要建** `doing/<sid>.md`：一建，Stop 就开始给规划区递任务，隔离当场破功
   （`dispatch` 也会判定"本会话已在干"而不再派发）；
2. `todo/` 里已有内容时**不要覆盖**：停手让它派发，或先问用户；
3. 派发按**内容指纹**去重：`state.json` 记着树的位置与这份队列的指纹，树还在且内容没变就不重复建；
   内容变了（同一会话派发第二批）会再建一棵，同一天同一个单词撞名时追加 `-2` 后缀；
   **树没了但内容没变也不重建**——那说明是同一批的残留（做完后清理 / 被人删掉），不是第二批；
   再建只会多一个同名目录、甚至把做完的活重做一遍。确实要重跑：删掉 `doing/.worktree/todo/state.json`；
   **树名来自 `queue.md` 头部的 `> 树名：<单词>`**（AI 按这一批的需求取词），不写就退化成 `worktree_task_<日期>`；
4. `doing/` 空着时写了 `todo/` 也**不会派发**：`dispatch` 会提示把内容搬进 `doing/<sid>.md`——
   这是防"手塞收件箱"的兜底，不该当成常态；
5. **收尾不做任何合并**：树里的会话做完这批、按五步收尾并提交，就算结束；`rebase` / `merge` / 删树
   都由用户自己处理。树里的会话与主工作区并行，互不递任务。

排错与手动操作：

- 只预演：`node .continue/hooks/dispatch.mjs --dry-run`（不建树、不开窗，被守卫挡住时打印原因）；
- 关掉自动派发：`worktree.auto=false`，之后写完 `todo/` 手动跑一次 `node .continue/hooks/dispatch.mjs`；
- 窗口没弹出来：打印的路径直接 `cd` 过去开会话，交接仍然有效；
- 想看有哪些树与分支：`git worktree list`（框架不再提供"收尾同步"脚本，合并由用户自己做）；
- 建树失败（目录 / 分支已存在）：todo **原样保留**，不会丢任务；
- 老的手工路径（`worktree.mjs` → `doing/worktree.md`）仍可用，`queue-init` 同样会自动接管。
